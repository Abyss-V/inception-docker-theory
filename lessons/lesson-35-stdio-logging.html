stdio & logging

DEEP-CUT

This lesson is about how output moves. A program in the container writes bytes to stdout or stderr. Those bytes travel through containerd and the shim, then into dockerd, where they can be copied to a live attach session, turned into stored log records, or both.

governing idea

A container process does not “write to Docker logs.” It only writes bytes to its standard file descriptors. Docker logging begins after those bytes leave the process.

So the right way to study this lesson is to follow one byte from start to finish:

This is the roadmap for the whole lesson. We will now walk through each arrow.

1. Where the bytes start: stdout and stderr

Inside a Linux process, stdout is normally file descriptor 1 and stderr is file descriptor 2. The program does something like:

write(1, "hello\n", 6);
write(2, "oops\n", 5);

At this moment the program has only done a normal kernel write to an open file descriptor. It has not created a “log record,” and it has not called a Docker API.

important distinction

Byte stream means the raw stdout/stderr bytes. Docker log record means the structured message that dockerd later creates from those bytes.

2. How the process gets connected to containerd and the shim

When the container task is created, containerd sets up the standard I/O endpoints that will carry stdin, stdout, and stderr. On Linux, the common non-TTY path uses named pipes (FIFOs) so independent processes can open the same path and exchange stream data.

termmeaning here
FIFOA named pipe with a filesystem path. containerd can open one end and the shim/task side can open the other end.
shimThe per-container runtime helper that keeps the task and its I/O alive even if the original CLI disconnects.
TTY / PTYA pseudoterminal. If enabled, stdout and stderr no longer stay as two separate output streams.

So the job split is:

  • containerd prepares the I/O endpoints and task configuration.
  • the shim owns the lifetime of the task and its I/O.
  • runc starts the container process with those standard streams attached.

Source anchors: containerd 2.2.6 · pkg/cio and runtime-v2 task create path.

3. How dockerd receives the bytes

Once the task exists, containerd exposes a live I/O object for it. dockerd connects to that object and begins reading the task's stdout and stderr streams. Internally, Docker Engine then sends those bytes into its own stream-distribution layer.

The key idea is simple:

containerd task stdout/stderr
            ↓
        dockerd receives bytes
            ↓
   dockerd can copy the same bytes to:
   - the logging path
   - a live attach session

This is why stored logs and live attach can coexist. Docker is not choosing one or the other at the moment the program writes to stdout. It is reading the stream once and then distributing it.

names you may see in the source

The containerd-side live I/O object is called DirectIO. Docker Engine’s stream fan-out object is called StreamConfig. You do not need those names to understand the mechanism, but now you know what they refer to when you inspect the source.

Source anchors: Docker Engine 29.6.2 · daemon/container/container.go::InitializeStdio, daemon/internal/stream/streams.go.

4. Where raw bytes become stored log records

The logging path is where Docker stops thinking in terms of a raw stream and starts thinking in terms of messages.

Docker Engine runs a copier for stdout and another copier for stderr. Each copier reads bytes, searches for newline boundaries, and when it has a line, creates a log message with:

  • the line bytes,
  • the source stream: stdout or stderr,
  • a timestamp.

If a line is very long or never ends with \n, Docker can emit a partial log message instead of waiting forever.

source-over-folklore correction

Docker log records do not preserve application write(2) boundaries. Two writes may become one stored line. One large write may become several partial records.

After Docker Engine has created a log message, it hands that message to the selected logging driver such as json-file.

Source anchors: Docker Engine 29.6.2 · daemon/logger/copier.go, daemon/logger/logger.go, daemon/logger/jsonfilelog.

What about stdout/stderr ordering?

Within one stream, byte order is preserved. But stdout and stderr are drained by different goroutines. So Docker does not promise one perfect combined ordering across both streams.

5. docker logs and docker attach are different pipelines

commandwhat it readswhat that means
docker logsstored log recordsIt goes through the logger read path.
docker attachlive stream bytesIt taps into the current live output stream.

So:

  • docker logs is mainly a storage read.
  • docker attach is mainly a live stream.

If Docker is not using a TTY, one API connection may carry both stdout and stderr. In that case Docker prefixes each payload with an 8-byte header so the client can demultiplex the stream back into stdout versus stderr.

why the 8-byte header exists

The program inside the container did not generate that header. Docker adds it later so one connection can carry two logical streams.

Source anchors: Docker Engine 29.6.2 · daemon/logs.go, daemon/attach.go, api/pkg/stdcopy/stdcopy.go.

6. Why -t changes more than formatting

Without a TTY, stdout and stderr stay separate. With -t, the process gets a pseudoterminal. That changes the wiring before Docker logging sees the bytes.

without -t:
  fd 1 → stdout stream
  fd 2 → stderr stream

with -t:
  fd 1 and fd 2 → one terminal stream

That is why Docker cannot later tell which original descriptor produced each byte in TTY mode: that information was destroyed earlier by the PTY wiring.

important consequence

-t does not just make output look terminal-like. It changes the actual data path, and it can also change application behavior because programs detect that they are talking to a terminal.

Source anchors: OCI runtime-spec 1.3.0 · process.terminal; containerd 2.2.6 pkg/cio terminal handling.

7. How a slow logging path can eventually block the application

Now follow the pipeline backward. If the logging driver is slow, the logging copier stops draining its input quickly enough. That can stall Docker Engine’s stream distribution. Then Docker stops draining containerd’s live output quickly enough. Eventually buffers fill, and the next application write to stdout or stderr can block.

slow logging driver
      ↓
log copier cannot keep up
      ↓
dockerd stops draining fast enough
      ↓
runtime buffers fill
      ↓
application write() can block

This is not always immediate because several buffers may absorb data first.

Non-blocking logging

Docker also has a non-blocking mode. In that mode, Docker puts log messages into an in-memory queue and a background goroutine forwards them to the real logging driver.

source-over-folklore correction

When the non-blocking queue is full, Docker drops the new incoming log message. It does not rotate by evicting the oldest queued message.

Source anchors: Docker Engine 29.6.2 · daemon/logger/ring.go.

8. Inspect it yourself

A. prove stdout and stderr are separate without a TTY
docker rm -f l35 2>/dev/null || true

docker run -d --name l35 alpine sh -c '
  i=0
  while :; do
    printf "OUT %03d\n" "$i"
    printf "ERR %03d\n" "$i" >&2
    i=$((i+1))
    sleep 1
  done
'

docker inspect -f 'tty={{.Config.Tty}} driver={{.HostConfig.LogConfig.Type}}' l35
docker logs --tail 6 l35
B. compare stored logs with live attach
# terminal 1
docker logs --tail 3 l35

# terminal 2
docker attach --no-stdin l35
# detach with Ctrl-p Ctrl-q
C. see that TTY mode changes fd topology
docker run --rm alpine sh -c '
  echo "stdout=$(readlink /proc/$$/fd/1)"
  echo "stderr=$(readlink /proc/$$/fd/2)" >&2
'

docker run --rm -t alpine sh -c '
  echo "stdout=$(readlink /proc/$$/fd/1)"
  echo "stderr=$(readlink /proc/$$/fd/2)" >&2
'

9. Check yourself

  • The process writes bytes to fd 1 and fd 2, not to a Docker logging API.
  • containerd and the shim keep the task I/O alive; dockerd reads those streams.
  • dockerd can copy one live stream into both a logging path and an attach path.
  • Stored log records are created later by splitting byte streams into line/partial messages.
  • docker logs reads stored log records. docker attach reads live bytes.
  • TTY mode merges output into one terminal stream earlier, so stdout/stderr identity is lost.
  • A slow logging path can push back far enough that the application eventually blocks on write.
