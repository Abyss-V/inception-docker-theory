The architecture: what actually happens when you type docker run

Five programs, two sockets, and a surprising punchline: none of the programs you'd expect is the one holding your container. We follow the request all the way down and read the source at each handoff.

In Lesson 1 we established that a container is just a host process placed in a configured environment. This lesson answers the obvious next question: which program builds that environment and starts that process? The honest answer is "not the one you think," and the path there explains why Docker is split into the pieces it is.

The intuition

Why isn't Docker just one program?

Imagine the simplest possible design: a single program called docker. You run it, it sets up namespaces and cgroups, it starts your process, and it stays running to babysit that process. Clean — until you think about two things.

First, upgrades and crashes. If that one program is also the parent of every running container, then the moment you upgrade Docker or it crashes, every container on the machine dies with it. That's unacceptable on a server running production workloads. You want to be able to restart the management software without killing the workloads it manages.

Second, two totally different jobs are mixed together. One job is "a thing you type commands into" — short-lived, runs in your terminal, exits. The other is "a thing that persists and supervises containers" — long-running, starts at boot, never attached to a terminal. Cramming both into one binary is like making your text editor also be the operating system.

So the very first split is forced on us: a thin client you run (the docker command) and a long-lived daemon that persists (dockerd). The client's entire job is to translate what you typed into a request and send it to the daemon. Everything real happens in the daemon. Let's prove that from the source, because it's more literal than you'd guess.

Mechanism 1

The docker command is an HTTP client. That's all it is.

Step 1 · Explain

When two programs on the same machine need to talk, one common way is a Unix domain socket: a special file on disk that acts like a two-way pipe. One program listens on it; another connects to it and they exchange bytes. Docker uses exactly this. The daemon dockerd listens on a socket file, and the docker client connects to it and speaks HTTP — the same request/response protocol your browser uses to talk to a website. The daemon exposes a REST API: a set of URLs like /containers/create that you POST to in order to make things happen.

Step 3 · Read it line by line
  • unix:///var/run/docker.sock The client's default target. The unix:// scheme means "connect to this socket file," not a network address. Set the DOCKER_HOST environment variable and the client will talk to a socket somewhere else — including a remote machine — without any other change. That's how one docker command controls a daemon on another host.
  • NewPostRoute("/containers/create", …) A URL and the daemon function that handles it. POSTing to this path with a JSON body creates a container (sets up its config) but does not start it.
  • NewPostRoute("/containers/{name}/start", …) A separate route that actually starts a created container. The {name:.*} is a wildcard capturing the container's id or name from the URL.
  • NewGetRoute("/containers/json", …) A GET route that lists containers — this is literally what docker ps calls.
Where this corrects the familiar version

Two folk beliefs fall here. First, "the docker command runs your container" — it doesn't; it serializes your flags into an HTTP request and sends it. All the logic lives in the daemon. Second, "docker run is one operation" — it isn't. There is no /containers/run route. docker run is the client making two calls in sequence: POST /containers/create, then POST /containers/{id}/start. That's precisely why the separate commands docker create and docker start exist — they're the two halves exposed individually.

A small detail, but it confirms beyond doubt that this channel is real HTTP.

Mechanism 2

dockerd doesn't run containers either — it hands off to containerd

Step 1 · Explain

So the daemon receives your request. Does it create the namespaces and start the process? No — and for the same restart-survival reason as before, one level deeper. Docker's daemon has a lot of high-level jobs: building images, managing networks and volumes, serving that REST API, handling authentication. The Docker maintainers separated the low-level job of "supervise the lifecycle of containers" into its own daemon called containerd, so that piece could be standardized, reused by non-Docker tools, and — critically — kept stable while the higher-level daemon churns.

So dockerd is itself a client of a second daemon. It connects to containerd over containerd's own socket, using a defined API (this one is gRPC — same idea as the REST API above, a request/response protocol, just a different wire format). Here is where that second socket lives:

Step 2 · The source Step 3 · Read it line by line
  • /run/containerd/containerd.sock A second Unix socket, distinct from docker.sock. dockerd opens this and issues commands like "create a container from this bundle," "start it," "tell me when it exits." containerd owns everything about the running container from here down.
Two sockets, two boundaries of responsibility. docker.sock is you → dockerd. containerd.sock is dockerd → containerd. Each is a clean seam where one program stops and delegates to the next. Keep them straight; the first is the one with the famous security footgun we'll dissect in Lesson 46.
Mechanism 3

containerd launches one shim per container — and computes its name from a string

Step 1 · Explain

Now the pattern should feel familiar, because containerd does the same move one final time. It does not hold your container as a child of the containerd process — that would resurrect the original problem, where restarting containerd kills every container. Instead, for each container it launches a small, separate helper process called a shim, and lets that be the container's parent. containerd can then come and go; the shim stays, holding the container. (The full story of how the shim outlives its parent is Lesson 5 — here we only need to know that a separate shim process is spawned per container.)

The interesting mechanism is which shim gets launched. containerd supports pluggable runtimes, each identified by a dotted string like io.containerd.runc.v2. It turns that string into an actual executable filename with a tiny function. Once you see it, the naming convention containerd-shim-runc-v2 stops being magic:

Step 3 · Read it line by line
  • strings.Split(runtime, ".") Take io.containerd.runc.v2 and split on dots → the list ["io","containerd","runc","v2"].
  • parts[len(parts)-2], parts[len(parts)-1] Grab the last two pieces: "runc" and "v2". The prefix (io.containerd) is just a namespace and gets ignored for the filename.
  • "containerd-shim-%s-%s" Fill those two pieces into the template → containerd-shim-runc-v2. That's the exact binary you'll find in the process list. Mystery solved: the name is generated, not hard-coded.
  • exec.CommandContext(ctx, …) Go's way of running an external program. This proves the shim is a separate process that containerd spawns, not code running inside containerd. Separate process = survives containerd restart.
Step 4 · Inspect it yourself

Start a container, then inspect the processes. The fixed relationship is that the container process is supervised by a shim. Do not infer containerd's control relationship from the shim's PPID: runtime-v2 uses a socket API, and the serving shim is deliberately able to survive containerd.

The second row is the load-bearing one: the container process is a child of the serving shim. The shim itself was bootstrapped by containerd, but containerd controls it through the runtime-v2 socket API rather than relying on a durable parent-child relationship. On many hosts the serving shim is adopted by PID 1; a configured child subreaper can change the displayed PPID without changing the architecture. Lesson 5 traces that bootstrap and reconnection path.

Mechanism 4

The shim calls runc — and runc immediately exits

Step 1 · Explain

One layer remains. The shim itself still doesn't know how to build namespaces and cgroups; it delegates that to the OCI runtime, runc (the program from Lesson 1). But runc is not a daemon and not a supervisor — it is a command-line tool that does one job and exits. It creates the container process, hands control back, and terminates. After that, runc is gone from the process list entirely. This is the final twist that makes the whole "who runs your container?" question so counterintuitive.

You can see runc's short-lived, command-per-action nature in the list of subcommands it registers:

Step 2 · The source Step 3 · Read it line by line
  • createCommand / startCommand Two separate subcommands — the same create/start split we saw at the very top of the stack in Docker's REST API, now at the very bottom. The shim invokes runc create then runc start.
  • runCommand A convenience that does create+start in one shot — but each is still a fire-and-exit invocation, not a resident process.
  • "creates an instance … for a bundle" runc's input is a bundle: a directory containing a config.json plus the root filesystem. That config.json is the OCI runtime spec we'll read field-by-field in Lesson 21; for now, just know it's the file that tells runc exactly which namespaces, cgroups, and mounts to set up.
  • the comment's implication runc's model is one command → one action → exit. Nothing about it stays running to babysit the container. The babysitter is the shim above it.
The punchline · who runs your container?

Follow the whole chain and every candidate disqualifies itself. The docker CLI sent an HTTP request and exited. dockerd forwarded it to containerd and moved on. containerd spawned a shim and moved on. runc built the container and exited. The process that is actually left holding your container — its real parent, the thing that would notice it die and report the exit code back up — is the humble shim, the one component nobody talks about. "Docker runs your container" is wrong at all four layers; the true answer is "a runtime shim supervises it, and everything above drives that shim through APIs."

Where we are

The chain, in one view

docker (CLI, you run it, then it exits) │ HTTP over unix:///var/run/docker.sock ▼ dockerd (daemon: images, networks, volumes, the REST API, build) │ gRPC over /run/containerd/containerd.sock ▼ containerd (higher-level task manager; bootstraps or locates a shim service) │ exec.CommandContext(...) → name computed by BinaryName() ▼ containerd-shim-runc-v2 (supervises one container or a runtime-defined group; Docker commonly uses one per container) │ runs the CLI: runc create → runc start ▼ runc (builds namespaces/cgroups from config.json, starts your process, EXITS) ▼ your process (a normal host process, child of the shim)

Every arrow in that diagram is a deliberate seam, and every seam exists for the same reason: so the layer above can be restarted or replaced without killing what runs below it. You typed one command; it descended through five programs and two sockets to become a single clone() parented by a shim. Next lesson we zoom in on the piece that turns out to be doing the real long-term work — the shim — and see how it manages to outlive the very daemon that started it.
