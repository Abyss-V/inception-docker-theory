Docker, From the Source · Part II — Kernel primitives
11

Capabilities: root, chopped into ~40 separate powers

Lesson 7 left a cliffhanger — container root is host root by default, held back by "capabilities." This is that wall. Capabilities split the monolith of root into individual privileges, and Docker hands your container just 14 of them.

Here's the promise we're keeping from Lesson 7: even though a default container's root is genuinely host uid 0, it is nowhere near as dangerous as real root — because Docker has stripped it of most of root's actual powers. The mechanism that makes "root" divisible is Linux capabilities. Once you see the exact 14 Docker keeps and the ~26 it throws away, "container root" stops being a scary phrase and becomes a precise, inspectable thing.

The intuition

Why "root" needed to be broken up

Classic Unix has a binary model of privilege: you are either root (uid 0), able to do everything — reboot the machine, load kernel modules, override every file permission, reconfigure the network, trace any process — or you are an ordinary user who can do almost none of it. There's no middle. That's a disaster for least-privilege. A web server needs exactly one privileged thing: to bind port 80. Under the old model, to get that, you had to run it as full root — and now a bug in your web server is a bug that can reboot the host.

Capabilities fix this by shattering "the power of root" into around forty independent privileges, each guarding one category of operation. Binding a low port is CAP_NET_BIND_SERVICE. Loading a kernel module is CAP_SYS_MODULE. Overriding file permissions is CAP_DAC_OVERRIDE. The kernel's privileged checks no longer ask "is this uid 0?" — they ask "does this process hold the specific capability for this action?" Now you can give a process exactly the powers it needs and withhold the rest. Docker uses this to defang container-root.

Mechanism 1

A capability gates one class of operation

Step 1 · Explain

Every operation that used to require "being root" is now tied to a named capability. The kernel checks the process's capability, not its uid. A few that matter, to make it concrete: CAP_CHOWN lets you change a file's owner; CAP_DAC_OVERRIDE lets you bypass all file read/write/execute permission checks; CAP_NET_BIND_SERVICE lets you bind ports below 1024; CAP_KILL lets you signal processes you don't own. And the dangerous ones: CAP_SYS_ADMIN is a sprawling grab-bag (mounting filesystems and much more — so broad it's nicknamed "the new root"); CAP_SYS_MODULE loads kernel code and is game-over for the host; CAP_SYS_PTRACE inspects and manipulates other processes; CAP_SYS_BOOT reboots the machine.

How many are there? The count grows with the kernel — it's whatever CAP_LAST_CAP is on your system, currently around 40. The exact number matters less than the model: privileges are itemized, and you grant them individually.
Mechanism 2

Docker's default: keep 14, drop the rest

Step 1 · Explain

When Docker runs a container, it does not hand it the full set of capabilities even though the process is uid 0. It grants a fixed, curated list of 14 — the ones ordinary software legitimately needs — and drops everything else. This single list is the practical meaning of "container root is safer than real root."

Step 2 · The source

✓ Kept (the 14) — everyday needs

files: CHOWN, DAC_OVERRIDE, FOWNER, FSETID
identity: SETUID, SETGID, SETPCAP, SETFCAP
network: NET_BIND_SERVICE, NET_RAW
misc: MKNOD, SYS_CHROOT, KILL, AUDIT_WRITE

✗ Dropped — the dangerous powers

SYS_ADMIN — mount, "the new root"
SYS_MODULE — load kernel code
SYS_PTRACE — inspect other processes
NET_ADMIN — reconfigure networking
SYS_TIME — set the system clock
SYS_BOOT — reboot  ·  …and ~20 more
The part that does the job

These 14 let normal programs work: change ownership of their files, drop privileges (SETUID/SETGID), bind port 80 (NET_BIND_SERVICE), chroot, kill their children. What's absent is the point: no SYS_ADMIN, no SYS_MODULE, no NET_ADMIN, no SYS_TIME, no SYS_BOOT. So container-root can't mount arbitrary filesystems, load a rootkit module, rewrite the host firewall, change the clock, or reboot the box — even though it's uid 0. You adjust the list with --cap-drop (remove more) and --cap-add (grant back a specific one); --privileged grants them all and is the big red button that undoes this entire lesson.

The one debated inclusion. CAP_NET_RAW is in the default set so tools like ping work — but it also permits crafting raw packets and ARP spoofing on the container's network. Many hardened setups drop it explicitly (--cap-drop NET_RAW). It's a deliberate convenience-vs-safety trade the maintainers chose, and worth knowing you can reverse.
Mechanism 3

Not one list but five sets

Step 1 · Explain

A process doesn't carry a single "capabilities" value — it carries five sets. Five sounds like a lot, so start with the one fact that makes them all fall into place:

When the kernel checks a permission, it looks at exactly one set — effective. The other four sets exist only to control what is allowed to get into effective — now, and after you run a new program.

So don't try to hold five things in your head. Hold one — effective is the live set the kernel reads — and treat the rest as the plumbing around it. Here's a toolbox analogy that maps cleanly onto all five.

Group A — what you can use right now (three sets)

Picture your process as a worker, and each capability as a tool. Three sets describe your tools at this instant:

effective = the tools in your hands. The guard (kernel) only ever checks your hands. Screwdriver in hand → you may turn the screw. This is the only set that decides an action.
permitted = the tools in your toolbox. You may freely move a tool from the box into your hands (permitted → effective) whenever you need it — but you can't hold a tool that isn't in your box.
bounding = the catalog of tools you're ever allowed to own. If a tool isn't in the catalog, it can never enter your toolbox — not even if you visit the supply room (run a setuid-root program). Cross a tool off the catalog and it's gone forever, for you and every process you start.

These three nest: what's in your hands is a subset of what's in your box, which is capped by the catalog.

bounding · the ceiling — a cap outside this can NEVER be held (dropping is irreversible)
permitted · what you're allowed to switch on
effective · what's switched ON this instant  ←  the kernel checks only this
Why split effective from permitted at all? So a careful program can keep a powerful tool in its box but out of its hands until the exact moment it's needed, then put it back. If a bug strikes while the tool is in the box (permitted) but not in hand (effective), the kernel check fails — the power wasn't active. It's defense in depth. (Docker doesn't bother with this subtlety — it puts the same 14 in both — but it's why the two sets exist.)

Group B — what you keep when you start a new program (two sets)

Running a new program with execve() normally wipes your tools — you walk into a new job and hand everything in at the door. Two sets control which tools you carry through that door:

inheritable = the old, awkward mechanism. It only works if the program file you're running also has matching "inheritable" bits stamped on it. On its own it usually does nothing, which is why you'll almost always see it empty.
ambient = the modern fix (Linux 4.3+). Tools in the ambient set are simply kept through the door when you exec an ordinary program — no cooperation from the file needed. This is the set that actually lets a non-root process hold onto a capability across exec.

For a container this pair matters because the container's first process execs your program — so the 14 caps need to survive that exec, which is what ambient guarantees.

Step 2 · The source

The runtime-spec carries all five as separate arrays in config.json, which is how Docker's 14 reach runc:

If you remember one thing

The kernel only checks effective. permitted is the pool effective can draw from; bounding is the irreversible ceiling nothing can exceed; inheritable/ambient decide what carries across running a new program. Docker fills all five with the same 14, so in a container they look identical — but the meaningful one is bounding: because a cap dropped from bounding can never come back for that process or its children, the ~26 capabilities Docker left out are locked out for good, no trick inside the container can reacquire them.

Mechanism 4

How runc installs them

Step 1 · Explain

runc reads the five arrays from config.json and applies them to the container's process just before it starts. Each set uses a different kernel operation — dropping from the bounding set, setting the thread's permitted/effective/inheritable in one call, and raising ambient caps individually — but from your side it's just "these five lists become the process's five sets."

Step 2 · The source
The part that does the job

Five sets in, five sets applied. Apply(CAPS | BOUNDS) writes the thread's permitted/effective/inheritable and drops everything not in the bounding whitelist; SetAmbient raises the ambient ones. By the time your container's process runs its first instruction, its capability sets already reflect Docker's 14 — the powers were removed before your code ever executed.

Where this corrects the familiar version

"Containers drop privileges so root inside is fake" is half-right and half-wrong. The uid really is 0 (Lesson 7), but the powers attached to it are cut to 14 — that's the real safety, and it's a concrete, listable set, not magic. Two consequences: (1) --privileged re-grants all capabilities (bitmask 000001ffffffffff), erasing this wall entirely — it should be rare and deliberate. (2) Even the default 14 aren't nothing: CAP_DAC_OVERRIDE bypasses file permissions and CAP_NET_RAW enables spoofing, so a locked-down container often drops further with --cap-drop ALL and adds back only what it needs. Capabilities are a dial, and the default is a sensible middle, not the safest possible setting.

Where we are

Summary

Capabilities break the all-or-nothing power of root into ~40 named privileges, each gating one class of operation, so the kernel checks "do you hold this capability?" instead of "are you uid 0?". Docker grants a container a fixed set of 14 (DefaultCapabilities()) and drops the rest — notably SYS_ADMIN, SYS_MODULE, NET_ADMIN, SYS_TIME, SYS_BOOT — which is the concrete reason default container-root can't wreck the host. Each process carries five sets — permitted, effective, bounding, inheritable, ambient — with bounding as the irreversible ceiling; the runtime-spec ships all five in config.json and runc applies them before your code runs. Tune with --cap-add/--cap-drop; --privileged restores everything. This is the first of three security primitives that harden the shared-kernel wall; next is seccomp, which restricts not privileged operations but the syscalls a container may make at all.
