COREDEPTH + DIAGRAMS REBUILD

Networking I: from a private netns to real packet flow

Same implementation depth as the deeper Lesson 33, but with a strict first-use rule: every new networking term is defined before the lesson relies on it, and each spatial or packet-flow mechanism gets its own drawn diagram.

Governing idea

dockerd prepares Linux networking objects and rules; the Linux kernel later moves every real packet through those objects. We will not use a networking term until its job is clear.

How to read this rebuild. Each section starts with a drawn diagram. The prose comes underneath it. A gold new words box defines every term that is new to this lesson before the term is reused. Source-level implementation comes after the mechanism is understandable.

1Isolation comes before connectivity

A process can get a private networking world without getting any connection

New words before we continue
network namespace (netns)
A Linux-kernel isolation boundary for networking state. A process uses the interfaces, addresses, routes and sockets belonging to the network namespace it is in.
network stack
The kernel networking state and code used to send, receive, route and deliver network traffic. A netns gives that code a separate set of networking objects; it is not a separate kernel.
interface
A kernel networking device through which traffic enters or leaves a network stack. An interface can be physical, such as a host Ethernet/Wi-Fi device, or virtual, such as a container's eth0.

There is still only one Linux kernel. A process inside a container does not receive a private kernel. Instead, when that process makes a networking syscall, Linux evaluates it using the process's network namespace. That is why a container can see a different set of interfaces and routes from the host even though both are using the same kernel.

A fresh netns answers one question only: which networking world does this process use? It does not automatically create a cable, a virtual interface, a bridge, an IP address, or a route to another namespace. A perfectly valid fresh netns may have only a loopback interface and no path to the host.

Who creates the ordinary Docker private netns? dockerd describes the desired namespace in the OCI runtime specification; runc asks the Linux kernel to create that namespace during task creation.

Who makes it useful afterward? dockerd's networking subsystem, libnetwork, configures connectivity around the runtime-created netns.

OCI Runtime Spec 1.3.0 · Linux namespaces defines create-vs-join semantics. Moby 29.6.2 · daemon/oci_linux.go · WithNamespaces chooses Docker's namespace intent.

2Place Docker's networking subsystem before naming it

Before packets move, place Docker's networking subsystem correctly

New words before we continue
libnetwork
Moby's networking subsystem inside the dockerd process. It is Go code, not a separate daemon, not containerd, not runc, and not kernel code.
Controller
libnetwork's top-level manager for Docker networks and networking drivers.
Network
Docker's logical network object, for example the default bridge network. It is not itself the Linux bridge device.
Endpoint
The logical attachment between one Docker network and one container networking environment.
Sandbox
libnetwork's object representing the networking environment associated with a container. It refers to/configures the real OS networking namespace; it is not the netns itself.
network driver
libnetwork code that knows how to realize a Docker Network using concrete Linux networking mechanisms. Lesson 33 follows the bridge driver.

The most important distinction is configuration time versus packet time. During setup, dockerd calls libnetwork. Libnetwork and its bridge/firewall backends create or configure Linux networking objects and install rules. Later, when an application sends a real packet, the Linux kernel—not dockerd—performs route lookups, moves Ethernet frames, evaluates firewall/NAT rules, rewrites packet headers when required, and transmits the traffic.

Configurer dockerd + libnetwork.

Executor for live packets Linux kernel networking code.

Moby 29.6.2 · daemon/daemon.go · Daemon.netController places the libnetwork controller inside dockerd; daemon/libnetwork/{controller,network,endpoint,sandbox}.go define those logical objects.

3Build the connection topology

Which Linux objects connect the container's private networking world to the host?

New words before we continue
veth pair
Two peer virtual Ethernet interfaces created by Linux. A frame transmitted into one peer appears as received traffic on the other. Putting the peers in different netns creates a virtual link across the namespace boundary.
Linux bridge
A kernel Layer-2 switching device. Docker's legacy/default bridge network normally uses a bridge device named docker0.
bridge port
An interface attached to a Linux bridge. The host-side peer of a container's veth pair becomes a bridge port.
subnet
A range of IP addresses treated as one IP network. In our example 172.17.0.0/16 is the Docker subnet.
/16 prefix
The first 16 bits identify the network portion of the IPv4 address. It tells Linux which destinations are considered directly reachable on that subnet.
gateway
The next IP-speaking machine to which a host sends traffic when the final destination is outside its directly connected subnet. In this example the container uses 172.17.0.1, an IP assigned to docker0.

Assume Docker gives container A 172.17.0.2/16. Inside A's netns, the container-side veth appears as eth0. The other veth peer lives on the host side and is attached to docker0. The bridge itself has 172.17.0.1 in this example, so that host address can act as A's gateway.

The veth and bridge have different jobs. The veth crosses the namespace boundary. The bridge decides which attached Ethernet destination should receive a frame. Neither one is the host's IP router, and neither one performs NAT merely because it exists.

4Start with the easy packet

How one container reaches another on the same Docker network

New words before we continue
IP packet
A unit of Layer-3 traffic containing an IP header, including source and destination IP addresses, plus the higher-level payload.
Ethernet frame
A Layer-2 unit carried on an Ethernet-like link. It wraps the IP packet and has source and destination MAC addresses for the current local link.
MAC address
An address used for Ethernet delivery on the current Layer-2 network. It is different from an IP address: a MAC selects the next local interface/device, while an IP address identifies the packet's network-layer destination.
ARP
Address Resolution Protocol for IPv4. Linux uses it on an Ethernet-like subnet to learn which MAC address corresponds to a local IPv4 address.
Layer 2 (L2)
The Ethernet/link layer. In this lesson, L2 decisions are primarily about MAC addresses and bridge ports.
forwarding database (FDB)
The Linux bridge's MAC-to-port knowledge. It lets the bridge decide which bridge port should receive a frame for a learned destination MAC.

Suppose A is 172.17.0.2 and B is 172.17.0.3, both on 172.17.0.0/16. Linux sees B as directly reachable on A's local subnet, so A does not send the packet to the gateway. If A does not already know B's MAC address, Linux uses ARP to learn it. Linux then creates an Ethernet frame whose destination MAC is B's.

The frame crosses A's veth pair to the host-side peer. Because that peer is a port of docker0, the bridge processes the frame. It looks at the destination MAC, consults its FDB, and forwards the frame out B's host-side veth port. The peer inside B's netns receives it.

A's networking context route lookup + ARP + frame construction.

veth kernel driver frame transfer between peers.

Linux bridge MAC-based selection of B's bridge port.

No host IP forwarding is required here because the IP packet is not being routed between two different IP networks; it stays on the same Docker subnet and is switched at Layer 2.

5Now leave the Docker subnet

How the container decides where to send a packet for 1.1.1.1

New words before we continue
routing table
A set of rules in a network namespace that tells Linux how to reach destination IP ranges.
route lookup
The kernel's act of comparing the packet's destination IP with the routing table to choose how the packet should leave that networking context.
directly connected route
A route saying that a destination subnet is reachable directly through an interface, without first sending the packet to a router.
default route
The fallback route used when no more-specific route matches the destination. A line such as default via 172.17.0.1 dev eth0 says to use 172.17.0.1 as the next IP hop and eth0 as the interface.
next hop
The next IP-speaking machine that should receive this packet on its journey. It is not necessarily the final IP destination.

Now A wants to reach 1.1.1.1. A's network namespace has routes similar to:

inside A's netns
172.17.0.0/16 dev eth0
default via 172.17.0.1 dev eth0

The first route covers destinations in 172.17.x.x. 1.1.1.1 is not there, so Linux chooses the default route. That route says: send the packet to next hop 172.17.0.1 through eth0.

This does not replace the IP destination. The IP header still says:

IP packet source IP 172.17.0.2 destination IP 1.1.1.1 Ethernet frame used for this local hop source MAC container eth0 MAC destination MAC gateway/docker0 MAC

Why two different destinations? The IP destination answers where the packet ultimately needs to go. The Ethernet destination answers which device on this local link should receive the frame next. Because the next hop is 172.17.0.1, Linux uses ARP to learn the MAC corresponding to 172.17.0.1, then addresses the local Ethernet frame to that MAC.

Who performs the route lookup and ARP? The Linux kernel, using A's network namespace.

What stays unchanged? The packet's destination IP remains 1.1.1.1.

Linux 6.18 · net/ipv4/arp.c · arp_process() is part of the IPv4 ARP receive/update path.

6The gateway frame reaches the host

How the frame that targeted the gateway enters the host's own IP processing

New words before we continue
local delivery
Delivery to the current host itself rather than forwarding the frame out another bridge port.
host network stack
The same Linux kernel networking code, now operating in the host network namespace with the host's interfaces, addresses and routes.

The frame has crossed the veth and arrived at the bridge. Its destination MAC is the MAC for the host-side gateway. Therefore this is different from A → B. The bridge is not being asked to find another container's bridge port; the frame is addressed to the host.

The Linux bridge therefore passes the received data upward from Layer-2 bridge processing into the host's own network stack. Once this happens, the host IP code can inspect the IP packet inside the frame. That packet still says src=172.17.0.2, dst=1.1.1.1.

Source-level anchor

Linux 6.18 net/bridge/br_input.c · br_pass_frame_up() is the bridge local-delivery function used when the bridge determines that a frame is for the local host. Here, “up” means from bridge/link-layer handling into the host's higher network-stack receive path.

7The host now has to route

What the host does when it receives an IP packet that is not for the host itself

New words before we continue
router
A system that receives an IP packet from one network and forwards it toward another network according to an IP routing decision.
IP forwarding
Linux's router behavior for packets that arrive at the host but are not addressed to the host itself: route them onward instead of treating them as local traffic only.
output interface
The host interface chosen by the host's route lookup to transmit the packet toward its next hop. It might be Ethernet, Wi-Fi, a VPN interface, or something else; there is no special Docker interface called an “uplink.”
sysctl
A Linux mechanism for reading/changing kernel runtime settings. The IPv4 forwarding setting is exposed as net.ipv4.ip_forward and through /proc/sys/net/ipv4/ip_forward.

The host has received an IP packet whose destination is 1.1.1.1. That address is not one of the host's local addresses. Linux must therefore decide whether it may act as a router. If IPv4 forwarding is disabled, the host does not forward ordinary received IPv4 traffic between interfaces. If it is enabled, Linux performs a second route lookup, this time using the host network namespace's routing table.

That host route lookup chooses an output interface and, where needed, a next-hop router. For example, if the host normally reaches the Internet through Wi-Fi, the selected output interface might be wlan0; on another machine it might be enp3s0. The name is not important—the route lookup chooses it.

Who enables/checks the prerequisite? During bridge-network setup, dockerd/libnetwork checks or configures the kernel's forwarding setting according to Docker configuration.

Who forwards each real packet? The host Linux IP stack.

Linux 6.18 documents ip_forward as forwarding packets between interfaces, with 0 disabled and 1 enabled. Moby 29.6.2 checks/configures this through daemon/libnetwork/drivers/bridge/setup_ip_forwarding.go.

8Define packet-rule machinery before address rewriting

Where Docker's packet rules live, and who executes them

New words before we continue
netfilter
A Linux-kernel framework that exposes packet-processing points in the networking path. Kernel networking code can run registered filtering/NAT logic when a packet reaches those points.
hook
One of those packet-processing points. Think “a defined place in the kernel packet path where configured logic can examine this packet.”
rule
A stored instruction with a condition and an action. Example: if a packet matches these addresses/ports, perform this NAT rewrite.
match
The condition part of a rule: packet properties that must be true for the action to run.
action
What the rule tells the kernel to do when the match succeeds—for example accept, drop, or rewrite an address.
firewall
Packet policy that allows, rejects or otherwise controls traffic. Docker uses firewall rules both for access control and to support its networking behavior.
NAT
Network Address Translation: kernel logic that rewrites address and sometimes port fields in packet headers while maintaining enough state for the traffic flow to remain coherent.
iptables / nftables
Linux rule-programming mechanisms. Moby has firewall backends that use them to install Docker networking policy into the kernel. They are not processes through which every packet must travel.

At setup time, dockerd/libnetwork decides which networking rules are needed and programs them through its selected firewall backend. At packet time, dockerd is not on the packet path. The Linux kernel reaches the relevant netfilter hook, compares the packet against the stored rules, and executes the matching action.

Setup-time actor dockerd/libnetwork + iptables or nftables backend.

Packet-time actor Linux kernel netfilter/NAT code.

Mental-model correction

Do not imagine packet → dockerd → packet. Docker prepares kernel state. The kernel handles the live traffic later.

9Fix the outbound reply path

Why the host changes the source address before sending the packet outward

New words before we continue
SNAT
Source Network Address Translation. It changes the packet's source address (and, when necessary, source port).
MASQUERADE
A Linux source-NAT action useful when the translated source should be taken from the route's chosen outgoing interface. It is a particular form of source NAT, not a separate packet-transport mechanism.
conntrack
Linux connection tracking: kernel state that records traffic-flow relationships. NAT uses this state so later packets and reply-direction packets receive the translation that belongs to the same flow.
NAT mapping / binding
The remembered relationship between the original packet identity and its translated identity, for example container source address/port ↔ host translated address/port.

Forwarding solved one problem: it allowed the host to route the packet outward. It did not solve the reply-path problem. If the packet left unchanged as src=172.17.0.2, dst=1.1.1.1, the remote server would reply to 172.17.0.2. The surrounding network normally has no route saying “the Docker-internal 172.17.0.0/16 network is behind this host,” so the reply would not naturally find the container.

Docker's normal bridge NAT mode therefore installs a source-NAT rule. When the outbound packet reaches the relevant netfilter/NAT point, the Linux kernel rewrites the source from the container address to an address belonging to the output interface selected by the host route.

before MASQUERADE src 172.17.0.2:container-port dst 1.1.1.1:server-port after MASQUERADE src HOST_OUTPUT_ADDRESS:translated-port dst 1.1.1.1:server-port

The remote server now replies to the host-visible translated source. Conntrack/NAT state remembers which container flow that translated address/port represents. When the reply comes back, the kernel applies the corresponding reverse-direction translation and routes the packet back toward 172.17.0.2.

Who installs the policy? dockerd/libnetwork bridge firewall setup.

Who rewrites the packet? Linux netfilter/NAT code.

What field changes? The source address, and possibly the source port.

Source-level anchor

Linux 6.18 net/netfilter/nf_nat_masquerade.c · nf_nat_masquerade_ipv4() selects the new source for IPv4 masquerading and passes the translated source range to the generic NAT setup path via nf_nat_setup_info(..., NF_NAT_MANIP_SRC). The important meaning of NF_NAT_MANIP_SRC is simply “this NAT operation manipulates the packet source.”

10Publish a host port to the container

What -p 18080:80 changes in an incoming client packet

New words before we continue
port
A transport-layer number used with an IP address and protocol to identify a socket endpoint. In this example nginx listens on TCP port 80 inside the container.
published port
A Docker mapping that makes traffic addressed to a host IP/port reach a container IP/port. -p 18080:80 publishes host port 18080 to container port 80.
DNAT
Destination Network Address Translation. It changes the packet's destination address and/or destination port.
TCP stack
The kernel's TCP implementation. After a packet reaches the container's IP address and TCP port, the container networking context's TCP stack finds the matching listening socket and delivers the received data to the process.
userland proxy
A normal userspace process that accepts traffic on one side and opens/forwards it to another address. Docker's docker-proxy can be used for specific mappings where the firewall/NAT path is not sufficient; it is not the definition of ordinary -p.

Assume nginx listens inside the container at 172.17.0.2:80, and the Docker host has some host address HOST_IP. A client connects to HOST_IP:18080. During networking setup, libnetwork's bridge firewall backend has already installed a rule describing the published-port translation.

When the client packet arrives later, the host Linux kernel matches that rule and performs DNAT:

before DNAT destination HOST_IP:18080 after DNAT destination 172.17.0.2:80

DNAT has only changed the destination fields. It has not physically moved the packet to the container. Now the host performs a route lookup for the new destination 172.17.0.2. That route points toward the Docker bridge network. Docker's forwarding policy must allow the published-port traffic. The host emits the packet toward docker0; the bridge chooses the container's host-side veth port; the peer inside the container receives the frame; and the container TCP stack finally delivers the traffic to nginx's listening socket on port 80.

Conntrack/NAT state also handles the reply direction so the client continues to observe a conversation with HOST_IP:18080, even though nginx is actually speaking from 172.17.0.2:80.

Who installs the mapping rule? dockerd/libnetwork's bridge firewall backend.

Who executes DNAT? Linux netfilter/NAT code when a matching real packet arrives.

What changes? Destination IP/port.

Who delivers after the rewrite? Normal host routing, Linux bridge switching, the veth pair, then the container TCP stack.

Moby 29.6.2 · daemon/libnetwork/drivers/bridge/internal/iptabler/port.go · setPerPortNAT() constructs the published-port DNAT path; setPerPortForwarding() installs the separate forwarding permission.

Source-over-folklore correction

docker-proxy is not what -p fundamentally means. Current Moby's ordinary bridge path uses kernel DNAT/forwarding rules. The source explicitly hands certain address-family combinations to docker-proxy instead of installing the normal iptables DNAT path.

11Compare Docker network modes

How the four Docker network modes choose a networking world

New words before we continue
loopback interface
A special local interface, usually named lo, used for traffic that stays inside the same network namespace. Addresses such as 127.0.0.1 are loopback addresses.
shared network namespace
Two containers can be placed in the same netns. They then see the same interfaces, IP addresses, routes, loopback device and port-number space because those objects belong to that one netns.
ModeNamespace choiceWhat follows
bridgeFresh private netnsDocker attaches an endpoint, typically via veth + Linux bridge, then configures addressing/routes/firewall/NAT as needed.
hostHost's existing netnsNo separate container network stack and no normal container veth/bridge path. The process uses host interfaces, host routes and host port-number space.
noneFresh private netnsDocker does not attach a normal network endpoint. The namespace stays isolated except for local/loopback configuration.
container:<id>Another container's existing netnsBoth containers share that same kernel networking world.

The namespace choice explains why two containers using separate bridge netns can both listen on the same container port, while two containers sharing one netns compete for the same address/port combinations.

12Second read: exact runtime order

Who creates the private networking world, and when Docker wires it

New words before we continue
OCI runtime specification
The standardized configuration consumed by an OCI runtime such as runc. Lesson 21 covered the full config.json; here we care specifically about its Linux namespace entries.
namespace path
An optional filesystem path naming an already-existing namespace, for example /proc/<pid>/ns/net. In OCI namespace configuration, an entry with no path requests a new namespace; a supplied path requests joining that existing namespace.
task
containerd's running-container execution object. During creation, the runtime can establish the process environment before the configured application is actually started.
PID
Process ID. Once the created task exists, dockerd can use its PID to refer to kernel objects associated with that process, including /proc/<pid>/ns/net.
CLONE_NEWNET
The Linux clone/unshare namespace flag for creating a new network namespace. runc maps the OCI network-namespace request to this kernel namespace type.

For ordinary private networking, Moby's daemon/oci_linux.go · WithNamespaces puts a network-namespace entry into the OCI spec with no path. Under OCI Runtime Spec 1.3.0 semantics, that means the runtime must create a new network namespace. For --network=container:<id>, Moby supplies a path to the existing namespace. For host networking, Moby removes the network-namespace entry so the process remains in the runtime/host network namespace.

The startup ordering matters because dockerd must configure the runtime-created namespace before the application begins sending traffic. Moby's flow establishes a created task, then calls initializeCreatedTask, then starts the task.

1
dockerd builds OCI namespace intent
Normal bridge: network namespace requested, no existing path.
2
containerd/runc create the task context
runc asks Linux for the requested fresh network namespace.
3
dockerd has a created task and PID
The execution context exists, but the configured application has not yet been started.
4
initializeCreatedTask wires networking
dockerd/libnetwork realizes/configures the endpoint using the task's network namespace.
5
Task.Start
Only after created-task initialization succeeds does the configured container application run.

Who creates the ordinary private netns? runc asks the Linux kernel to create it, based on the OCI request constructed by dockerd.

Who wires bridge connectivity? dockerd/libnetwork after task creation and before application start.

Moby 29.6.2 · daemon/start_linux.go · initializeCreatedTask() describes initialization needed for a freshly created task before start. runc 1.3.6 maps the network namespace to CLONE_NEWNET.

13Second read: current virtual-link placement

How current Moby places the two ends of the virtual link

New words before we continue
netlink
A Linux kernel/userspace communication family used to query and configure networking objects such as links, addresses and routes. Moby uses Go netlink libraries rather than issuing shell ip commands.
PeerNamespace
A netlink veth-creation setting used by current Moby to request that the peer end of a new veth pair be created directly in a specified network namespace.
fallback path
An alternate implementation path used when the preferred direct placement cannot be used. The important invariant is the final topology, not that one exact creation sequence must always occur.

A common explanation says Docker must first create both veth ends in the host netns and then move one into the container. That sequence can happen, but current Moby 29.6.2 does not require it. The bridge driver can open the target container namespace and set the veth peer's namespace during creation so the peer is born directly inside the target netns. Moby also retains a move/configure-later fallback.

Source-over-folklore correction

The invariant is final placement: one peer participates in the host bridge topology and the other peer appears in the container netns. “Both must first exist on the host” is not a kernel requirement and is not the only current Moby path.

Moby 29.6.2 · daemon/libnetwork/drivers/bridge/bridge_linux.go · veth creation / PeerNamespace path.

14Inspect it yourself

Observe the exact objects and rules from the diagrams

Command words used below
nsenter
A userspace tool that runs a command in selected namespaces of another process. -n selects its network namespace.
ip
The iproute2 command used to inspect/configure Linux links, addresses and routes.
bridge
The iproute2 bridge command for inspecting Linux bridge ports and related bridge state.
conntrack
A userspace inspection tool for the kernel's connection-tracking table, when installed.
create one bridge-networked container
docker run -d --name net33 -p 18080:80 nginx:alpine
PID=$(docker inspect -f '{{.State.Pid}}' net33)
1 · compare host and container network namespaces
readlink /proc/$$/ns/net
readlink /proc/$PID/ns/net
sudo nsenter -t "$PID" -n ip addr
sudo nsenter -t "$PID" -n ip route

Inside the container route table, identify the directly connected Docker subnet and the default via ... line. That line is the concrete gateway decision described in section 5.

2 · inspect veth peers and the bridge
ip link show type veth
ip -br addr show docker0
bridge link
3 · inspect the forwarding prerequisite
sysctl net.ipv4.ip_forward
4 · inspect Docker NAT rules
# iptables backend
sudo iptables -t nat -S 2>/dev/null | grep -E 'DOCKER|MASQUERADE|SNAT|DNAT' || true

# nftables backend
sudo nft list ruleset 2>/dev/null | grep -E -i 'docker|masquerade|snat|dnat' || true

Read each matching rule as: what packet fields are matched, and what action will the kernel perform if the match succeeds?

5 · exercise outbound and published-port paths
docker exec net33 sh -c 'wget -qO- https://example.com >/dev/null && echo outbound-ok'
curl -I http://127.0.0.1:18080

# optional, if conntrack is installed
sudo conntrack -L

Check yourself — every term must have an actor and a job

  • network namespace: selects which networking state a process uses; it does not itself create connectivity.
  • libnetwork: networking configuration code inside dockerd.
  • veth: transfers Ethernet frames between two peer virtual interfaces, often across netns boundaries.
  • Linux bridge / docker0: switches Ethernet frames by MAC/bridge-port decisions; it is distinct from host IP routing.
  • gateway: the next IP hop used when the final destination is outside the local subnet.
  • ARP: resolves a local IPv4 next-hop address to a MAC address.
  • IP forwarding: host-kernel router behavior for a packet received from one network and routed onward toward another.
  • netfilter: kernel packet-processing framework; Docker programs rules, the kernel executes them.
  • SNAT/MASQUERADE: source rewrite that makes the outbound return path come back through the host.
  • conntrack: kernel state that lets NAT remain consistent across later/reply packets of the same flow.
  • DNAT: destination rewrite used by ordinary published-port mappings before normal routing/bridge/veth delivery.
  • runc: creates the ordinary requested private netns; dockerd/libnetwork wires it before Task.Start.
