Part 5 · Runtime concerns · Lesson 37 of 46

Healthchecks, restart policies, resource limits, non-root

CORE

Four runtime controls, one execution pipeline. We will follow health results, exit events, resource numbers, and UID/GID values from the Docker CLI through the responsible components until each reaches the place where it actually matters.

governing idea

These features do four different jobs. A healthcheck observes a running container. A restart policy reacts to the main task exiting. Resource limits become kernel cgroup policy. A non-root setting becomes process credentials. Understanding them means following the correct object to its final owner.

pinned source baseline

Docker Engine / Docker CLI 29.6.2 · containerd 2.2.6 · runc 1.3.6 · OCI runtime-spec 1.3.0 · OCI image-spec 1.1.1 · Linux 6.18. runc 1.3.6 pins opencontainers/cgroups v0.0.4, so that dependency is the authoritative cgroup-v2 writer used below.

The four controls share the start pipeline, then terminate in different owners: health state in dockerd, restart decisions in dockerd, resource enforcement in the Linux kernel, and process credentials in the Linux kernel.
first define the four nouns

1. What each control actually controls

Healthcheck. A command periodically executed inside an already running container to produce an exit code and diagnostic output. Docker turns repeated results into a health status: starting, healthy, or unhealthy.

Restart policy. Rules stored by dockerd telling it whether to create and start another task for the same container after the container's main task exits.

Resource limit. A request such as “at most 256 MiB memory” or “average at most 1.5 CPUs.” The request begins as Docker configuration, but the live enforcement mechanism is a Linux cgroup controller.

Non-root. Running the container process with a numeric user ID and group ID other than 0. This changes the process's Linux credentials. It is not, by itself, a user namespace.

do not merge these ideas

An unhealthy container can keep running forever. A healthy container can exit and be restarted. A non-root process can still be resource-limited. A restart recreates the task but preserves the container's configured resource and user settings.

whole start path

2. Before any feature can act, its configuration has to reach the right layer

Consider a deliberately busy command:

docker run -d --name app \
  --health-cmd='test -f /tmp/ready' \
  --health-interval=5s --health-retries=2 \
  --restart=on-failure:3 \
  --memory=256m --memory-reservation=128m \
  --cpus=1.5 --cpu-shares=1024 --pids-limit=64 \
  --user=10001:10001 \
  alpine sh -c 'sleep infinity'

The flags look like one command, but they split into different data structures inside dockerd:

inputwhere dockerd keeps itwhere it must finally matter
health flagscontainer Config.Healthcheckdockerd health monitor + probe execs
--restartHostConfig.RestartPolicydockerd restart manager after task exit
CPU / memory / PIDsHostConfig.ResourcesOCI resource fields → runc → cgroup-v2 files → kernel controllers
--usercontainer Config.Usernumeric OCI process.user → runc → Linux credentials
1

Docker CLI sends configuration

The Docker CLI parses the flags and sends container-create configuration to dockerd. The CLI is not the long-term monitor and does not enforce the limits.

2

dockerd stores Docker-level policy

The health configuration, restart policy, resource request, and user string become persistent container configuration. This matters because a restart creates a new task from the same container configuration.

3

dockerd builds the OCI runtime spec

At start, daemon.createSpec applies WithResources and WithUser. Resource numbers move into OCI linux.resources; the user string is resolved against the container root filesystem's user/group databases and becomes numeric OCI process.user.

4

containerd and the shim carry the task request

dockerd replaces/creates the containerd container record, creates a task, then starts it. containerd's runtime-v2 path forwards task creation and start to the shim. This is the same task pipeline established in Lesson 23; here we care about the additional resource and credential fields riding through it.

5

runc converts configuration into Linux state

runc converts the OCI resource structure into its cgroup configuration, configures the cgroup, and sets the process credentials. Once the process is alive, the kernel—not dockerd—is scheduling CPU, charging memory, enforcing the PID ceiling, and checking process credentials on syscalls.

6

dockerd starts health monitoring only after the task starts

After tsk.Start succeeds and the container state becomes running, dockerd calls initHealthMonitor. The health state begins at starting.

health path

3. A healthcheck is an exec process, not a ping from outside

Suppose the health command is:

test -f /tmp/ready

The object that moves is first an exec request, then an exit code plus bounded output.

1

dockerd's timer expires

The health monitor is a per-container goroutine owned by dockerd. It runs only while the container is running and not paused. There is never more than one health monitor for a container.

2

dockerd builds an exec configuration

For CMD, the command is executed directly. For CMD-SHELL, dockerd prepends the configured shell; on Linux the fallback is /bin/sh -c. The probe is non-privileged, has no stdin, captures stdout/stderr, uses the container working directory, and—critically—uses cntr.Config.User.

3

The exec travels through the existing task

dockerd starts the exec through containerd. containerd sends an exec-process request to the shim for the already-running task. The probe therefore runs inside the container's existing runtime context rather than starting a second container.

4

The probe exits

Exit code 0 means success. In this pinned implementation, every other result is treated as a failure. dockerd keeps at most 4096 bytes of combined probe output and at most five recent health log entries.

5

dockerd updates health state

A success resets the failing streak to zero and sets healthy. A counted failure increments the streak. When the streak reaches Retries, the status becomes unhealthy. State transitions emit health-status events.

primary-source checkpoint · Docker Engine 29.6.2 · daemon/health.go

The probe path explicitly sets execConfig.User = cntr.Config.User. The same file defines the health result buffer limit, log-entry limit, default timings, failure streak, and state transitions.

The defaults are implementation behavior

health fielddefault in the pinned Engine sourcemeaning
interval30 snormal delay between probe runs, and initial delay when no start period applies
timeout30 smaximum configured probe runtime after the exec has started
retries3consecutive counted failures before unhealthy
start period0window in which failures are not counted while status is still starting
start interval5 sprobe cadence during the start period while still starting
source-over-folklore correction

start-period is not a period with no healthchecks. Probes can run during it. While health state is still starting, failures inside that period do not increment the failing streak. A success immediately makes the container healthy.

The health timeout has a subtle boundary

dockerd gives the exec-start operation its own hard 30-second startup timeout. The configured health Timeout starts only after the probe exec reports that it has actually started. That prevents slow dockerd/containerd exec setup time from being charged as probe runtime.

Source anchor: Docker Engine 29.6.2 · daemon/health.go::cmdProbe.run, handleProbeResult, monitor, initHealthMonitor.

separate state machines

4. unhealthy does not mean restart

This relationship is load-bearing. A health failure is the exit of an exec process. Restart policy is evaluated for the exit of the container's main task.

health probe exits 1
        ↓
dockerd health monitor
        ↓
failing streak increases
        ↓
State.Health = unhealthy
        ↓
container main task is still running
        ↓
NO restart-policy decision yet

main task later exits
        ↓
container exit path
        ↓
restart policy is evaluated

This is why an application can remain unhealthy indefinitely under --restart=always if its main process never exits. The policy name says what to do after exit, not what to do after health failure.

source-over-folklore correction

Docker Engine does not contain a “restart when health becomes unhealthy” transition in the health path. The health code records state and events. The restart decision lives in the container-exit path.

restart path

5. What actually moves when a container restarts

The moving object is an exit event/status on the way up, then a new task start request on the way back down.

1

The main process exits in the kernel

PID 1 for the container terminates with an exit status. The shim/containerd task machinery observes that task exit and makes the exit information available upstream.

2

dockerd enters handleContainerExit

dockerd stops healthchecks for the old task, deletes the stopped task from containerd, records the exit code/time, and asks the container's restart manager whether another task should be started.

3

The restart manager evaluates four inputs

The decision uses the stored restart policy, exit code, whether the container was manually stopped, and how long the just-finished execution ran. The runtime duration affects backoff; it is not a separate “policy activation” test.

4

If restart is selected, dockerd waits

The restart manager starts with a 100 ms delay, doubles repeated-failure delays, and caps the delay at one minute. A run lasting at least 10 seconds resets that backoff so the next restart begins again at the default delay.

5

dockerd starts a new task for the same container

The container object and container ID remain. dockerd calls the start pipeline again without resetting the restart manager. containerd creates a new task, the shim/runc path starts a new main process, and the health state is reinitialized to starting.

the 10-second rule, corrected

A process that crashes after one second can still be restarted immediately by policy. The 10-second check in the pinned source resets the exponential backoff after a sufficiently long run. It is not a requirement that a container first survive ten seconds before restart policies “turn on.”

primary-source checkpoint · Docker Engine 29.6.2 · restartmanager.go

The source resets the delay when executionDuration.Seconds() >= 10; it then separately evaluates always, unless-stopped, and on-failure.

6. The four restart policies, precisely

policyafter main task exitsmanual-stop / daemon-restart consequence
nonever automatically restartstays stopped
on-failure[:N]restart only when exit code is nonzero; optional N limits retry count; zero count means no maximumdecision still depends on recorded exit state/retry budget when dockerd restores container state
alwaysrestart after exit regardless of exit codean explicit stop cancels the current restart loop, but on a later daemon restore always does not consult the manual-stop flag
unless-stoppedrestart after exit unless the container has been marked manually stoppedmanual-stop state suppresses automatic start across daemon restore

Why docker stop can stop an always container

Before sending the stop signal, dockerd calls ExitOnNext(). That cancels the current restart manager. It also persists HasBeenManuallyStopped = true when the daemon itself is not shutting down. So always does not immediately fight your explicit stop.

On an explicit later docker start, dockerd resets the restart manager and clears the manual-stop flag. On daemon restoration, the stored policy is evaluated again. This is where always and unless-stopped differ: unless-stopped checks the manual-stop flag; always does not.

resource path

7. Resource limits become kernel cgroup files

Resource limits are easier when you stop thinking of the Docker flags as the final mechanism. The flags are merely the first representation of the numbers.

Docker CLI flag
    ↓
HostConfig.Resources       (dockerd metadata)
    ↓
OCI linux.resources        (runtime handoff representation)
    ↓
runc cgroup.Resources      (runtime's internal representation)
    ↓
cgroup-v2 interface files  (/sys/fs/cgroup/...)
    ↓
Linux scheduler / memory / pids controllers enforce policy

At container start, dockerd's WithResources takes HostConfig.Resources and fills OCI Linux.Resources.Memory, CPU, and Pids. runc's CreateCgroupConfig copies those values into the cgroup library's structure. Because runc 1.3.6 pins opencontainers/cgroups v0.0.4, that library is where the cgroup-v2 file writes in this lesson actually happen.

source-boundary correction

Older explanations may point to old in-tree runc cgroup-v2 files. In runc 1.3.6, cgroup handling is delegated to the separately versioned opencontainers/cgroups v0.0.4 dependency pinned in runc's go.mod. The lesson follows that current pinned boundary.

8. Memory: hard ceiling, reclaim protection, and swap conversion are three different things

--memory=256m → memory.max

dockerd places the byte count in OCI memory.limit. runc carries it into the cgroup resource structure. The cgroup-v2 writer writes the number to memory.max.

memory.max is the kernel's hard memory-usage limit. If the group reaches it and memory cannot be reclaimed sufficiently, the kernel invokes cgroup OOM handling. That enforcement occurs on memory charge/reclaim paths in the kernel; dockerd is not watching RSS and killing the process itself.

--memory-reservation=128m → memory.low

The Docker API and OCI field use the historical word reservation or “soft limit.” On the pinned cgroup-v2 implementation, however, runc's cgroup dependency writes that value to memory.low.

The Linux 6.18 kernel documentation defines memory.low as best-effort reclaim protection. Below the effective low boundary, a cgroup is protected from reclaim while unprotected reclaimable memory exists elsewhere. Above it, reclaim pressure increases with overage.

source-over-folklore correction

On this pinned cgroup-v2 path, --memory-reservation is not a soft maximum and does not map to the kernel's throttling boundary memory.high. The implementation writes memory.low. memory.max is the hard ceiling.

--memory-swap crosses a semantic translation

OCI runtime-spec 1.3.0 defines its memory swap field in the older combined sense: memory + swap. cgroup v2's memory.swap.max limits swap alone. The cgroup library therefore converts between the two.

For example, with:

--memory=256m --memory-swap=384m

the combined limit is 384 MiB while memory itself is limited to 256 MiB, so the cgroup-v2 swap-only allowance is 128 MiB. If combined memory+swap is configured equal to the memory limit, the cgroup-v2 writer uses memory.swap.max = 0, disabling swap for that cgroup.

primary-source checkpoint · opencontainers/cgroups v0.0.4

fs2/memory.go writes memory.max, memory.low, and memory.swap.max. utils.go::ConvertMemorySwapToCgroupV2Value subtracts memory from combined memory+swap where required.

9. CPU: a quota and a weight solve different problems

--cpus=1.5 is a bandwidth ceiling

The Docker CLI/API representation uses NanoCPUs. For 1.5 CPUs the value is 1.5 billion nano-CPUs. In the pinned dockerd source, getCPUResources uses a 100,000 μs period and computes:

quota = NanoCPUs × period / 1,000,000,000
      = 1,500,000,000 × 100,000 / 1,000,000,000
      = 150,000 μs

runc's cgroup-v2 path therefore writes:

cpu.max = 150000 100000

This means the cgroup may consume up to 150,000 μs of CPU time per 100,000 μs period. On a multi-CPU host that is an average bandwidth of 1.5 CPUs; threads can execute concurrently and then be throttled when the cgroup exhausts its quota for the period.

--cpu-shares=1024 is competition weight

CPU shares are not a CPU ceiling. dockerd puts the shares value into OCI cpu.shares. runc converts that cgroup-v1-shaped number to a cgroup-v2 CpuWeight. The cgroup writer writes cpu.weight.

Linux defines cpu.weight as proportional distribution among active competing children. The default cgroup-v2 weight is 100; the conversion function is deliberately shaped so Docker's historical default share value 1024 maps to that default weight.

source-over-folklore correction

--cpu-shares does not guarantee or cap a percentage of a CPU. If peers are idle, a cgroup can use available CPU. The weight matters when eligible cgroups compete for CPU time. Use quota (--cpus / cpu.max) when you mean a maximum bandwidth.

--pids-limit=64 → pids.max

The Docker PID limit becomes OCI pids.limit, then runc's cgroup PidsLimit, then pids.max. Linux documents this as a hard task-count ceiling. The kernel's PID controller counts kernel tasks/TIDs, not merely the number of process leaders you might casually call “processes.” If fork() or clone() would violate the policy, the kernel returns -EAGAIN.

Source anchors: Docker Engine 29.6.2 · daemon/daemon_unix.go::getCPUResources, getPidsLimit; runc 1.3.6 · libcontainer/specconv/spec_linux.go::CreateCgroupConfig; opencontainers/cgroups v0.0.4 · fs2/cpu.go, fs2/pids.go, utils.go::ConvertCPUSharesToCgroupV2Value; Linux 6.18 · Documentation/admin-guide/cgroup-v2.rst.

10. A running container's resource limits can move again

Creation is not the only path. docker update can change supported resource limits on a running container.

docker update
    ↓
dockerd updates + checkpoints HostConfig
    ↓
containerd task Update(resources)
    ↓
shim task Update
    ↓
runtime cgroup update
    ↓
existing process remains alive under changed kernel policy

The important distinction is that this is an update path, not a restart. dockerd persists the new configuration and, if the task is running, sends updated resource data to the existing task. If the container is stopped, changing HostConfig is enough; the resources are applied next time it starts.

A restart later reconstructs the new task from the now-updated stored configuration, so the changed limits persist across that restart.

Source anchors: Docker Engine 29.6.2 · daemon/update.go::ContainerUpdate/update; containerd 2.2.6 · client/task.go::Update, core/runtime/v2/shim.go::Update.

credential path

11. Non-root: follow a user name until it becomes numbers in a kernel credential

Imagine an image contains:

USER app

or you override it:

docker run --user 10001:10001 image

The string app or 10001:10001 is not what runc finally receives. OCI runtime-spec requires numeric UID/GID fields for POSIX process users and explicitly leaves symbolic name resolution to an upper layer.

1

The image or CLI provides a user expression

Image USER is a default. Runtime --user can override it. dockerd keeps the selected value in Config.User.

2

dockerd resolves names inside the container root filesystem

getUser locates the container's passwd/group files and resolves the requested user. It produces numeric UID, primary GID, and supplementary groups. That result becomes OCI process.user.

3

runc applies the numeric credentials

During container initialization, runc sets supplementary groups where allowed, then calls setgid and setuid for the configured GID/UID. The process that finally executes the application therefore enters user space with those credentials.

4

The Linux kernel enforces those credentials on every relevant operation

File access, signaling, binding privileged ports, and other permission checks use the process credentials together with capabilities, namespace mappings, filesystem ownership/mode, and other security mechanisms. “Non-root” is one input to that authorization picture, not a replacement for all of it.

primary-source checkpoint · runc 1.3.6 · libcontainer/init_linux.go

The user-setup path performs unix.Setgid(config.GID) and then unix.Setuid(config.UID) after supplementary-group handling.

Non-root is not a user namespace

dockerd's OCI building code has a separate path for user namespaces. A user namespace is added only when the container is configured for private user-namespace mapping and the daemon has UID/GID mappings. Merely setting USER app or --user 10001 does not create that namespace.

source-over-folklore correction

Without user-namespace remapping/rootless machinery, running as UID 10001 means the process uses that numeric UID in the host's user namespace as well. It is still safer than UID 0 for many permission checks, but it is not UID translation. Revisit Lesson 7 for user namespaces and Lesson 11 for capabilities.

Source anchors: OCI runtime-spec 1.3.0 · config.md::process.user; Docker Engine 29.6.2 · daemon/oci_linux.go::getUser, WithUser, WithNamespaces; runc 1.3.6 · libcontainer/init_linux.go::setupUser.

12. The four mechanisms interact, but ownership still stays separate

A healthcheck inherits the configured user

The health probe is created with cntr.Config.User. So an image that works only when its probe runs as root can become unhealthy after you correctly move the application to non-root. That is not Docker arbitrarily changing health semantics; the probe is executing under the configured container user.

A healthcheck also consumes the container's resources

The probe is an exec process in the container's existing task context. Its CPU time, memory, and task count are not magically outside the container's runtime constraints. Very tight CPU/PID/memory limits can therefore affect the probe just as they affect the application.

A restart creates a new task under the same stored policy

When dockerd restarts a container, it rebuilds/starts the task from the same container configuration. The resource settings and selected user are applied again to the new task. The health state is reset to starting because the new main process must be evaluated afresh.

OCI standardizes some fields, not Docker's lifecycle policy

OCI runtime-spec defines numeric process.user and Linux resource fields. Docker's health monitor and restart manager are Engine behavior. OCI image-spec 1.1.1 reserves fields such as Healthcheck, Memory, MemorySwap, and CpuShares for compatibility; it does not define Docker's health state machine or restart policy.

boundary rule

Do not search runc for “restart policy” or Linux cgroup code for “healthy/unhealthy.” Those concepts terminate earlier in the pipeline. Conversely, do not expect dockerd to be the component enforcing every CPU scheduling decision once cpu.max is installed.

14. Check yourself

  • A healthcheck is an exec command launched and interpreted by dockerd; its result changes health state, not restart policy directly.
  • Restart policy is evaluated when the container's main task exits. A restart creates a new task/main process for the same container object.
  • The 10-second test resets exponential restart backoff; it is not a minimum survival period required for restart policies to work.
  • --memory ends at memory.max; --memory-reservation ends at memory.low, which is reclaim protection rather than a soft ceiling.
  • --cpus ends at CPU bandwidth quota in cpu.max; --cpu-shares becomes relative cpu.weight.
  • --pids-limit ends at pids.max; the kernel rejects violating fork()/clone() with EAGAIN.
  • USER/--user becomes numeric OCI process.user and then Linux process credentials. It does not itself create a user namespace.
  • Once cgroup files and process credentials are installed, the Linux kernel is the enforcement point. dockerd remains responsible for health state and restart decisions.
