Volumes, bind mounts & tmpfs

One container path can point to four different storage places. Once that relationship is clear, the three Docker mount types stop looking like unrelated features.

The governing idea

Mounting at /data changes what storage the path /data refers to.

How to read this lesson: do not begin by memorizing “volume, bind, tmpfs.” First follow one path—/data. We will ask the same question every time: what does this path point to now?

1 Before any mount

/data is initially part of the container root filesystem

Suppose the image contains a file at /data/default.txt. When the container starts with no extra mount, the path is resolved through the image layers plus the container’s writable OverlayFS layer from Lesson 15.

no extra mount
→
container root filesystemImage layers underneath; the container’s writable layer on top.

If the process writes /data/new.txt, that file belongs to the container’s writable layer. It is tied to that container, and it uses copy-on-write storage.

Connection to Lesson 15. This is the normal root filesystem path. A large, frequently modified database file here may trigger OverlayFS copy-up and grows the container’s writable layer. Mounts give the path a different backing store.
2 What a mount changes

A mount covers the old view and places another filesystem view at the same path

A Linux mount has two sides:

sourceThe storage or filesystem view being attached.
→mounted at
destinationThe path inside the container, such as /data.

After the mount is installed, a lookup of /data/file.txt crosses the mount point and continues inside the mounted source. It no longer continues into the image directory that used to be visible at /data.

no mount
→
image + container writable layer
bind mount
→
a path already present on the daemon host
volume
→
storage located through a Docker volume driver
tmpfs
→
a new temporary filesystem created by the kernel
Nothing underneath was deleted

If a mount hides /data/default.txt, the image still contains the file. Recreate the container without that mount and the image file becomes visible again.

The OCI Runtime Specification expresses this with mount entries containing a destination, a source when needed, a filesystem type, and options. runtime-spec v1.3.0 · config.md · POSIX-platform mounts

3 Bind mount

/data points directly to a host path that you selected

bind a host directory
docker run --rm \
  --mount type=bind,src=/srv/mydata,dst=/data \
  alpine

The relationship is direct:

daemon host/srv/mydata
→bind-mounted at
container/data

If the container creates /data/report.txt, the daemon host sees /srv/mydata/report.txt. Both paths are views of the same underlying files.

Who owns and chooses the location?

You do. Docker does not create a separate storage object with its own identity. It records the source path and makes that host path available at the destination.

Which host?

The source path belongs to the machine running the Docker daemon—not necessarily the machine running the CLI. With a remote Docker context, src=/srv/mydata refers to /srv/mydata on the remote daemon host. This follows directly from Lesson 3’s client/daemon split.

Why bind mounts need care

They are writable by default. A container can modify or delete host files through the mount. Use readonly when the process only needs to read:

read-only bind
docker run --rm \
  --mount type=bind,src=/srv/config,dst=/app/config,readonly \
  IMAGE
A practical syntax difference

With legacy -v /missing:/data, Docker historically creates a missing host path as a directory. With explicit --mount type=bind, the source normally must already exist unless bind-create-src is requested. The source preserves this compatibility split in Moby 29.6.2 · daemon/volumes.go and daemon/volume/mounts/mounts.go · MountPoint.Setup.

4 Docker volume

/data points to storage that Docker resolves through a volume driver

create and use a named volume
docker volume create mydata

docker run --rm \
  --mount type=volume,src=mydata,dst=/data \
  alpine

This time you did not provide a host pathname. You provided a volume name: mydata.

1
dockerd looks up or creates mydata
The volume service records the object and the driver responsible for it.
2
dockerd asks the volume driver for a usable path
For the default local driver, the data directory is a Docker-managed _data path under the daemon’s volume root. Other drivers may mount NFS, block storage, or plugin-provided storage there.
3
dockerd places that resolved path into the OCI mount list
The high-level object called “volume” has now been translated into a concrete source path.
4
runc installs the mount at /data
The process sees the driver’s storage through an ordinary mounted path.
Source-over-folklore correction

A Docker volume is a real Docker-managed storage object, but it is not a special OCI mount type understood by runc. Moby resolves the volume to a source path. In daemon/oci_linux.go · withMounts, tmpfs stays type: "tmpfs", while ordinary user mounts—including resolved volume paths—are emitted as OCI bind mounts.

Where does the default local volume live?

The local driver constructs a directory whose data component is named _data. On a conventional rootful Linux Engine using the default data root, it commonly appears as:

typical local-driver path
/var/lib/docker/volumes/mydata/_data

Do not hard-code that path into applications. Docker’s data root can move, rootless mode uses a different location, and a non-local driver may not map to a permanent local directory at all. Use docker volume inspect mydata when inspecting it.

Named versus anonymous

FormHow identity is chosenExample
namedYou choose a stable name.src=mydata
anonymousDocker generates the volume identifier.--mount type=volume,dst=/data

Both use the same volume-service and volume-driver mechanism. The main difference is how easily you can identify and manage the object later.

5 tmpfs

/data points to a fresh temporary filesystem

mount a bounded tmpfs
docker run --rm \
  --mount type=tmpfs,dst=/data,tmpfs-size=64m \
  alpine

A tmpfs has no pre-existing source directory and no Docker volume object. The OCI entry names the filesystem type tmpfs; runc asks the Linux kernel to mount a new tmpfs at the destination. runc v1.3.6 · libcontainer/rootfs_linux.go · mountToRootfs

kernelcreates a new tmpfs instance
→mounted at
container/data

Its contents live in the kernel’s virtual-memory-backed filesystem and may consume RAM and swap. When the mount is destroyed, the files disappear. A new container gets a new, empty tmpfs.

Use case. tmpfs is useful for temporary state that must not enter the image writable layer or persist on disk as ordinary container storage—for example transient caches, scratch files, or sensitive short-lived data. It is not durable storage.
First-read checkpoint

At this point, keep only this map: bind = your host path; volume = Docker/driver-resolved storage; tmpfs = a new temporary kernel filesystem. All three change what the destination path points to.

6 Why existing image files can disappear—or be copied

Mounting normally hides the old directory; Docker volumes add one special population step

Return to the image that contains:

inside the image before any mount
/data/default.txt

Empty bind mount

If an empty host directory is bind-mounted at /data, the container sees the empty host directory. The image’s default.txt is covered and hidden. Docker does not copy it into the host directory.

Fresh tmpfs

A fresh tmpfs also begins empty. It covers the image directory; it does not inherit the image’s files.

New Docker volume

Volumes have a Docker-specific convenience behavior. During container creation, if volume copying is enabled, dockerd copies the existing directory content from the container root filesystem into the volume before the process starts.

1
Image root has /data/default.txt
The file exists in the unpacked image view.
2
dockerd prepares the new volume
It obtains the volume’s writable source path from the driver.
3
dockerd populates the volume
It copies the image directory contents into the volume.
4
the volume is mounted at /data
The file you see now is the copy stored in the volume—not the hidden image file underneath.

The implementation is explicit in Moby 29.6.2 · daemon/create_unix.go · populateVolumes / populateVolume: it applies to mount points of type volume with CopyData enabled and is called when the container is created.

Disable this behavior with:

do not populate the volume
docker run --rm \
  --mount type=volume,src=mydata,dst=/data,volume-nocopy \
  IMAGE
Do not confuse two different “copy” mechanisms

OverlayFS copy-up copies a lower-layer file into the container’s writable upper layer when it is modified. Volume population is a dockerd operation that copies an image directory into a Docker volume during container creation. They solve different problems and happen in different components.

7 Lifetime and persistence

Unmounting a storage source and deleting that source are separate actions

Mount typeWhen container stops/removesWhat remains?
bindThe bind mount is removed from the container.The host files remain because they were ordinary host files.
named volumeThe mount is released.The separate volume object normally remains until explicitly removed.
anonymous volumeThe mount is released.Removal depends on container-removal options such as --rm or docker rm -v.
tmpfsThe tmpfs is unmounted.Its contents are gone.

The Moby volume service rejects removal while a volume is still referenced, and the local driver tracks active mounts separately from the volume’s underlying data directory. daemon/volume/service/service.go · Remove · daemon/volume/local/local.go · Mount / Unmount / Remove

Precise persistence rule

A volume is not durable because “the container filesystem survives.” It is durable because the volume is a separate storage object whose lifetime is managed separately from the container.

8 Real execution order

Who performs each step?

1
Docker CLI sends a mount request
type, source/name, destination, read-only flag, and type-specific options go to dockerd over the Engine API.
2
dockerd resolves the high-level source
For a bind, it validates the daemon-host path. For a volume, it creates/gets the object and asks the driver to mount it. For tmpfs, there is no source path to resolve.
3
dockerd constructs OCI mount entries
The mount destination and concrete source/type/options enter the runtime specification.
4
containerd and the shim carry the spec to runc
They do not invent the Docker volume abstraction; the source has already been resolved by dockerd.
5
runc asks the kernel to install the mounts
runc safely resolves the destination inside the container root, then performs bind/tmpfs mounting before the user process starts.

This is the component boundary to remember:

dockerd
→
understands Docker volume names, drivers, population, and lifecycle
runc
→
understands concrete OCI mount entries and performs kernel mount operations
kernel
→
provides bind mounting, tmpfs, path lookup, permissions, and mount namespaces
9 Choosing the right source

Choose by ownership, portability, and lifetime

Bind mount

You own the path

Best when the container must directly use a known host directory: source code, local configuration, or host-generated files. Host-coupled and potentially dangerous when writable.

Volume

Docker/driver owns placement

Best for persistent application data whose lifecycle should be managed independently of one container: databases, queues, or shared service state.

tmpfs

Kernel owns temporary instance

Best for disposable runtime data that should vanish when the mount disappears and should not enter the container writable layer.

QuestionBindVolumetmpfs
Who selects storage?You name a host path.Docker asks a driver.Kernel creates it.

10 Inspect it yourself

Observe the same image through four different /data backings

Create a small image whose /data directory already contains a file:

build the demonstration image
mkdir -p lesson32-demo
cd lesson32-demo

cat > Dockerfile <<'EOF'
FROM alpine:3.21
RUN mkdir -p /data \
 && echo "from the image" > /data/default.txt
CMD ["sh", "-c", "ls -la /data; echo '---'; cat /data/default.txt 2>/dev/null || true"]
EOF

docker build -t lesson32-mounts .

A. No mount: see the image directory

normal container rootfs
docker run --rm lesson32-mounts

# default.txt is visible from the image.

B. Empty bind: the image directory is hidden

bind mount
mkdir -p host-data

docker run --rm \
  --mount type=bind,src="$PWD/host-data",dst=/data \
  lesson32-mounts

# /data is the empty host-data directory.
# default.txt still exists in the image, but the mount covers it.

C. New volume: Docker populates it

volume population
docker volume rm lesson32-data 2>/dev/null || true

docker run --rm \
  --mount type=volume,src=lesson32-data,dst=/data \
  lesson32-mounts

# default.txt appears because dockerd copied it into the new volume.

docker run --rm \
  --mount type=volume,src=lesson32-data,dst=/data \
  alpine sh -c 'echo "written in volume" > /data/persistent.txt'

docker run --rm \
  --mount type=volume,src=lesson32-data,dst=/data \
  alpine cat /data/persistent.txt

D. tmpfs: fresh and temporary

tmpfs lifetime
docker run --rm \
  --mount type=tmpfs,dst=/data,tmpfs-size=16m \
  alpine sh -c 'echo temporary > /data/value; cat /data/value'

docker run --rm \
  --mount type=tmpfs,dst=/data,tmpfs-size=16m \
  alpine sh -c 'test ! -e /data/value && echo "new tmpfs is empty"'

E. Inspect what dockerd recorded

mount metadata
docker create --name lesson32-check \
  --mount type=volume,src=lesson32-data,dst=/data \
  alpine sleep 60

docker inspect lesson32-check \
  --format '{{json .Mounts}}'
docker volume inspect lesson32-data

docker rm lesson32-check
docker volume rm lesson32-data
rm -rf host-data

For a running container on Linux, you can also inspect the kernel’s view:

kernel mount table from inside
docker run --rm \
  --mount type=tmpfs,dst=/data,tmpfs-size=16m \
  alpine sh -c 'grep " /data " /proc/self/mountinfo'

Check yourself

  • Without an extra mount, /data belongs to the image plus the container writable layer.
  • A mount does not delete the old directory; it covers that view with another source.
  • A bind mount uses a path chosen on the daemon host.
  • A volume is a Docker-managed object resolved through a driver, then normally passed to runc as a concrete bind-mount source.
  • A tmpfs is a fresh kernel filesystem whose contents vanish when it is unmounted.
  • Docker’s volume population is a daemon feature; it is not ordinary mount behavior and is not OverlayFS copy-up.
  • Storage lifetime is separate from mount lifetime: unmounting a named volume does not itself delete the volume.
Final correction

“Use a volume because it lives outside the container” is too vague. All three sources are mounted into the container’s mount namespace. The useful distinction is what object backs the destination path, who selects and manages that object, and how long that object’s data survives.
