BuildKit: a build is a graph, not a script

The modern builder throws out the linear chain and compiles your Dockerfile into a content-addressed graph, then solves it — running only what changed, in parallel, with secrets and caches that never leak into layers.

The idea in one sentence

BuildKit compiles your Dockerfile into a graph of operations (LLB), then a solver runs only the parts whose inputs changed — in parallel — instead of executing lines top to bottom.

1 Start here

From a script to a graph

Plain version: the legacy builder ran your Dockerfile line by line. BuildKit compiles it into a plan, then works out the least it can do to satisfy that plan.

Lesson 24's builder was imperative: do line 1, commit, do line 2, commit. BuildKit is declarative. It treats your Dockerfile as a description of a desired result, compiles it into a graph of operations, and then a solver figures out which operations actually need to run. This one change — from "execute these steps" to "here's the graph, compute the result" — is where all of BuildKit's advantages come from.

2 The graph

LLB: the assembly language of builds

Plain version: LLB is a graph where each node is one operation — fetch a source, run a command, copy files — and the arrows show which node needs which.

LLB (Low-Level Build definition) is BuildKit's intermediate representation: a content-addressed DAG (directed acyclic graph) of operations, defined as protobuf (solver/pb/ops.proto). The node types are few: SourceOp (fetch an image, git repo, or local files), ExecOp (run a command), FileOp (copy, mkdir), plus merge/diff ops. Each Op lists its inputs — and those inputs are the edges that make it a graph rather than a line. Dockerfiles don't run directly anymore; they compile to LLB, the way source compiles to assembly.

3 Frontends

The Dockerfile is just one input language

Plain version: a "frontend" is a translator that turns some high-level format into LLB. Dockerfiles are one; you could write others.

A frontend converts a high-level build format into LLB. The Dockerfile frontend (frontend/dockerfile/dockerfile2llb, function Dockerfile2LLB) parses your Dockerfile and emits the LLB graph. Because the frontend is pluggable, the Dockerfile is just one supported language — and the # syntax=docker/dockerfile:1 line at the top of a Dockerfile actually selects a frontend container image, so you can get new Dockerfile features by bumping that line without upgrading Docker itself.

4 The solver

How the graph gets executed

Plain version: the solver walks the graph, and for each node asks "have I already computed this?" — running the node only if not.

The solver (solver/scheduler.go, solver/jobs.go) takes the LLB graph and computes the result. For each vertex it derives a cache key from that vertex's operation plus its inputs' cache keys, checks the cache, and executes the operation only on a miss. Execution of an ExecOp is handed to a worker, which runs the step in a container via runc/containerd — so the run pipeline you learned in Lesson 23 is what actually executes each build step. The solver's scheduler works on the graph's edges, which is what lets it run independent vertices at the same time.

5 The payoffs

Parallelism and graph-aware caching

Plain version: because it's a graph, unrelated steps run at once, and a change only reruns the steps that actually depend on it.

Two big wins fall directly out of the DAG. Parallelism: branches with no dependency between them run concurrently — while your app compiles, the runtime base image can be pulled at the same time. Graph-aware caching: a change invalidates only the vertex you changed and the vertices downstream of it; unrelated branches stay cached. This is the fix for Lesson 24's linear cache, where an early change rebuilt everything after it regardless of relevance. BuildKit can also export and import its cache (e.g. to a registry), so CI machines share build cache.

6 The new power

Cache mounts and secret mounts

Plain version: a step can mount a persistent cache dir or a secret that exists only during that step and never lands in a layer.

Because every ExecOp declares its mounts explicitly (ops.proto: Mount, with CacheOpt and SecretOpt), BuildKit can attach mounts the legacy builder never could. A cache mount (RUN --mount=type=cache,target=/root/.cache) persists a directory across builds — your package downloads survive, without becoming a layer. A secret mount (RUN --mount=type=secret,id=token) exposes a secret to one step and leaves no trace in any layer — directly solving the "deleted secret is still in the layer" leak from Lesson 17. These are impossible in a commit-chain model and natural in a graph of explicitly-mounted ops.

Why the graph changes everything

Every BuildKit advantage — parallel steps, precise caching, cache sharing, cache/secret mounts — is a consequence of one decision: represent the build as a content-addressed graph of explicitly-connected operations, and solve it, rather than execute a line-by-line script.

Inspect it yourself

Check yourself

  • BuildKit is declarative: it compiles the Dockerfile into a graph and solves it, instead of running lines in order.
  • LLB is a content-addressed DAG of ops — SourceOp, ExecOp, FileOp — each listing its inputs (the edges).
  • A frontend translates a format into LLB; the Dockerfile is one, selected by # syntax=.
  • The solver computes a cache key per vertex and runs only misses, dispatching exec steps to a worker (runc/containerd).
  • The graph gives parallelism and graph-aware caching (change → only descendants rerun), plus cache export/import.
  • Explicit mounts enable cache mounts and secret mounts — impossible in the legacy commit-chain.
Where this corrects the familiar version

"BuildKit is just a faster Dockerfile builder" undersells it — it's a different model. The Dockerfile isn't executed at all; it's compiled to LLB, and the LLB graph is what runs, which is why builds parallelize and cache by dependency instead of by line. And the secret-leak lesson from earlier finally has a real fix: a secret mount is present only for one step and never becomes a layer — so "I deleted it in the next line" is replaced by "it was never in a layer to begin with."

Where we are

Summary

BuildKit replaces the linear commit-chain with a graph. A frontend compiles your Dockerfile into LLB — a content-addressed DAG of SourceOp/ExecOp/FileOp nodes wired by their inputs — and the solver computes a cache key for each vertex, runs only the misses (dispatching exec steps to a runc/containerd worker), and schedules independent vertices in parallel. Caching follows the graph, so a change reruns only its descendants; cache can be exported and shared; and explicitly-mounted ops enable cache and secret mounts that never touch a layer. Every advantage traces back to representing a build as a solvable graph. Next, Lesson 26 walks every Dockerfile instruction and shows exactly what LLB each one compiles to.
