Checkpoint/restore with CRIU

DEEP-CUT

How can a container process stop existing, then later continue from the middle of its execution instead of starting from the beginning? This lesson follows that exact state movement.

governing idea

Checkpoint copies the process's live execution state into CRIU files. Restore creates new live kernel objects from those files, inside Docker's existing container environment, then gives the CPU back the saved register state so the program continues.

pinned source baseline

Docker Engine / Docker CLI 29.6.2 · containerd 2.2.6 · runc 1.3.6 · OCI runtime-spec 1.3.0 · Linux 6.18. CRIU is external to Docker's pinned runtime dependency family, so CRIU internals are pinned separately to v4.2.1.

1. First make the problem concrete

Imagine the container's main process is roughly this C program:

int n = 0;
int fd = open("/data/count.log", O_WRONLY | O_APPEND);

for (;;) {
    n++;
    dprintf(fd, "%d\n", n);
    sleep(1);
}

Suppose we checkpoint it when n == 812. At that instant, several different kinds of state exist:

StateConcrete exampleWhere it exists now
filesystem statethe executable and /data/count.logcontainer root filesystem / mounts
memory staten == 812, stack frames, heap datathe process address space, backed by kernel-managed memory
CPU statethe instruction pointer says which instruction should execute next; the stack pointer points into the current stackregister state associated with the task
kernel-resource stateFD 3 refers to an open file description, with flags and a current file positionLinux kernel objects referenced by the process

If you keep only the filesystem and later launch the executable again, the new process starts with n = 0. It does not know that the old process was at 812, which instruction was next, which descriptors were open, or what the old stack contained.

the misunderstanding to remove

A Docker checkpoint is therefore not an image snapshot. The rootfs is only one input. CRIU saves the missing live execution state.

2. Four terms, defined before we use them

live execution state

The information that makes the process be at its current instant rather than at program startup: memory contents, registers, open descriptors, task relationships, signals, timers, credentials, and other supported kernel-visible state.

checkpoint

A point-in-time serialization of supported live execution state into files.

CRIU image files

CRIU's name for its checkpoint files. Here, image does not mean Docker/OCI image. These files describe saved process state.

restore

Reconstruction of live processes and resources from those saved files. The old kernel task objects do not have to survive; compatible new kernel objects are created.

3. The entire pipeline before any internals

Checkpoint destination: files on disk. Restore destination: new live tasks and resources in the Linux kernel. The Docker container's rootfs/configuration is not replaced by the checkpoint; it is the environment CRIU restores into.

movement summary
what starts

a CLI request naming a running container and checkpoint ID

what moves

first control requests move downward; then CRIU copies descriptions/content of live state into checkpoint files

what changes

live kernel/process state becomes serialized files; on restore, serialized state becomes live kernel/process state again

final result

the application continues from the checkpointed execution state instead of starting from its executable entry point

4. Checkpoint: follow one command all the way down

docker checkpoint create mycontainer cp1
1

Docker CLI sends the checkpoint request

The CLI sends the container name, checkpoint ID, optional checkpoint directory, and an Exit boolean. By default Exit=true. Passing --leave-running flips it to false.

2

dockerd finds the live task and creates the destination directory

dockerd resolves the container, obtains its running task, creates the checkpoint directory, and calls the task's checkpoint operation with that path and the Exit value. If checkpointing fails, it removes the directory it just created.

At this hop, no process memory has moved yet. Only control information and a filesystem destination have been prepared.

The running container already has a runtime-v2 shim. containerd does not itself read the process's memory. It forwards the checkpoint operation to that shim.

Responsibility split: runc prepares the container-specific restore/dump context; CRIU performs the actual process-state dump and restore.

6

CRIU finally touches the live process state

This is the first point where the mechanism becomes about the actual running process. CRIU freezes/stabilizes the task tree, inspects its state, obtains memory/register/resource information, and writes CRIU checkpoint files into the directory runc was given.

5. What CRIU actually does during checkpoint

Use our example process again: n == 812, FD 3 is open, and the CPU is somewhere inside the loop. CRIU needs a consistent picture of that instant.

A. Stop the state from changing

If the process kept running while CRIU copied it, CRIU could read the stack at one instant, the descriptor table at another, and the memory pages after the program had already changed them. The result would not describe one coherent process state.

CRIU therefore first immobilizes the task tree. Its documented normal mechanism walks the process/thread tree and seizes tasks with ptrace(PTRACE_SEIZE, ...); CRIU can also use a freezer cgroup path in suitable setups.

After this point, think: the process is held still while CRIU measures it.

B. Read the shape of the process

CRIU reads Linux process interfaces such as /proc/<pid>/maps/smaps for virtual-memory areas and /proc/<pid>/fd/fdinfo for descriptor information. It also uses ptrace for task/register information.

This tells CRIU facts such as: “this process has this address range mapped,” “FD 3 refers to this resource,” and “these are the saved registers.”

C. Copy memory contents

Knowing that a memory mapping exists is not enough. For our counter, CRIU also needs the page bytes containing n == 812. CRIU's memory-dump path determines which pages need saving and transfers their contents into checkpoint files.

CRIU uses small helper code inside the seized process for operations that are easiest from the process's own address-space context. CRIU calls that helper code the parasite.

parasite — only what you need

Do not treat “parasite” as another Docker component. It is CRIU's internal helper code temporarily executed inside the process being dumped. Its purpose is to help CRIU obtain state such as memory contents and credentials from the target's own context. CRIU removes it before completing the dump.

D. Write state to disk

CRIU serializes the collected state into multiple checkpoint files. Conceptually, the files now contain enough information to reconstruct things such as memory mappings/pages, register state, task relationships, descriptors, signals, timers, credentials, and other supported resources.

do not make this substitution

checkpoint files ≠ container rootfs. The executable and ordinary filesystem still belong to the existing Docker container. CRIU's files contain the live-state side of the equation.

6. What happens to the original process?

There are two different modes, and the distinction is simple:

CommandAfter successful checkpoint
docker checkpoint create c cp1Docker CLI sends Exit=true. The original runtime task is not kept running.
docker checkpoint create --leave-running c cp1Docker CLI sends Exit=false; lower layers request leave-running behavior and the original task continues.

With --leave-running, the checkpoint remains a snapshot of one earlier instant. If the live process goes from n=812 to n=900 afterward, the checkpoint still describes the saved 812-era state.

7. Restore: two inputs meet

Restore becomes much easier once you stop imagining the checkpoint as self-contained. Docker needs two inputs:

  1. the existing container environment — rootfs, container configuration, mounts, network/runtime setup;
  2. the CRIU checkpoint files — the saved live execution state.
docker start --checkpoint cp1 mycontainer
1

dockerd prepares the container as if it is going to run again

The pinned Engine start path mounts/prepares storage, initializes networking, sets up mounts, and creates a fresh OCI runtime configuration. If a checkpoint name is supplied, it also resolves that existing checkpoint directory.

This matters: CRIU is not asked to manufacture Docker's container environment from nothing. dockerd prepares that environment first.

Engine 29.6.2 · daemon/start.go · containerStart
2

dockerd creates a new containerd task with a checkpoint path

The old live task is gone in the normal checkpoint case. So restore creates a new runtime task instance. dockerd calls containerd's task-creation path and passes the checkpoint directory.

Engine 29.6.2 · daemon/start.go · ctr.NewTask(checkpointDir, ...)
3

The shim enters a special “created from checkpoint” state

When the shim sees a checkpoint path during creation, it does not perform a normal runc create. It builds runc.RestoreOpts containing the checkpoint image path and moves into createdCheckpointState.

So at this moment the task is prepared for restore, but the restored application is not live yet.

containerd 2.2.6 · process/init.go · createCheckpointedState
4

Task Start triggers runc restore

The key source-level detail is in createdCheckpointState.Start: instead of calling normal runc start, the shim calls runtime.Restore(...). After runc/CRIU successfully restore the process, the shim reads the restored PID and transitions the task to running.

containerd 2.2.6 · process/init_state.go · createdCheckpointState.Start
5

runc passes CRIU the checkpoint directory plus the container/runtime information needed to place the restored tasks into the correct environment. This is where the saved state and the prepared runtime context meet.

6

CRIU rebuilds live processes and resources

CRIU reads the checkpoint files, reconstructs the process tree, recreates/restores supported files, memory mappings, namespaces/resources, memory contents, timers, credentials, threads and other saved state. The Linux kernel now contains new live task/resource objects corresponding to the saved execution state.

8. The hardest part: why execution continues at 812

Suppose CRIU has already rebuilt the process's memory. The memory page containing n again contains 812. That still is not enough.

The CPU also needs to know where to continue executing. On x86-64, for example, the saved instruction pointer is in RIP, the saved stack pointer is in RSP, and many other registers hold the process's current machine state.

Starting the executable normally would initialize a fresh register context and run the program's startup path. CRIU instead needs the kernel to install the saved register context.

How CRIU gets the saved registers back into the CPU context

Linux already has a mechanism for restoring a complete userspace register context: returning from a signal handler. When a signal handler finishes, the rt_sigreturn system call tells the kernel to restore register state from a signal frame.

CRIU uses that machinery deliberately. Near the end of restore it runs a small restorer blob—temporary code placed where it will not collide with either CRIU's mappings or the target process's final mappings. The restorer finishes putting the target memory layout and late resources into place and arranges a signal frame containing the saved CPU state.

Then rt_sigreturn makes the kernel load the saved registers. If the saved instruction pointer says “continue at the instruction after this point in the loop,” that becomes the task's instruction pointer again.

this is the moment to understand

After rt_sigreturn, the CPU is not told “start this executable.” It is given the register state of the checkpointed process. Combined with the restored memory, that is why the program can continue with n == 812 rather than start again with n == 0.

CRIU 4.2.1 · cr-restore.c · sigreturn_restore · pie/restorer

9. Same logical process, not the same old kernel objects

After a default checkpoint, the original task may be gone. Restore therefore cannot literally awaken the old task_struct from memory.

Instead, CRIU creates new tasks/resources and reconstructs their userspace-visible state to match the checkpoint as closely as supported. Think of this as:

old live kernel objects
        ↓ checkpoint
serialized CRIU state
        ↓ restore
new live kernel objects with reconstructed saved state

The continuity is the logical execution state, not physical survival of the old kernel objects.

10. Why checkpoint/restore is harder than restart

OperationWhat survives?What happens next?
restartcontainer filesystem/configuration; not the old process memory/registersa fresh process begins through normal program startup
pause/unpausethe same live tasks remain present; execution is temporarily stoppedthe same kernel tasks continue
checkpoint/restoresupported live execution state is serialized to disknew live tasks/resources are reconstructed and continue from saved state

Because checkpoint/restore reconstructs kernel-visible state, compatibility matters. Open files must still make sense; mounts and namespaces must be compatible; sockets and network peers can require special handling; kernel and CPU features can matter. CRIU cannot promise that arbitrary external resources can always be recreated.

11. Where OCI stops, and Docker's pinned limitations

The OCI Runtime Specification 1.3.0 standardizes the normal runtime lifecycle such as create, start, state, kill, and delete. It does not standardize checkpoint/restore as an OCI runtime lifecycle operation.

So this is an extension implemented by the real stack:

Docker CLI → dockerd → containerd → shim → runc → CRIU → Linux kernel
pinned Engine 29.6.2

Restore with a checkpoint is allowed only when daemon experimental mode is enabled. The same start path explicitly rejects a non-empty custom checkpoint directory with custom checkpointdir is not supported. These are properties of the pinned Engine implementation, not universal CRIU laws.

rootless boundary

runc 1.3.6 warns in its checkpoint/restore paths that this is unlikely to work cleanly in a user namespace; its source still treats unprivileged restore as an unresolved area. Do not assume Lesson 44's rootless path automatically supports CRIU restore.

12. Inspect it yourself: prove that memory state continued

Run this only on a disposable Linux host where CRIU is installed and Docker checkpoint/restore is supported. Restore on the pinned Engine line requires experimental mode.

host checks
docker version
criu --version
sudo criu check
docker info | grep -i experimental || true

The experiment below deliberately keeps the counter i only in the shell process's memory. A signal handler writes its current value to a file only when we ask for an observation.

start a process with in-memory state
docker rm -f l38 2>/dev/null || true

docker run -d --name l38 alpine \
  sh -c 'i=0; trap '\''echo "$i" >/tmp/seen'\'' USR1; \
  while :; do i=$((i+1)); sleep 1; done'

sleep 5
docker kill --signal=USR1 l38
sleep 1
echo -n 'before checkpoint: '
docker exec l38 cat /tmp/seen

If the output is around 5 or 6, that value came from the shell variable i that exists in the running process.

checkpoint the task
docker checkpoint create l38 cp1

docker inspect l38 \
  --format 'running={{.State.Running}} status={{.State.Status}} pid={{.State.Pid}}'

docker checkpoint ls l38

With default Exit=true, the old task should not remain running after a successful checkpoint.

restore and observe the same counter continuing
docker start --checkpoint cp1 l38
sleep 3

docker kill --signal=USR1 l38
sleep 1
echo -n 'after restore: '
docker exec l38 cat /tmp/seen

If the checkpoint observation was around 5, the post-restore observation should continue from that neighborhood and then advance—not restart from zero. The exact numbers vary because timing varies.

find the CRIU checkpoint files
cid=$(docker inspect -f '{{.Id}}' l38)
root=$(docker info -f '{{.DockerRootDir}}')

sudo find "$root" -type d -path '*/checkpoints/cp1' -print 2>/dev/null

List the directory you find. The contents are checkpoint-state files/logs, not an OCI image manifest/config/layer graph.

13. Check yourself before moving on

  1. Why is the container rootfs insufficient for checkpoint/restore?
    Because it does not contain the current memory, register context, FD table/resource state, timers, task relationships, and other live execution state.
  2. Who actually serializes process state?
    CRIU. runc supplies container-specific runtime context and orchestrates CRIU.
  3. What are the two restore inputs?
    The existing Docker container environment/rootfs plus the CRIU checkpoint files.
  4. Why does the program continue rather than restart?
    CRIU restores memory and ultimately uses signal-return machinery to install the saved register context, including the saved instruction/stack pointers.
  5. Are the restored tasks literally the old kernel task objects?
    No. Restore creates new live kernel objects whose supported visible state is reconstructed from the checkpoint.
60-second model

Checkpoint: hold the process still → inspect memory/registers/resources → write CRIU files. Restore: dockerd rebuilds the container runtime environment → containerd/shim select the restore path → runc gives CRIU the runtime context → CRIU rebuilds tasks/memory/resources → rt_sigreturn installs the saved CPU state → execution continues.

Primary-source appendix

The explanation above is built from the pinned implementation/specification chain, not from generic checkpoint folklore.

Docker CLI 29.6.2 — checkpoint options

cli/command/checkpoint/create.go: runCreate sends CheckpointID, CheckpointDir, and Exit: !opts.leaveRunning.

Docker Engine 29.6.2 — checkpoint create

daemon/checkpoint.go: CheckpointCreate resolves the running task, creates/resolves the checkpoint directory, and calls tsk.CreateCheckpoint(context.Background(), checkpointDir, config.Exit).

Docker Engine 29.6.2 — restore start preparation

daemon/start.go: ContainerStart requires experimental mode when a checkpoint is supplied. containerStart rejects a custom checkpoint directory, prepares mounts/networking/spec, resolves the checkpoint, creates a new containerd task with the checkpoint directory, then starts that task.

containerd 2.2.6 — checkpoint/restore state path

cmd/containerd-shim-runc-v2/process/init.go: Init.checkpoint maps Exit=false to runc's LeaveRunning. createCheckpointedState builds runc.RestoreOpts. process/init_state.go: createdCheckpointState.Start calls runtime.Restore(...), reads the restored PID, and transitions to running.

runc 1.3.6 — CRIU adapter

libcontainer/criu_linux.go: Container.Checkpoint and Container.Restore construct CRIU RPC options for the container environment; criuSwrk runs the CRIU service-worker RPC path. The same source warns about rootless/user-namespace limitations.

CRIU 4.2.1 — checkpoint internals

CRIU's authoritative Checkpoint/Restore design describes collecting/freezing the process tree, reading state from /proc, using ptrace, injecting parasite helper code for target-context operations, and writing task/resource/memory state to dump files. Its memory documentation describes mapping/page discovery and page transfer.

CRIU 4.2.1 — restore and sigreturn

CRIU's restore design describes resolving shared resources, forking the process tree, restoring basic resources, switching into a restorer code blob, restoring final memory/timers/credentials/threads, and returning to the saved execution context. In criu/cr-restore.c, the path reaches sigreturn_restore.

OCI runtime-spec 1.3.0 — boundary

runtime.md defines the ordinary create, start, state, kill, and delete operations. Checkpoint/restore is not standardized there.
