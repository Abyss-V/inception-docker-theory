Garbage collection & leases: what's safe to delete

Blobs and snapshots accumulate forever unless something reclaims them. How containerd decides which bytes are still needed — and how it avoids deleting content out from under an in-progress pull.

The idea in one sentence

containerd keeps content by reachability: it marks everything reachable from a "root" (an image, a container, or a lease) and sweeps the rest — and a lease is a temporary root that protects content mid-operation.

1 Start here

When is a blob safe to delete?

Plain version: you can't just delete anything nobody points at right now — something might be halfway through pulling it. You need a careful rule.

The content store (Lesson 20) and the snapshotter (Lesson 16) accumulate blobs and snapshots as you pull, build, and run. Something has to reclaim the ones no longer needed, or the disk fills forever. But "delete anything unreferenced" is dangerous: during a pull, blobs exist on disk before the image record that will reference them — delete them in that window and you've corrupted an in-progress operation. So containerd needs a disciplined rule for "still needed," and it borrows the classic one: garbage collection by reachability.

2 The graph

References are labels on records

Plain version: every stored object can carry little "I point to that" tags; together they form a graph of what-needs-what.

containerd's metadata database stores every object — images, containers, content blobs, snapshots — and records the references between them as labels (from metadata/gc.go). An object marked containerd.io/gc.root is a root; a label containerd.io/gc.ref.content points to a blob by digest; containerd.io/gc.ref.snapshot.<snapshotter> points to a snapshot. So an image references its manifest, config, and layer blobs; a container references its snapshot; a snapshot references its parent. These labels are the edges of a graph.

3 The algorithm

Mark from the roots, sweep the rest

Plain version: start at the things definitely in use, follow every "points to" edge, keep what you reach, delete what you don't.

Garbage collection is mark-and-sweep. containerd's scanRoots gathers the roots — images, containers, and leases — then follows the gc.ref.* labels to mark everything reachable. Anything not marked is unreachable by any root, so it's garbage and gets swept (deleted). A base layer shared by two images has two roots reaching it, so removing one image leaves it marked by the other — which is exactly why deleting one image never breaks another that shares layers.

4 The subtle part

Leases: temporary roots that protect an operation

Plain version: during a pull or build, there's no image record yet to keep the new blobs alive — a lease stands in as a stand-in root until the operation finishes.

This is the piece people miss. When you start a pull, the layer blobs land in the content store before any image record references them. If GC ran in that gap, those blobs would look like orphans and be swept mid-download. A lease prevents that: containerd creates a lease at the start of the operation, and that lease is a root (from core/leases: a lease "retains resources to prevent cleanup"). While the lease exists, everything it references is reachable and safe. When the operation completes and a permanent root exists (the image record), the lease is released. And a lease can carry an expiry (gc.expire), so if the process crashes, the pin clears itself rather than leaking forever.

Why this design

Reference counting alone can't tell "unreferenced because done" from "unreferenced because not-yet-referenced." Roots-plus-leases solves both: permanent roots (images, containers) express steady-state needs, and leases express in-flight needs with a built-in expiry for crashes. One mechanism, both cases.

5 In practice

What docker prune actually does

Plain version: prune removes the roots; GC then sweeps whatever those roots were keeping alive.

Now docker image prune and docker system prune make sense: they delete image records — that is, they remove roots. Removing a root doesn't directly free bytes; it makes the blobs and snapshots that only that root reached become unreachable, and the next GC pass sweeps them. This is why space isn't always reclaimed the instant you docker rmi, why a shared layer survives until the last image referencing it is gone, and why prune is the real reclaim command — it's removing roots so the collector can do its job.

Check yourself

  • Content can't be deleted just for being unreferenced now — it might be mid-operation. GC by reachability solves this.
  • References are labels in the metadata db: gc.root (a root), gc.ref.content / gc.ref.snapshot (edges).
  • GC is mark-and-sweep from roots = images, containers, leases; unreachable objects are swept.
  • A lease is a temporary root that pins in-progress content during a pull/build, with an expiry so crashes don't leak pins.
  • A shared layer stays until the last root referencing it is gone.
  • docker prune removes roots; the next GC pass reclaims the now-unreachable bytes.
Where this corrects the familiar version

"docker rmi frees the disk" isn't quite it — removing an image removes a root, and space comes back only when GC sweeps what that root was solely keeping alive (and only if no other image shares it). And the reason a fresh pull never gets corrupted by a simultaneous prune isn't luck — it's leases, deliberately pinning in-flight blobs as roots until the operation commits. Reachability, not reference-count-hits-zero, is the actual rule.

Where we are

Summary

containerd reclaims storage by reachability, not by naive reference counts. Objects in the metadata database carry GC labels — gc.root for roots, gc.ref.content/gc.ref.snapshot for edges — forming a graph. The collector marks everything reachable from the roots (images, containers, and leases) and sweeps the rest. A lease is a temporary root that protects blobs and snapshots during an in-flight pull or build, with an expiry so a crash can't leak the pin. docker prune works by deleting roots and letting GC reclaim what becomes unreachable, and shared layers persist until their last referencing root is gone.
