Config & secrets

CORE

This lesson is about how values travel into a container. We will follow configuration through four different pipelines: ordinary environment variables, Compose .env, local Compose secrets, and Swarm secrets.

governing idea

Two methods can deliver the same password to an application but still be very different internally. The key question is: where do the bytes travel, who handles them, and where do they end up?

Same destination for the application, but different internal travel paths.

1. Ordinary docker run environment variables

Start with the simplest case:

docker run -e MODE=production --env-file app.env image

The first important fact is that Docker CLI reads --env-file. The daemon does not open that file itself. The CLI parses the lines, turns them into strings like NAME=value, and sends those strings in the container-create request.

client file app.env
      ↓  (read by Docker CLI)
NAME=value strings
      ↓
dockerd Config.Env

This means the path is a client-side path. If you talk to a remote daemon, --env-file still reads a file on the machine where the CLI runs.

Bare -e NAME is also client-side

If you write:

export TOKEN=abc123
docker run -e TOKEN image

Docker CLI looks up TOKEN in its own process environment. It then sends the resulting TOKEN=abc123 string to the daemon.

source-over-folklore correction

-e NAME does not mean “ask the daemon for NAME.” It means “copy NAME from the environment of the Docker CLI process.”

Source anchors: Docker CLI 29.6.2 · opts/parse.go, opts/env.go.

2. How dockerd builds the final process environment

Once the daemon has received the environment strings, it stores them in the container configuration as Config.Env. That is already an important point: the values now exist as Docker container metadata.

But that is not yet the final process environment. dockerd does three more things:

  1. It merges the runtime environment with the image’s ENV defaults.
  2. It adds its own runtime defaults such as PATH and HOSTNAME (and TERM when a TTY is requested).
  3. It writes the result into the OCI runtime spec field process.env.
CLI / Compose input
      ↓
dockerd Config.Env
      ↓
merge image ENV defaults
      ↓
add PATH / HOSTNAME / TERM
      ↓
OCI process.env
      ↓
process environ

Image ENV is a default, not an unbeatable value

If the image has:

ENV MODE=development

and you run:

docker run -e MODE=production image

then the runtime value wins for the same key. The image value stays only when the runtime configuration did not replace it.

Source anchors: Docker Engine 29.6.2 · api/types/container/config.go, daemon/commit.go::merge, daemon/container/container.go::CreateDaemonEnvironment, daemon/oci_linux.go; OCI runtime-spec 1.3.0 · process.env.

3. Compose .env and service env_file: are different

thingmain jobdoes it automatically become container env?
.envFeed values to Compose while it parses/interpolates the projectNo
service env_file:Populate that service’s runtime environmentYes

So if .env contains:

TAG=1.4
PASSWORD=secret

and the Compose file contains:

image: "myapp:${TAG}"

then Compose uses TAG to produce myapp:1.4. But PASSWORD does not automatically enter the container unless the Compose file actually puts it into a service environment section.

.env
  ↓
Compose interpolation environment
  ↓
resolved service config
  ↓
only enters container env if the service config uses it

By contrast, service env_file: is part of the service runtime configuration, so Compose eventually turns it into the same Docker Engine Config.Env path described earlier.

keep the two pipelines separate

.env is mainly for Compose itself. Service env_file: is for the container process environment.

Source anchors: Compose 5.1.4 · project options / dotenv loading; pkg/compose/create.go service environment → Engine Config.Env.

4. Why secret files are different from environment secrets

Suppose the application needs a database password.

If you deliver it as an environment variable:

DB_PASSWORD=actual-secret

then the secret value travels through Docker container metadata and then into the process environment.

If you deliver it as a file:

/run/secrets/db_password

then Docker can store a mount description or file path instead of storing the secret value itself in Config.Env.

precise benefit

A secret file does not make the secret unusable by the application. The benefit is narrower: it avoids spreading the actual secret value through ordinary environment metadata.

5. Local Compose file secrets are read-only bind mounts

Consider this Compose fragment:

services:
  app:
    image: alpine
    secrets:
      - db_password

secrets:
  db_password:
    file: ./db_password.txt

In current local Compose, that file-backed secret becomes a read-only bind mount. In other words:

host file ./db_password.txt
      ↓
Compose asks for a read-only bind mount
      ↓
dockerd mounts it inside the container at
/run/secrets/db_password

This connects directly to Lesson 32: the secret is being delivered with the bind-mount mechanism, not with a special encrypted kernel secret mechanism.

major correction

Local Compose file secrets are not the same implementation as Swarm secrets. They only look similar inside the container because both usually use the path /run/secrets/....

One current local-Compose edge case

If the secret source is not a file—for example, an environment-backed secret—current Compose can inject it by copying a file into the container before the container starts. That is why this path does not work with a read-only root filesystem.

Source anchors: Compose 5.1.4 · pkg/compose/create.go bind-mount secret path; pkg/compose/secrets.go file-copy injection path.

6. Swarm secrets really do use worker-side tmpfs staging

Now switch to a real Swarm secret. The worker-side daemon does something very different:

  1. Create a container-specific tmpfs staging directory.
  2. Fetch each secret from the worker’s dependency store.
  3. Write the secret bytes into files in that tmpfs.
  4. Apply the requested UID, GID, and mode.
  5. Remount the tmpfs read-only.
  6. Present the secret files to the task, usually under /run/secrets/....
Swarm secret object
      ↓
worker dockerd dependency store
      ↓
container-specific tmpfs
      ↓
write bytes + chown + chmod
      ↓
remount tmpfs read-only
      ↓
mount secret file into task

This is the implementation many people vaguely remember when they talk about “Docker secrets,” but it applies to the Swarm secret path, not to an ordinary local Compose file-backed secret.

Source anchors: Docker Engine 29.6.2 · daemon/container_operations_unix.go secret directory creation, tmpfs mount, secret write, remount, and task secret mounts.

7. _FILE is application code, not a Docker feature

You will often see patterns like:

POSTGRES_PASSWORD_FILE=/run/secrets/postgres_password

This works in the PostgreSQL official image because its entrypoint script explicitly implements that convention. It sees a variable ending in _FILE, opens the file, reads the contents, and sets the real variable.

/run/secrets/postgres_password
      ↓
entrypoint script opens file
      ↓
exports POSTGRES_PASSWORD
      ↓
PostgreSQL startup code uses it
important correction

_FILE is not a generic Docker rule. If the image or application does not implement it, nothing special happens.

Source anchor: PostgreSQL official image · docker-entrypoint.sh::file_env.

9. Inspect it yourself

A. see image defaults, env-file, explicit override, and client-side -e NAME
mkdir -p /tmp/l36-env && cd /tmp/l36-env

cat > Dockerfile <<'EOF'
FROM alpine
ENV COLOR=image-default
ENV IMAGE_ONLY=from-image
CMD ["sh","-c","env | sort"]
EOF

docker build -t l36-env .

cat > runtime.env <<'EOF'
COLOR=from-env-file
FILE_ONLY=from-env-file
EOF

export CLIENT_ONLY=from-client-shell

docker create --name l36-env-c \
  --env-file runtime.env \
  -e COLOR=from-explicit-flag \
  -e CLIENT_ONLY \
  l36-env

docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' l36-env-c
docker start -a l36-env-c
B. prove that Compose .env is not service env_file:
mkdir -p /tmp/l36-compose && cd /tmp/l36-compose

cat > .env <<'EOF'
INTERP=from-dot-env
ONLY_DOTENV=not-automatically-in-container
EOF

cat > service.env <<'EOF'
RUNTIME=from-service-env-file
COLLIDE=from-env-file
EOF

cat > compose.yaml <<'EOF'
services:
  demo:
    image: alpine
    env_file:
      - service.env
    environment:
      COLLIDE: from-environment
      FROM_INTERP: "${INTERP}"
    command: ["sh","-c","env | sort"]
EOF

docker compose config
docker compose run --rm demo
C. prove that a local file-backed Compose secret is a bind mount
cd /tmp/l36-compose
printf 'correct-horse-battery-staple\n' > db_password.txt
chmod 600 db_password.txt

cat > compose.yaml <<'EOF'
services:
  demo:
    image: alpine
    command: ["sh","-c","sleep 600"]
    secrets:
      - db_password

secrets:
  db_password:
    file: ./db_password.txt
EOF

docker compose up -d
CID=$(docker compose ps -q demo)

docker inspect -f '{{range .Mounts}}{{println .Type .Source "->" .Destination "RW=" .RW}}{{end}}' "$CID"
docker exec "$CID" sh -c 'ls -l /run/secrets/db_password; cat /run/secrets/db_password'
D. observe the environment metadata surface
docker run -d --name l36-proc \
  -e API_TOKEN=visible-in-config \
  alpine sleep 600

docker inspect -f '{{json .Config.Env}}' l36-proc
PID=$(docker inspect -f '{{.State.Pid}}' l36-proc)
sudo sh -c 'tr "\000" "\n" < /proc/'"$PID"'/environ | grep "^API_TOKEN="'

10. Check yourself

  • docker run --env-file is parsed by Docker CLI. It is not a secret-file mount.
  • Runtime env values travel through Config.Env, then into OCI process.env, then into the process environment.
  • Compose .env mainly feeds Compose interpolation. Service env_file: feeds the service runtime environment.
  • Local Compose file secrets are read-only bind mounts.
  • Swarm secrets use a worker-side tmpfs staging path.
  • _FILE is application or entrypoint code, not a Docker feature.
