Part 7 · Orchestration · Lesson 42

docker compose

Compose is easiest to understand if you stop treating it as a runtime. It is a client that turns one application model into ordinary Docker Engine objects, then keeps those objects aligned with the model.

CORE
one sentence first

Compose ends at the Docker Engine API. It loads configuration, decides what Docker resources should exist, and asks dockerd to create/start/remove them. The normal Lesson 23 runtime chain begins after that.

1. See the complete pipeline before the details

docker compose upDocker CLI finds and launches the Compose plugin.
↓ Compose files + environment + CLI options
Compose + compose-goLoad, interpolate, merge, normalize, and validate the files into one resolved Project.
↓ desired application model
ComposeDerive project/resource identity, discover existing Compose-labeled Engine objects, and decide reuse/create/recreate/scale.
↓ Engine API requests
dockerdCreate/reuse Docker networks, volumes, and containers.
↓ container IDs + Engine state
ComposeStart service containers in dependency order and wait only for explicit dependency conditions.
↓ ContainerStart
ordinary runtime pathdockerd → containerd → shim → runc → Linux kernel.
important boundary

Compose does not create OCI runtime bundles, call runc directly, implement namespaces, or keep a second kind of “Compose container.” The final resources are ordinary Docker objects.

Anchors: Docker CLI 29.6.2 · cli-plugins/manager/manager.go::PluginRunCommand; Compose v5.1.4 · pkg/compose/up.go::Up

2. One application: YAML → resolved model → Docker objects

We will use only this application for the entire lesson:

name: shop
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD:-devpass}
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
    volumes: [dbdata:/var/lib/postgresql/data]
    networks: [appnet]

  web:
    image: nginx:1.27-alpine
    environment:
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy
    networks: [appnet]

volumes:
  dbdata: {}
networks:
  appnet: {}

After loading, Compose is no longer reasoning about individual YAML lines. compose-go has produced one types.Project containing the resolved application:

Project
├── Name: "shop"
├── Services: web, db
├── Networks: appnet
└── Volumes: dbdata

That model is desired state. Compose must now turn it into Engine resources such as:

Docker network  shop_appnet
Docker volume   shop_dbdata
Docker container shop-db-1
Docker container shop-web-1

Anchor: compose-go v2.11.0 · types/project.go::Project

3. How the final Project is produced

The loader has four jobs that matter for this lesson:

  1. Choose input files. One or more Compose files are applied in order using the loader's merge/override rules.
  2. Interpolate values. ${DB_PASSWORD:-devpass} is resolved before the final service model is used. An interpolation value is not automatically a container environment variable; it only affects fields that reference it.
  3. Normalize and validate. Shorthand/default forms become the canonical model and invalid combinations are rejected.
  4. Choose the project name. Important precedence is explicit -p/--project-name → COMPOSE_PROJECT_NAME → Compose name: → normalized working-directory name.

Our model therefore has project name shop. For non-external networks/volumes without an explicit resource name:, compose-go derives:

<project>_<resource-key>
shop_appnet
shop_dbdata

Default container names use project, service, and replica number:

shop-db-1
shop-web-1
shop-web-2   # if web is scaled to 2

The implicit default network

If a service has neither its own network_mode nor an explicit nonempty networks list, compose-go attaches that service to logical network default. The project-level default network is inserted only when at least one service needs it, producing a normal Engine network such as shop_default.

correction

Compose does not create an implicit default network unconditionally. The pinned normalizer adds it only when a service actually needs it.

Anchors: compose-go v2.11.0 · cli/options.go::ProjectOptions.LoadProject / withNamePrecedenceLoad; loader/loader.go::LoadWithContext; loader/normalize.go::normalizeNetworks / setNameFromKey

4. A service is not a container

Project.Services["web"] is a recipe plus a desired replica count. The actual Docker containers are the current observed instances of that recipe.

desired web scale = 2
observed web containers = {shop-web-1}
                         ↓
Compose creates one missing replica
                         ↓
observed = {shop-web-1, shop-web-2}

This is why Compose can scale one service to several containers. The convergence code compares the desired scale from the service with the containers it has rediscovered from the Engine.

A fixed container_name: changes the situation: Compose v5.1.4 rejects scale greater than one for that service because several Engine containers cannot all use the same fixed name.

How Compose finds its existing objects

Compose does not need a hidden project database. It marks Engine resources with labels and later queries those labels. Important container labels include:

com.docker.compose.project=shop
com.docker.compose.service=web
com.docker.compose.config-hash=...
com.docker.compose.container-number=1

Networks and volumes also receive project identity plus their logical key:

com.docker.compose.network=appnet
com.docker.compose.volume=dbdata

Later up or down invocations reload the project and ask the Engine for objects matching these Compose labels. That label bridge is what reconnects the client-side model to existing Docker objects.

Anchors: Compose v5.1.4 · pkg/api/labels.go; pkg/compose/containers.go::getContainers/getDefaultFilters; pkg/compose/convergence.go::ensureService/getScale

5. What up really does

The pinned top-level structure is:

Up(...)
├── create / reconcile
└── start

Phase 1: create/reconcile. Compose first ensures project networks and volumes, lists the project's existing containers, then converges each service toward the resolved model.

For our application, the important movement is:

Project.Networks[appnet] → ensure network → Engine NetworkCreate if missing
Project.Volumes[dbdata]  → ensure volume  → Engine VolumeCreate if missing
Project.Services[...]    → compare labeled containers
                         → reuse / recreate / scale / create

When a container must be created, Compose translates the resolved service into ordinary Engine request structures:

ServiceConfig
   ↓ Compose
container.Config
container.HostConfig
network.NetworkingConfig
   ↓ Engine ContainerCreate
dockerd creates the Docker container object

Phase 2: start. Compose then traverses service dependencies and sends Engine ContainerStart requests for the relevant containers.

where Compose stops

After ContainerCreate, NetworkCreate, VolumeCreate, or ContainerStart crosses the API, dockerd owns the server-side operation. Container execution then follows Lesson 23 through containerd, shim, runc, and the kernel.

Anchors: Compose v5.1.4 · pkg/compose/create.go::create/ensureNetworks/ensureProjectVolumes; pkg/compose/convergence.go::createMobyContainer; pkg/compose/start.go::start

6. depends_on: order and readiness are different

Short syntax:

depends_on:
  - db

is normalized by compose-go to a required dependency with condition service_started. Compose already handles that through dependency ordering: start db before web.

do not over-read it

service_started does not mean “PostgreSQL is ready to accept queries.” It is start ordering, not application readiness.

Our example explicitly asks for:

condition: service_healthy

Now Compose actively inspects the dependency's Engine health state and waits until db is healthy before the condition is satisfied. The health-check machinery itself was Lesson 37; Compose is consuming that Engine state.

Anchors: compose-go v2.11.0 · transform/dependson.go::transformDependsOn; Compose v5.1.4 · pkg/compose/dependencies.go::InDependencyOrder; pkg/compose/convergence.go::waitDependencies/shouldWaitForDependency

7. Why running up again can reuse, recreate, or scale

Each invocation loads a fresh desired Project, rediscovers existing Compose-labeled containers, then compares the two.

new Compose files
      ↓
new Project
      ↓
existing labeled Engine containers
      ↓
convergence
      ├── same enough → reuse
      ├── relevant config changed → recreate
      ├── too few replicas → create more
      └── too many replicas → remove excess

The pinned mustRecreate path compares the service configuration hash with com.docker.compose.config-hash, and also considers image and expected network/volume attachment. That is why a meaningful change can replace a container while an unchanged service is reused.

Scaling is the same convergence algorithm, not a separate runtime feature:

docker compose up -d --scale web=2

desired web replicas = 2
existing web replicas = 1
→ create shop-web-2

Anchor: Compose v5.1.4 · pkg/compose/convergence.go::ensureService/mustRecreate/getScale

8. What down removes — and what it keeps

down uses the same project identity in reverse: find the project's Compose-labeled containers, remove services in reverse dependency order, then clean up owned networks and optionally volumes.

resourcedowndown -v
service containersremovedremoved
owned network shop_appnetremovedremoved
owned named volume shop_dbdatakeptremoved
external network/volumekeptkept

The implementation only schedules project-volume removal when the volume-removal option is enabled, and it skips external resources.

correction

Plain docker compose down does not mean “delete everything declared in the file.” Declared named volumes are retained by default.

Anchors: Compose v5.1.4 · pkg/compose/down.go::down/ensureVolumesDown/ensureNetworksDown; pkg/compose/dependencies.go::InReverseDependencyOrder

inspect it yourself · one short experiment

Use the same compose.yaml from section 2.

# See the resolved model first.
docker compose config

# Create the Engine objects.
docker compose up -d

docker network inspect shop_appnet --format '{{json .Labels}}'
docker volume inspect shop_dbdata --format '{{json .Labels}}'

WEB=$(docker compose ps -q web)
docker inspect "$WEB" --format '{{json .Config.Labels}}'

# Prove service != container.
docker compose up -d --scale web=2
docker compose ps web

# Prove plain down keeps the named volume.
docker compose down
docker volume inspect shop_dbdata --format '{{.Name}} still exists'

# Explicitly remove it.
docker compose up -d
docker compose down -v

Watch for com.docker.compose.project, .service, .network, .volume, and .container-number. Those labels make the internal model visible on ordinary Docker objects.

9. Keep these six facts

  1. Compose is not a runtime. It is a client-side loader/reconciler over the Engine API.
  2. YAML becomes one resolved Project. Interpolation, file merging, defaults, validation, and project naming happen before resource reconciliation.
  3. A service is desired configuration, not a container. One service can converge to multiple Engine containers.
  4. Labels connect invocations. Compose reloads the model and rediscovers ordinary Engine objects using com.docker.compose.* metadata.
  5. depends_on start order is not readiness. service_healthy is the explicit health gate.
  6. up reconciles; down cleans owned runtime objects. Plain down retains declared named volumes.

Check yourself

  1. What object does compose-go produce from the Compose files?
  2. Why is web not the same thing as shop-web-1?
  3. How does a later Compose process find the project's existing containers?
  4. What does short depends_on: [db] guarantee?
  5. Why can a second up recreate a container instead of duplicating it?
  6. Does plain down remove shop_dbdata?
  7. At what exact conceptual boundary does Compose stop?
Answers
  1. A resolved compose-go types.Project.
  2. web is desired service configuration; shop-web-1 is one concrete Engine container instance satisfying it.
  3. By querying ordinary Engine resources using Compose identity labels such as com.docker.compose.project and service/config metadata.
  4. Dependency start ordering, not application readiness.
  5. Compose reloads desired state, rediscovers existing objects, and convergence compares config/image/network/volume expectations to decide reuse versus replacement.
  6. No. The named project volume is kept unless volume removal is explicitly requested, e.g. down -v.
  7. At the Docker Engine API. From there dockerd and the ordinary runtime stack own the actual Docker/container execution work.
