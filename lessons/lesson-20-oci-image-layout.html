The OCI image layout: an image as files on disk

Lessons 17–19 defined the documents — layers, configs, manifests, indexes. This is where they physically live: a portable directory anyone's tools can read, and it's simpler than you'd guess.

The idea in one sentence

An image on disk is three things: a version marker, an index.json entry point, and a blobs/ folder where every document and layer is a file named by its own hash.

1 Start here

Where do all those documents actually live?

Plain version: everything you've learned about images is a JSON or a tar — this lesson is just "which files, in which folders."

You now know the pieces of an image: layer tars (Lesson 17), a config, a manifest (Lesson 18), maybe an index (Lesson 19). The OCI image layout is the standard directory that holds them as files, so any tool can read or write an image without a running daemon. It's what docker save (in OCI mode), skopeo copy oci:…, and docker buildx --output type=oci produce, and it's conceptually how a registry stores things too.

2 The structure

Three things in the directory

Plain version: a marker file, one entry-point file, and a folder of hash-named blobs. That's the whole format.

From image-layout.md, a layout directory contains exactly three things: an oci-layout file (a tiny marker with an imageLayoutVersion, saying "this directory is an OCI layout"); an index.json file (the entry point — an image index, in the Lesson 19 sense, pointing at the top manifest or index by digest); and a blobs/ directory holding every blob.

myimage/ ├── oci-layout # { "imageLayoutVersion": "1.0.0" } — the marker ├── index.json # the entry point: points at the top manifest by digest └── blobs/sha256/ # everything else, each file named by its digest hex ├── 3588d0… # the manifest (a JSON blob) ├── 4b0bc1… # the config (a JSON blob) ├── 796832… # layer 0 tar (gzipped) └── afff39… # layer 1 tar (gzipped)
3 The trick

The digest is the filename

Plain version: every blob's filename is its own sha256. So you can find any blob by its digest, and verify it by re-hashing the file.

Here's the one elegant idea that makes the whole layout work. Every blob in blobs/sha256/ is named by its content hash — the file blobs/sha256/afff39… contains exactly the bytes whose sha256 is afff39…. The spec is explicit: the content of blobs/<alg>/<encoded> MUST match the digest <alg>:<encoded>. So a descriptor's digest (Lesson 18) is literally a file path into this folder, and you can verify any blob just by running shasum on it and checking the name matches.

That turns "read an image" into a simple walk: open index.json → it gives a manifest digest → open blobs/sha256/<that> → it gives config and layer digests → open those blobs. The entry point plus content-addressed files is the entire navigation system.

Why one flat blobs folder is clever

Because the filename is the content hash, a blob is stored once no matter how many manifests point at it. A base layer shared by ten images is a single file in blobs/sha256/. The dedup we kept mentioning is, physically, just "same content → same filename → same file." And nothing distinguishes a manifest blob from a config blob from a layer blob in the folder — they're all just hash-named files; what they are is determined by the mediaType in the descriptor that points to them.

This is the same idea as containerd's content store — and the registry. containerd keeps its own internal content store (its blobs live under /var/lib/containerd/…/content, addressed by digest); the OCI image layout is the portable, standardized version you can tar up and hand to another tool. And a registry (Lesson 39) is essentially this same content-addressed blob store exposed over HTTP. Learn the layout once and you understand all three.

Check yourself

  • The OCI image layout is a portable directory holding an image as files — no daemon needed.
  • Three parts: oci-layout (version marker), index.json (entry point), blobs/<alg>/ (the blobs).
  • Every blob — manifest, config, layer tar — is one file named by its own digest; the content must hash to the filename.
  • Reading an image = walk from index.json, resolving each digest to a file path in blobs/.
  • Shared blobs are stored once (same content → same filename), and a blob's kind comes from the mediaType of the descriptor pointing at it.
  • The same content-addressed idea underlies containerd's content store and the registry (Lesson 39).
Where this corrects the familiar version

People picture an image as an opaque bundle. On disk it's the opposite of opaque: a directory of plain, hash-named files you can cat, jq, and sha256sum by hand, all reachable from one index.json. And note what's not here — no tags. A tag is registry/daemon metadata, not part of the on-disk content (a layout may record a ref name in an annotation, but the blobs themselves are pure content). The image's real identity is always the digest, which here is quite literally the path to the bytes.

Where we are

Summary

The OCI image layout stores an image as a portable directory of three parts: an oci-layout version marker, an index.json entry point (an image index pointing at the top manifest by digest), and a blobs/<alg>/ folder where every document and layer is a single file named by its own content hash — the spec requires the bytes to match the filename. Reading an image is a walk from index.json, turning each descriptor's digest into a file path; identical blobs are naturally stored once. This same content-addressed scheme is what containerd's content store and the registry both use. That completes the "images at rest" picture.
