Part 8 · Security capstone · Lesson 44

Docker security boundary

Rootless Docker, authorization plugins, and why daemon-socket access is really a question about the authority of dockerd.

CORE · FINAL
one sentence first

The most important Docker security question is not “is the container process root?” but “who can command dockerd, and what is that daemon itself allowed to do on the host?”

This final lesson merges the former planned Lessons 44–46 because they are one causal story. Lessons 7, 11–13, and 37 already taught restrictions on a container process. Here we move one level outward: the Docker API and the daemon that receives it.

1. See the complete security pipeline first

Everything in this lesson is about one of three boundaries:

boundarywhat it limits
workload sandboxwhat the container process may do: namespaces, capabilities, seccomp, LSMs, cgroups, non-root user
API authorizationwhich Engine requests a client is allowed to ask dockerd to perform
daemon privilegewhat dockerd itself can do on the host: rootful versus rootless
do not mix these

Running the application as UID 1000 inside a container does not make the daemon rootless. An authorization plugin does not make the daemon unprivileged. Rootless mode changes the daemon's outer authority.

2. Rootless Docker moves the daemon inside an unprivileged boundary

A normal Linux Docker installation starts dockerd as host root. Rootless mode changes that starting point.

In Docker Engine 29.6.2, the rootless launcher refuses to run as UID 0. It then re-executes itself through RootlessKit. RootlessKit creates unprivileged user, mount, and network namespaces. Only inside those namespaces does the script finally exec dockerd.

ordinary host user
      ↓ starts user service
dockerd-rootless.sh
      ↓ RootlessKit creates user + mount + network namespaces
rootless namespace environment
      ↓ exec
     dockerd
      ↓ normal Docker runtime work
containerd → shim → runc → kernel

The user namespace is the load-bearing piece. Reuse the model from Lesson 7: credentials that look privileged inside that namespace map to an unprivileged host user/subordinate-ID range outside it. The setup tool therefore checks newuidmap/newgidmap and entries in /etc/subuid and /etc/subgid.

source microscope

The pinned launcher states its intent directly:

# Re-exec the script via RootlessKit, so as to create
# unprivileged {user,mount,network} namespaces.
...
exec $rootlesskit ... "$0" "$@"
...
exec "$dockerd" "$@"

The important ordering is namespace first → daemon second. That is what makes the daemon rootless.

Rootless is not userns-remap

userns-remap changes the user namespace used for containers while the Docker daemon itself remains host-root. Rootless mode places the daemon and its containers under an unprivileged user's namespace boundary. That is the security difference.

Rootless is not merely “USER 1000”

Lesson 37 changed the credentials of the process inside one container. Rootless changes the privilege context of the infrastructure that creates containers. You can still run a root-looking process inside a rootless container; its outer kernel authority is constrained by the daemon's user-namespace boundary.

Where does the client connect?

The rootless setup installs a per-user systemd service that runs dockerd-rootless.sh. It also creates a Docker CLI context pointing at:

unix://$XDG_RUNTIME_DIR/docker.sock

On a typical systemd login this is under /run/user/$UID/, rather than the rootful daemon's usual system socket.

why rootless has different networking/resource behavior

An unprivileged daemon cannot simply perform every host-root networking, port, mount, or cgroup operation. RootlessKit and delegated kernel features bridge some of those gaps. The limitations are a consequence of the security boundary, not evidence that rootless secretly becomes host root.

Pinned anchors: Docker Engine 29.6.2 · contrib/dockerd-rootless.sh (parent/child RootlessKit re-exec, final dockerd exec); contrib/dockerd-rootless-setuptool.sh (subuid/subgid checks, user service, rootless CLI context).

3. Why the Docker socket is an authority endpoint

A Unix socket is only a transport. The danger comes from what is listening behind it.

For a Unix listener, Docker Engine 29.6.2 resolves the configured socket group and creates the Unix socket with that group. A local user who can open that socket can send Engine API requests to the daemon.

Now look at the container-create path. The Engine handler decodes the incoming request into Config, HostConfig, and networking configuration. HostConfig contains host-sensitive controls including:

Binds       []string
Privileged  bool
CapAdd      []string
PidMode     ...
UsernsMode  ...
SecurityOpt []string
Mounts      []mount.Mount

So an API client is not merely asking an isolated helper to “run this program.” It can ask the daemon to create containers with host mounts, changed namespace modes, added capabilities, or privileged mode. The daemon is the component that tries to realize those requests.

the phrase “docker.sock = root” made precise

For a rootful daemon, unrestricted control of its Engine API is effectively root-level Docker authority because the client can instruct a host-root daemon to perform host-affecting operations. The socket file itself is not magical; the authority comes from the privileged daemon behind it.

This is why membership in a group that can access the rootful Docker socket is a security decision, not ordinary application access.

What changes with a rootless socket?

The rootless socket is still powerful. A client controlling it can control that user's Docker daemon and the containers/images/networks/resources that daemon can reach. But the daemon is no longer host root, so the outer damage boundary is the host authority available to that unprivileged user plus whatever capabilities the host explicitly delegates.

4. Authorization plugins put a policy gate in front of Engine handlers

Socket permissions answer a coarse question: may this client reach the daemon? Sometimes that is not enough. You may want a client to call some API operations but not others.

Docker's authorization middleware accepts a configured list of authorization plugins. If the list is empty, the middleware simply calls the normal Engine handler. If plugins exist, the request path becomes:

client HTTP request
      ↓
Docker API router
      ↓
AuthZRequest(plugin 1)
      ↓ allow
AuthZRequest(plugin 2)
      ↓ allow
actual Engine handler
      ↓ response
AuthZResponse(plugin 1, plugin 2, ...)
      ↓
client

The request object given to a plugin includes the HTTP method, URI, selected headers, and—when applicable—a bounded JSON body. On TLS connections, the middleware also uses the first peer certificate's Common Name as the user identity supplied to authorization.

all configured plugins must allow

AuthZRequest loops through the configured plugins. A plugin error stops the operation; an Allow=false result denies it. The pinned source explicitly states that when several authorization plugins are configured, allow/deny is the logical AND of their decisions.

After an allowed Engine handler succeeds, AuthZResponse gives the plugins the response status/headers and eligible body content and can deny release of the response. That is a second policy checkpoint, not another container runtime step.

What is the plugin here?

The authorization package defines a small interface: AuthZRequest and AuthZResponse. The adapter resolves the configured Docker plugin and calls the plugin endpoints named for request and response authorization. In other words, dockerd owns the API pipeline, but the policy decision is delegated to plugin code.

where authz stops

An authorization plugin can stop a request from reaching a privileged handler. It does not reduce dockerd's UID, move the daemon into a user namespace, or make an allowed operation less privileged. Rootless mode and authorization solve different problems.

Pinned anchors: Docker Engine 29.6.2 · pkg/authorization/middleware.go::Middleware.WrapHandler; pkg/authorization/authz.go::Ctx.AuthZRequest / AuthZResponse; pkg/authorization/plugin.go::Plugin / authorizationPlugin.

5. Put the three security layers together

Suppose a CI process is allowed to use Docker. Ask three separate questions in this order:

questionmechanismif it fails
Can the CI process reach the Engine API?Unix-socket permissions, context/transport, TLS for remote accessit gets no daemon access
If it can reach the API, which operations may it call?authorization plugins, if configuredspecific API requests can be denied
If a request is allowed, how much host power does the daemon possess?rootful versus rootless daemonthis determines the outer authority available to realize the request
Once a container process exists, what may that process do?user, namespaces, caps, seccomp, LSMs, cgroupsthe workload is constrained inside its runtime sandbox
common wrong model

“My container runs as non-root, therefore giving it /var/run/docker.sock is safe.” No. The process may be non-root inside its own container, yet the socket gives it a channel to command a separate rootful daemon. The API boundary bypasses the importance of that process's local UID for daemon operations.

better model

Security follows authority across component boundaries. Container credentials describe the workload. Socket permissions/authz describe access to the daemon. Rootless/rootful describes the daemon's own host authority.

6. Inspect it yourself

safe Linux inspection

These commands observe the boundaries; they do not deliberately escape a container or modify host security policy.

# Which daemon endpoint is this CLI targeting?
docker context show
docker context inspect "$(docker context show)"

# Rootful Unix-socket ownership/permissions, if that socket exists.
stat -Lc '%A %U %G %n' /var/run/docker.sock 2>/dev/null || true
getent group docker 2>/dev/null || true

# See whether the Engine reports rootless among its security options.
docker info --format '{{json .SecurityOptions}}'

# On a rootless installation: inspect its user service and socket.
systemctl --user status docker --no-pager 2>/dev/null || true
echo "$XDG_RUNTIME_DIR"
stat -Lc '%A %U %G %n' "$XDG_RUNTIME_DIR/docker.sock" 2>/dev/null || true

# Observe subordinate ID ranges used to build the user-namespace mapping.
grep "^$(id -un):" /etc/subuid /etc/subgid 2>/dev/null || true

# Find a dockerd owned by your user and inspect the kernel UID/GID map.
pid=$(pgrep -u "$(id -u)" -x dockerd | head -1)
[ -n "$pid" ] && cat /proc/$pid/uid_map
[ -n "$pid" ] && cat /proc/$pid/gid_map

# If authorization plugins are configured in daemon.json, observe the setting.
grep -n 'authorization-plugins' /etc/docker/daemon.json 2>/dev/null || true

On a rootless host, compare the dockerd owner and uid_map with Lesson 7. On a rootful host, compare the system socket's group with the users who are allowed to contact it.

7. Final recap

If you keep only four facts, keep these:

  1. Rootless Docker means dockerd itself starts inside an unprivileged user-namespace environment. It is not the same as running the application as a non-root container user, and it is not the same as rootful userns-remap.
  2. The Docker socket carries Engine API authority. For a rootful daemon, unrestricted API control is effectively root-level Docker authority because the daemon can perform host-affecting operations for the client.
  3. Authorization plugins sit in the Engine API path. They allow/deny requests before handlers and inspect/authorize responses afterward; all configured plugins must allow.
  4. These layers compose rather than replace one another. API access control, daemon privilege, and the container's runtime sandbox protect different boundaries.
course boundary reached

At this point the course has followed Docker from CLI requests through image/build/distribution/orchestration/security mechanisms down to the point where Docker programs Linux kernel primitives. Beyond this boundary, the next subject would be Linux kernel internals rather than Docker internals.
