Every Dockerfile instruction, and what it compiles to

Seventeen instructions look like a lot to memorize — until you see that each does exactly one of three things. Once you know which, every instruction's layer, cache, and runtime behavior follows.

The idea in one sentence

Every Dockerfile instruction does one of three things: add a filesystem operation to the graph, change the image's config, or set a build-time variable — and everything else about it follows from which.

1 Start here

The three kinds of instruction

Plain version: don't memorize seventeen behaviors — memorize three categories, then place each instruction in one.

In the BuildKit frontend (Lesson 25), every instruction is handled by a dispatch* function (dockerfile2llb/convert.go), and each one does exactly one of three things: it adds an LLB op that changes the filesystem (so it produces a layer), it mutates the image config (metadata only — no filesystem layer), or it sets a build-time ARG (affects the build, never the final image). Sort every instruction into one of these buckets and its behavior — does it add a layer? does it bust cache? does it appear at runtime? — becomes predictable.

Parser directives are not instructions. # syntax=, # escape=, and # check= alter how the Dockerfile frontend parses or validates the file. They must appear at the top, create no layer, and do not appear as build steps. They sit above the three instruction categories rather than inside them.
2 Kind one

Graph-building instructions (these make layers)

Plain version: these five actually change the filesystem — they're the ones that add content and cost size.

The instructions that emit LLB filesystem ops: FROM resolves a base image (a SourceOp) and starts a stage; RUN runs a command in a container (an ExecOp); COPY and ADD copy files in (a FileOp); and WORKDIR is a hybrid — it sets the config's working directory and creates that directory if missing (a small FileOp mkdir). These are the only instructions that change what's on disk.

Two distinctions worth nailing here. COPY vs ADD: COPY is a plain file copy from the build context (or from another stage with --from); ADD does the same plus fetches remote URLs and auto-extracts local tar archives. Because that extra behavior is surprising, the guidance is to prefer COPY unless you specifically need the extraction. RUN mounts: as Lesson 25 showed, RUN --mount=type=cache and --mount=type=secret attach to that one ExecOp.

3 Kind two

Config-only instructions (no layer, pure metadata)

Plain version: these just set fields in the image config from Lesson 18 — they add a history entry but no filesystem layer.

The largest group mutates the image config and produces no filesystem change: ENV, USER, EXPOSE, ENTRYPOINT, CMD, LABEL, HEALTHCHECK, VOLUME, STOPSIGNAL, SHELL, ONBUILD, and the deprecated MAINTAINER. They set exactly the config fields you met in Lesson 18. A few carry real subtlety:

ENTRYPOINT vs CMD: ENTRYPOINT is the fixed command; CMD supplies default arguments appended to it (or, if there's no ENTRYPOINT, CMD is the default command itself). So ENTRYPOINT ["nginx"] + CMD ["-g","daemon off;"] runs nginx -g "daemon off;", and docker run img --version replaces just the CMD part. ENV both persists into the final image and is visible to later build instructions. SHELL changes the shell used for shell-form commands. ONBUILD stores triggers that fire only when your image is later used as a base. The rest — EXPOSE, VOLUME, LABEL, HEALTHCHECK, STOPSIGNAL — are pure declarations read at runtime.

4 Kind three

ARG: the build-time-only variable

Plain version: ARG is a variable that exists during the build and then vanishes — it never lands in the image, but it does affect caching.

ARG (dispatchArg) is the odd one out: it declares a variable available during the build (settable with --build-arg), but it is not written into the final image config. It's scoped per stage, and an ARG before the first FROM is special (available to FROM lines). Crucially, an ARG's value feeds the cache key of the instructions that use it — change the arg, bust that part of the cache. The contrast to remember: ENV persists into the image (and leaks to runtime); ARG is build-only. But note — ARG values are visible in the build history, so they are not a way to pass secrets; that's what secret mounts (Lesson 25) are for.

5 Cross-cutting

Shell form vs exec form

Plain version: writing a command as a string runs it through a shell; writing it as a JSON array runs it directly. This matters for signals.

Three instructions — RUN, CMD, ENTRYPOINT — accept two forms. Shell form (RUN apt-get update) wraps the command in a shell: /bin/sh -c "…" (or whatever SHELL is set to). Exec form (RUN ["apt-get","update"]) executes the binary directly, with no shell. The difference bites at runtime: with shell form as your entrypoint, your process runs as a child of sh, so it isn't PID 1 and won't receive signals like SIGTERM directly — the source of "my container ignores docker stop." Exec form makes your process PID 1. We'll dig into exactly why in Lesson 28.

Check yourself

  • Every instruction is one of three kinds: graph op (filesystem/layer), config (metadata/no layer), or ARG (build-only).
  • Graph ops: FROM, RUN, COPY, ADD, WORKDIR — the only ones that change disk. ADD also fetches URLs / extracts tars (prefer COPY).
  • Config-only: ENV, ENTRYPOINT, CMD, USER, EXPOSE, VOLUME, LABEL, HEALTHCHECK, STOPSIGNAL, SHELL, ONBUILD, plus deprecated MAINTAINER.
  • ENTRYPOINT = fixed command; CMD = default args appended (or the default command alone).
  • ARG is build-time only, affects the cache key, never enters the image — and isn't safe for secrets.
  • Shell form wraps in /bin/sh -c (not PID 1); exec form (JSON array) runs directly (PID 1, gets signals).
Where this corrects the familiar version

Three common mix-ups. ADD is not "COPY but nicer" — its URL/tar magic is why COPY is preferred. ARG and ENV are not interchangeable — ARG vanishes after the build (and leaks into history, so never a secret), while ENV persists into the running container. And shell-vs-exec form isn't cosmetic — shell form leaves your program as a child of sh, which is the usual reason docker stop seems ignored. Sort each instruction into its kind and these stop being surprises.

Where we are

Summary

Every Dockerfile instruction resolves to one of three effects: a graph op that changes the filesystem (FROM, RUN, COPY, ADD, WORKDIR — the layer-makers), a config mutation that sets image metadata with no layer (ENV, ENTRYPOINT/CMD, USER, EXPOSE, and the rest), or an ARG that lives only during the build and feeds cache keys. Layered on top is the shell-vs-exec form choice for RUN/CMD/ENTRYPOINT, which decides whether your process becomes PID 1. Parser directives sit above those categories, and deprecated MAINTAINER remains only for compatibility. Knowing an instruction's kind predicts its size, cache, and runtime behavior. Next, Lesson 27 uses these to build multi-stage images — the pattern that keeps build tools out of your final image.
