ARG vs ENV & the history leak

Two values may look identical while a build is running, yet one is only a build input and the other becomes a default stored in the finished image. The dangerous part is that neither is a safe place for secrets.

Governing idea

ARG supplies a value to the build. ENV changes the configuration of the image produced by the build.

1 Start with one build

Both values can exist during a RUN — that is why they are easy to confuse

Use one Dockerfile and follow two values all the way through it:

# syntax=docker/dockerfile:1 FROM alpine:3.21 ARG APP_VERSION=dev ENV APP_MODE=production RUN printf 'version=%s mode=%s\n' "$APP_VERSION" "$APP_MODE" \ > /build-info.txt CMD ["sh", "-c", "env | grep '^APP_' || true; cat /build-info.txt"]

During the RUN, both variables are available:

APP_VERSION
Comes from ARG; it is available while this stage is being built.
APP_MODE
Comes from ENV; it is available while the stage is built and is also written into the output image configuration.

After the image is built, the difference appears:

ARG APP_VERSION

It is not automatically supplied as an environment variable when a container starts.

ENV APP_MODE

It is stored in the image configuration, so a new container receives it as a runtime default.

Do not translate that into “ARG leaves no trace.” The value can affect files, installed packages, cache keys, image history, and provenance. It merely does not become a runtime environment default automatically.
2 Three places to track

A value can live in the build state, the output image config, or the metadata trail

Most confusion disappears once you stop asking only “does the variable exist?” and instead ask where it exists.

1

Current build-stage state

Values that Dockerfile instructions can expand and that a later RUN can receive. Both ARG and ENV can enter this state.

2

Finished image configuration

The OCI image config holds runtime defaults such as environment variables, entrypoint, command, user, and working directory. ENV writes here; ordinary ARG does not.

3

History and provenance

The image and build records explain how the artifact was produced. Resolved build arguments can appear here even though they are absent from the runtime environment.

ARG → build-stage value + possible metadata/effects
ENV → build-stage value + image.Config.Env + metadata
3 ARG

ARG is a parameter accepted by the Dockerfile

A Dockerfile declares the name and may provide a default:

ARG APP_VERSION=dev

The caller may replace that default:

docker build --build-arg APP_VERSION=2.4 -t demo:arg .

For this build, the resolved value is 2.4. BuildKit makes it available to later instructions in that stage, so these are valid uses:

RUN echo "$APP_VERSION" LABEL org.example.version="$APP_VERSION" COPY app-$APP_VERSION /app

The last two examples are important: an ARG may not survive as an environment variable, but its effect can survive permanently. It can select a package, choose a base tag, change a label, or cause a value to be written into a file.

The precise boundary

ARG is available to Dockerfile processing and build execution after it is declared in the relevant scope. BuildKit does not automatically append it to the finished image's Config.Env array.

4 ENV

ENV changes both the current build and the future container default

Consider:

ENV APP_MODE=production

BuildKit performs two logically separate updates:

1
Update the current stage
Later instructions and RUN processes can see APP_MODE=production.
2
Update the output image config
The pair is appended or replaced in the OCI image's config.Env array.

The OCI Image Specification defines those entries as defaults used when a container is created. Therefore this image:

FROM alpine:3.21 ENV APP_MODE=production

supplies the value here:

docker run --rm IMAGE sh -c 'echo "$APP_MODE"' production

A runtime option may override the default without changing the image:

docker run --rm -e APP_MODE=debug IMAGE sh -c 'echo "$APP_MODE"' debug
ENV is metadata, not a filesystem file. The instruction changes the image configuration and creates a history entry, but it does not need to create a filesystem diff layer.
5 Deliberate conversion

To make a build argument become a runtime default, copy it into ENV explicitly

This common pattern connects the two mechanisms:

ARG APP_VERSION=dev ENV APP_VERSION=$APP_VERSION

Build with:

docker build --build-arg APP_VERSION=2.4 -t demo:2.4 .

The value travels in a deliberate sequence:

1
CLI supplies 2.4
--build-arg provides a candidate value for the declared ARG APP_VERSION.
2
ARG exposes 2.4 to the stage
Dockerfile expansion can now resolve $APP_VERSION.
3
ENV writes 2.4 into the image config
Future containers receive APP_VERSION=2.4 unless the runtime overrides it.
Correction

--build-arg APP_VERSION=2.4 does not directly edit an ENV instruction. It supplies the ARG; the Dockerfile's ENV APP_VERSION=$APP_VERSION is the separate step that publishes the resolved value into the image.

You can stop here on a first read. Remember: ARG parameterizes the build; ENV publishes a runtime default. The remaining sections explain stage scope, the metadata leak, and the correct secret mechanism.
6 Scope

ARG follows the stage graph — textual position alone is not enough

Before the first FROM

An ARG declared before the first FROM belongs to the global pre-stage scope. Its special job is to parameterize FROM:

ARG ALPINE_VERSION=3.21 FROM alpine:${ALPINE_VERSION}

That global declaration does not automatically make the value available to later instructions inside the stage. Consume it again:

ARG ALPINE_VERSION=3.21 FROM alpine:${ALPINE_VERSION} ARG ALPINE_VERSION RUN echo "$ALPINE_VERSION"

Across stages

A stage created from an earlier named stage inherits that stage's state and declared build arguments. An unrelated stage begins from its own base instead.

FROM alpine:3.21 AS base ARG APP_VERSION=2.4 ENV APP_MODE=production FROM base AS child # APP_VERSION and APP_MODE are inherited through the base relationship RUN echo "$APP_VERSION $APP_MODE" FROM alpine:3.21 AS unrelated # this stage does not descend from "base" RUN echo "$APP_VERSION $APP_MODE"
DeclarationWhere it is available
ARG before first FROMGlobal Dockerfile scope for FROM expansion; redeclare inside a stage to consume it there.
ARG inside a stageThat stage and child stages derived from it.
ENV inside a stageThat stage's later instructions and its output image config; child stages derived from it inherit the config/state.
New unrelated FROMStarts from that selected base image, not from the previous textual stage.

This is the same graph relationship from Lesson 27. A stage does not inherit merely because it appears later in the file.

7 The history leak

“ARG is build-only” does not mean “ARG is secret”

An OCI image is more than filesystem layers. Its configuration blob also contains a history array. Each entry may contain created_by: the command or instruction associated with that build point.

In the pinned BuildKit frontend, handling an ARG creates a history message containing the resolved KEY=value. When BuildKit records a later RUN, it also prefixes the recorded command with declared build arguments and their resolved values.

ARG API_TOKEN RUN curl -H "Authorization: Bearer $API_TOKEN" https://private.example/file

Even when a future container has no API_TOKEN environment variable, the token may still be recoverable from image history or fuller provenance metadata. If the command writes it into a file or output artifact, it can also enter a filesystem layer.

Security correction

Never use “it is only an ARG” as a security claim. ARG controls runtime persistence, not confidentiality. ENV is worse for a secret because it intentionally stores the value in Config.Env, but neither instruction is a secret transport.

MechanismAutomatic places the value may remainRuntime environment
ARGHistory; cache keys for instructions that use it; fuller provenance; plus any file, label, or content produced with it.Not automatic.
ENVimage.Config.Env and history; plus any later build effects.Yes, as a default.
secret mountThe payload is not automatically placed in image config or history; provenance records the secret ID, not its contents.No.
8 Correct secret path

Mount a secret only for the RUN operation that needs it

Pass the secret separately from the Dockerfile and consume it through a BuildKit secret mount:

# Dockerfile RUN --mount=type=secret,id=api_token \ token="$(cat /run/secrets/api_token)" && \ curl -H "Authorization: Bearer $token" https://private.example/file
# build command docker build --secret id=api_token,src=token.txt .

For that one RUN, BuildKit mounts the payload at /run/secrets/api_token. The mount is not part of the resulting root filesystem snapshot, so it is absent from the next build step and from the finished image.

A secret mount prevents automatic persistence, not deliberate leakage. A command can still copy the secret into the image or print it into build logs. The mechanism gives the process temporary access; your command must still handle the value safely.
9 Provenance and one exception

The build request itself may be recorded

BuildKit provenance describes how an artifact was produced. In maximal provenance, external parameters can include build arguments. In minimal mode, BuildKit explicitly removes request entries whose keys begin with build-arg:. This is another reason build arguments are not a secret boundary.

Secret mounts have a deliberately smaller record: BuildKit captures the secret ID and whether it was optional, not the payload.

Predefined proxy arguments

HTTP_PROXY, HTTPS_PROXY, NO_PROXY, and related predefined proxy arguments receive special treatment when supplied without a matching Dockerfile ARG. Docker excludes them from normal history and cache behavior by default. Explicitly declaring or referencing the proxy argument opts back into ordinary Dockerfile argument behavior.

Narrow exception, not a secret system. The proxy special case exists to avoid baking ordinary proxy configuration into images and cache keys. General credentials still belong in secret or SSH mounts.

Check yourself

  • ARG accepts a build parameter; ENV writes an image/runtime default.
  • Both may be visible to later instructions in the current build stage.
  • Only ENV automatically enters the OCI image's config.Env array.
  • An ARG can still leave permanent effects and metadata.
  • ARG X before the first FROM is global for base resolution; consume it again inside a stage.
  • Stage inheritance follows the build graph: a child of a named stage inherits its state; an unrelated FROM does not.
  • Resolved build arguments may appear in image history and fuller provenance.
  • Neither ARG nor ENV is appropriate for secrets; use RUN --mount=type=secret.

Summary

ARG is an input to the build graph. ENV is a mutation of the image configuration as well as the current build environment. The fact that an ARG is absent from a future container's environment does not erase its history, provenance, cache influence, or filesystem effects.
