The shim: how a container outlives the daemon that started it

You can systemctl restart containerd and your containers keep running. That's not luck — it's a specific, deliberate mechanism built out of process detachment and a reconnectable socket. This lesson is that mechanism, top to bottom.

Lesson 2 introduced the shim as "the per-container process that's the real parent." Lesson 4 placed it as the runtime.v2 plugin's output. Now we earn that claim. The organizing question is the one every production operator eventually asks: why doesn't restarting containerd kill my containers? Answering it forces us through everything the shim is and does — and forces me to correct a simplification I made in Lesson 2.

Source-baseline note — containerd 2.2.6 (Docker Engine 29.6.2). Runtime-v2 uses a short-lived start invocation to launch or locate a long-running shim server and return its socket address; containerd then controls it over ttRPC. In this baseline the shim receives legacy flags/environment plus runtime options and writes JSON BootstrapParams containing the protocol/address. containerd 2.3+ replaces that startup exchange with protobuf BootstrapParams/BootstrapResult. Runtime-v2 permits one shim to serve a runtime-defined group; one-shim-per-container is common in Docker, not a universal API rule.
The intuition

The restart problem, and the shape of its only solution

containerd is software. Software gets upgraded and occasionally crashes. On a server running real workloads, it is unacceptable for "upgrade containerd" to mean "kill every container." So containerd has a hard requirement: it must be able to stop and restart without disturbing running containers.

Think about what that demands. A child is not automatically killed merely because its parent exits; the kernel can reparent it. The real failure would be losing the dedicated supervisor that owns the task's stdio, waits for its exit, and preserves its exit status. So containerd must not be the only live supervisor. A separate shim stays with the task, and containerd needs a way to find that shim and resume control after coming back.

Those two requirements — a parent that is not containerd, and a way for containerd to reconnect to it — fully determine the design. That surviving parent is the shim. It detaches from containerd so it can outlive it, and it listens on a stable socket so containerd can find it again. Everything below is just how the source implements those two ideas.

Mechanism 1

Detachment: the shim re-execs itself and cuts the cord to containerd

Step 1 · Explain

Here's the clever part. containerd invokes the shim binary with the start action. That bootstrap path creates or locates the long-running server, returns the server's protocol/address, and exits. The serving shim is therefore independent of the short-lived bootstrap helper. The kernel reparents an orphan to the nearest configured child subreaper, or ultimately PID 1; the exact PPID is not the architectural contract. The contract is that containerd can disappear while the shim server and task continue.

Setpgid: true places the server shim in its own process group. The short-lived start path then returns the bootstrap result and exits, leaving the server independent of that helper. It may be adopted by PID 1 or another configured subreaper; what matters is that its lifetime is not tied to containerd's process lifetime.

containerd, meanwhile, keeps only the address it read from stdout (ttrpc+unix://…). Its relationship to the shim is now a network client, not a parent — which is exactly what lets it disappear and come back.

Correcting Lesson 2 · the source wins

Lesson 2 originally drew the serving shim as a durable child of containerd. That is the wrong invariant. containerd bootstraps or locates the shim and then talks to it over the runtime-v2 socket. The displayed PPID may be PID 1 or another subreaper depending on the host, but it must not be used to infer the control API relationship.

Mechanism 2

Reconnection: a socket address you can recompute from scratch

Step 1 · Explain

Detachment solves “survive.” Now solve “reconnect.” The socket address is deterministic. containerd hashes its socket root, namespace, and the runtime's grouping key. With the default per-container grouping the key is the container ID; a runtime may group multiple containers behind one shim and use a shared key. Same inputs produce the same address, so containerd can dial the surviving shim again.

Step 2 · The source
The part that does the job

The address is derived from socketRoot / namespace / grouping-key and then hashed. In Docker's common configuration the grouping key is the container ID, so the familiar result is effectively sha256(namespace/id). The transport over that Unix socket is ttRPC, a compact RPC protocol suited to long-lived shim services. Runtime-v2 permits one shim per container or one shim for a defined group.

Mechanism 3

Why it must stay resident: parent duties + the control API

Step 1 · Explain

We now know the shim survives and can be re-found. But why does it need to keep running at all, rather than exiting like runc does? Two reasons, both tied to being the container's parent.

First, a parent process owns its child's standard input/output and is the one the kernel notifies when the child dies. The shim holds the container's stdio streams (so docker logs and docker attach have something to connect to) and, crucially, it catches and remembers the exit code the instant the container exits — buffering it until someone asks. Second, the shim exposes a small control API over its ttrpc socket so containerd can drive the container's lifecycle: create, start, kill, query state, wait, delete.

Step 2 · The source
The part that does the job

These methods are the shim's reason to exist. Notice the division of labor with Lesson 2: the shim's Create/Start are what actually shell out to the short-lived runc; runc builds the container and exits, but the shim stays to be the parent. And Wait returning p.ExitStatus() is the payoff of residence: because the shim buffers the exit code, a container that dies while containerd is down loses nothing — when containerd reconnects and calls Wait, the shim hands over the exit status it has been holding. No exit event is ever dropped across a daemon restart.

The stdio path, concretely. The container's stdout/stderr aren't wired straight to a file; they pass through the shim, typically via named-pipe FIFOs the daemon opens. That's the plumbing behind docker logs, and it's why logging drivers are a daemon concern — a thread we pick up in Lesson 35, not here.
Putting it together

What actually happens on systemctl restart containerd

before: adopter/subreaper → shim → your container containerd ←ttRPC→ shim restart: containerd exits ✗ shim keeps running, owns task wait/I/O state container untouched — the serving shim never exited after: containerd restarts → derive the same group socket → re-dial → resume control

The container never noticed. Its supervising shim and socket remained alive while containerd restarted. containerd derives the same group socket and resumes the RPC conversation.

Step 4 · Inspect it yourself

Three checks: show that the container process is supervised by the shim, record the shim's actual adopter without assuming it must be PID 1, then watch the task and shim survive a containerd restart.

Where we are

Summary

The shim exists to satisfy one requirement — containers must survive a containerd restart. In the pinned containerd 2.2.6 baseline, a short-lived start path bootstraps or locates an independent shim server and returns JSON BootstrapParams; containerd 2.3+ uses a protobuf bootstrap protocol. The serving shim stays reconnectable through a deterministic socket derived from the namespace and runtime grouping key, and stays resident to own task I/O, wait state, exit status, and the ttRPC Task API. Docker commonly uses one runc-v2 shim per container, while runtime-v2 permits grouped shims. runc performs the OCI operations and exits; the shim endures.
