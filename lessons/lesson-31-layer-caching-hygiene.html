Layer caching & hygiene

A Docker build is a chain of filesystem states. Each instruction receives one state and produces the next. BuildKit’s cache may reuse a previously produced next state; image layers record the filesystem change between those states.

The one relationship this lesson builds

instruction + starting filesystem state → resulting filesystem state

Why the earlier versions were hard: they introduced cache keys, layer cleanup, and cache mounts as separate rules before showing the object they all act on. The missing foundation is the chain of filesystem states. We will build that first, then derive every rule from it.

1 Before cache: what one build instruction does

Every filesystem instruction transforms one state into another

Start with a base image. It gives the build an initial root filesystem. Call that state S0.

FROM alpine:3.21 COPY deps.txt /app/deps.txt RUN install-dependencies COPY src/ /app/src/ RUN build-application

Ignore caching for a moment. Follow only the filesystem:

S0
Base filesystemFiles supplied by alpine:3.21.
COPY deps.txttakes S0, produces S1
S1
Base + dependency file/app/deps.txt now exists.
RUN install-dependenciestakes S1, produces S2
S2
Dependencies installedThe installed files are now part of the root filesystem.
COPY src/takes S2, produces S3
S3
Application source addedThe source tree is now present.
RUN build-applicationtakes S3, produces S4
S4
Finished filesystemThis becomes the final image root filesystem.

The crucial relationship is not “line 2 comes after line 1.” It is:

operation O receives state Sbefore and produces state Safter

Each later operation receives the state produced by the previous operation. That dependency is why a change can propagate forward.

Source anchor. BuildKit models these as graph operations with input dependencies. The cache-key structure in moby/buildkit v0.31.1 · solver/cachekey.go connects an operation to the cache identities of the states it reads.
2 Now add the cache

The cache remembers a solved state transition

When BuildKit performs an operation, it can remember this fact:

operationRUN install-dependencies
+
starting stateS1
→
saved resultS2

On the next build, BuildKit reaches the same operation. It asks two questions:

Is the operation the same?
Same command, environment, working directory, user, mounts, platform details, and other execution settings.
Is the starting state the same?
The filesystem arriving from earlier operations has the same cache identity.

If both answers are yes, BuildKit returns the saved S2. The command does not run. That is a cache hit.

If either answer is no, BuildKit performs the operation and produces a new result state.

Memory rule

BuildKit does not cache “line 4.” It caches “this operation, starting from this input state, produced this output state.”

3 Why a change propagates forward

A later instruction misses because the state entering it changed

Use this order:

COPY deps.txt . RUN install-dependencies COPY src/ . RUN build-application

Nothing changed

OperationStarting stateResult
COPY deps.txtSame base and same selected fileReuse S1
RUN installReceives the same S1Reuse S2
COPY srcSame S2 and same source filesReuse S3
RUN buildReceives the same S3Reuse S4

Only src/app.c changed

OperationWhat BuildKit seesResult
COPY deps.txtIts selected input did not changeReuse S1
RUN installIt still receives the same S1Reuse S2
COPY srcSelected source content changedProduce new S3′
RUN buildIts command is unchanged, but it now receives S3′ instead of S3Produce new S4′

The last RUN misses even though its command text did not change. Its starting filesystem state changed.

Correction to the beginner shortcut

“When one Dockerfile line changes, every line below it is invalidated” describes a common visible result, but not the mechanism. Each later operation is checked separately. It misses when its own operation definition or one of its input dependencies changed.

4 What counts as an input

COPY and RUN receive different kinds of input

COPY: selected client files are inputs

For:

COPY deps.txt /app/deps.txt

BuildKit computes a content identity for the selected source. The source path, contents, permissions, ownership, symlink target, and other relevant metadata can affect it. Ordinary modification time is deliberately omitted from the selected v1 checksum fields.

Changes the COPY input

Editing deps.txt, changing its executable bit, changing ownership represented in the source, or changing a symlink target.

Does not normally change it alone

Running touch deps.txt without changing the file contents or other relevant metadata.

Changing an unrelated file is irrelevant when that file is outside the source selected by this COPY.

RUN: the execution request and incoming state are inputs

For:

RUN gcc source.c -o app

BuildKit’s execution cache description includes the command and execution settings, plus the dependency state mounted as the operation’s root filesystem. Important settings include environment, working directory, user, mounts, network mode, security mode, and platform.

Source anchors. solver/llbsolver/ops/file.go assigns content-hash functions to file-operation dependencies. cache/contenthash/filehash.go defines the selected file checksum fields. solver/llbsolver/ops/exec.go · ExecOp.CacheMap constructs the execution-operation cache description and its dependencies.

The network is not an automatic input

RUN curl -o /tmp/tool.tar.gz https://example.com/latest.tar.gz

If the operation definition and its declared input state still match, BuildKit can reuse the old result. It does not normally contact the URL merely to ask whether the remote bytes changed.

That is why moving names such as latest.tar.gz are bad reproducible-build inputs. Prefer a pinned version, digest, release URL, or verified checksum.

Forcing execution is different from defining better inputs

--no-cache

Do not reuse ordinary operation-result cache entries for this build. The operations execute again.

--no-cache-filter STAGE

With Buildx, invalidate the named stage while allowing unrelated stages to keep using cache.

Neither option makes a moving remote resource reproducible. They only control whether BuildKit may reuse a previous result. Reproducibility still requires an immutable or verified external input.

5 Derive the ordering rule

Put stable inputs before frequently changing inputs

Now the common Dockerfile recommendation follows directly from the state chain.

Poor ordering

COPY . . RUN npm ci RUN npm run build

Any application-source edit changes the broad COPY . . result. Therefore npm ci receives a different starting state and cannot reuse its previous result.

Better ordering

COPY package.json package-lock.json ./ RUN npm ci COPY . . RUN npm run build

Application edits occur after dependency installation. As long as the package manifests do not change, the npm ci operation keeps receiving the same starting state and can remain cached.

The reason—not merely the rule

Instruction order controls which earlier filesystem states are dependencies of expensive later work.

Second half: image hygiene

The cache decides whether to reuse a state transition. A layer records the filesystem change produced by a transition that becomes part of the image.

6 Connect states to image layers

A layer records the difference between the starting and resulting states

Return to one operation:

Sbefore -- operation --> Safter

For a filesystem-producing image operation, the image needs the change that turns Sbefore into Safter. That change is the layer changeset.

starting stateS0
RUN creates /tmp/blobfilesystem change Δ1
result stateS1

Cache and layer are therefore different:

MechanismQuestion answered
Build cacheCan BuildKit reuse a state it produced before instead of executing the operation?
Image layerWhat filesystem changes must be applied to transform the parent state into this image state?

A cached operation may supply a previously created layer/result without executing again. The concepts are connected, but they are not the same object.

7 Why deleting later does not shrink the image

Each operation can only add a new changeset; it cannot rewrite an old one

Consider three operations:

RUN curl -o /tmp/tool.tar.gz https://example.com/tool.tar.gz RUN tar -xf /tmp/tool.tar.gz -C /usr/local RUN rm /tmp/tool.tar.gz

Follow the states and layers:

Operation 1
S0 → S1/tmp/tool.tar.gz exists in S1. Layer Δ1 contains the archive bytes.
Operation 2
S1 → S2The extracted program files are added. The archive still exists.
Operation 3
S2 → S3The final state no longer shows the archive. Layer Δ3 records a whiteout hiding the parent path.

The final merged filesystem shows no archive. But Δ1 is an immutable earlier layer blob, so its bytes still exist in the image.

Security consequence

Deleting a secret in a later RUN does not erase it from an earlier layer. Anyone who obtains the image can inspect the earlier layer blob.

The OCI Image Specification defines deletion from a parent layer using a .wh.<name> whiteout. A later changeset hides the path; it does not rewrite the parent blob. opencontainers/image-spec v1.1.1 · layer.md

8 Why same-RUN cleanup works

Only the final state of that operation is committed as its filesystem change

RUN curl -o /tmp/tool.tar.gz https://example.com/tool.tar.gz \ && tar -xf /tmp/tool.tar.gz -C /usr/local \ && rm /tmp/tool.tar.gz

During the command, the temporary archive exists. But BuildKit commits the operation’s root-filesystem result after the complete command finishes.

Before RUNS0

No archive; program not installed.

→
After complete RUNS1

Program installed; temporary archive absent.

The changeset needed to transform S0 into S1 includes the installed files. It does not need to include the temporary archive as an added final path, because that path is absent when the operation finishes.

Layer-hygiene rule

If temporary bytes must never enter an image layer, create, use, and remove them before the same filesystem-producing operation finishes.

This does not mean “put the whole Dockerfile in one giant RUN”

Keep togetherKeep separate
Creation, use, and deletion of one temporary archive, package index, or temporary credential.Independent work whose results can be reused separately, such as dependency installation and application compilation.
The reason is layer hygiene: temporary bytes must be absent from the operation’s final state.The reason is cache reuse: a later application edit should not invalidate earlier stable work.
9 A second cache mechanism: cache mounts

A cache mount is an extra filesystem attached to a RUN, not part of the image root state

Package managers often need downloaded archives again. You want those files to survive for future builds, but you do not want them in the image layer.

RUN --mount=type=cache,target=/root/.cache/pip \ pip install -r requirements.txt

During this operation, there are two writable filesystems:

Root filesystemthe image state

Installed application files written here may become part of the operation’s output state and image layer.

Cache mountseparate BuildKit storage

Downloaded package archives written here can remain for a future execution, but are not automatically part of the image rootfs result.

This produces two very different forms of reuse:

Result cacheCache mount
BuildKit reuses the complete previous output state.The operation runs, but one mounted directory may already contain downloaded files.
On a hit, the command does not execute.The command can execute again and use the retained directory.
Represents a solved transition.Represents auxiliary mutable storage outside the normal rootfs output.

The build must remain correct if the cache mount is empty. BuildKit may garbage-collect it, another builder may not have it, or the build may run for the first time.

Sharing modes

sharedConcurrent builds may use the same cache directory simultaneously.
privateA concurrent writer gets a separate cache instance.
lockedA second writer waits. This is useful for package managers such as APT that require exclusive access.

Inspect it yourself · Part A

Watch state dependencies control cache reuse

Read the output using the state-chain model: the changed application source makes a new state only at the late COPY. Changing deps.txt makes a new early state, so every later dependent operation receives a different starting state.

Inspect it yourself · Part B

Prove that later deletion leaves earlier bytes

The bad image retains the 8 MiB addition in an earlier layer. The good image’s single operation finishes without the temporary file in its final state.

One earlier layer archive contains the real file. A later layer contains only the whiteout that hides it. This is the exact on-disk proof that a later deletion does not erase earlier bytes.

Inspect it yourself · Part C

See a cache mount survive while the RUN executes again

Changing BUST forces a new execution result. The counter still increments because the separate cache mount survives across those executions.

Check yourself

  • A Dockerfile filesystem instruction receives a starting state and produces a result state.
  • The normal cache remembers a solved mapping: operation + starting state → result state.
  • A later operation misses when its own definition changes or when a state/file dependency it reads changes; --no-cache can force execution but does not improve the identity of external inputs.
  • Put stable inputs before frequently changing inputs so expensive early states remain reusable.
  • An image layer records the filesystem difference between two image states; it is not the same thing as the build cache.
  • A later deletion adds a whiteout and does not rewrite an earlier layer blob.
  • Remove temporary bytes before the same operation ends if they must never enter its changeset.
  • A cache mount is separate mutable BuildKit storage attached to a RUN; the RUN may execute while reusing that directory.

→ Where we are

Summary

BuildKit sees a build as dependent state transformations. Its ordinary cache can reuse a previously solved transformation. Image layers are the immutable changesets that reconstruct the resulting image states. Good Dockerfiles exploit both facts: they put stable work early for cache reuse, and they remove temporary bytes before the creating operation commits. Cache mounts solve a different problem by retaining reusable downloads outside the image root filesystem.
