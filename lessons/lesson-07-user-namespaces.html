User namespaces: turning "root" into a harmless number

One idea, built slowly: a user namespace is a translator for ID numbers. We'll follow a single example — container root becoming host user 1000 — from the plain idea, to the exact table that does it, to how Docker switches it on.

Let's start with a question that has a surprising answer, and let the whole lesson grow out of it: when a program runs as "root" inside a container, is it also root on your actual machine? Most people assume "no, containers isolate that." The truth is "it depends on one setting, and by default the answer is yes, it really is host root." The user namespace is the setting that changes the answer. Here's the mechanism, one step at a time.

Start here · one experiment

The thing we're trying to control

Forget the theory for a second. Run a container as root, and have it create a file in a folder shared with the host. Then ask the host: who owns that file?

The file is owned by uid 0 — real host root. The "root" in the container wasn't pretend; it was the genuine article. That is the default, and it's the thing a user namespace exists to fix. By the end of this lesson the same experiment will print 1000 instead of 0, and you'll know exactly why. Let's build up to it.

The core idea

A user namespace is a translator for ID numbers

Linux decides who-can-do-what by comparing numbers. Your user is a number (uid). Files are stamped with an owner number. "Are you allowed to delete this file?" is really "does your number match?" Root is simply the number 0, which the kernel treats as "allowed to do anything."

A user namespace slips a translation table between the inside of a container and the outside world. Inside the namespace, a process can happily be uid 0 — it feels like root, and software that expects root works fine. But the moment that process does something the host can see — creates a file, sends a signal — the kernel looks its inside-number up in the table and uses the outside-number instead.

So with the right table, "uid 0 inside" becomes "uid 1000 outside." Inside the box you're root; outside the box you're an ordinary, powerless user #1000. That single sentence is the entire point of this lesson. Everything else is just: what does the table look like, and who fills it in?

Mechanism 1

The table is just three numbers

Step 1 · Explain

You might imagine the table lists every uid one by one. It doesn't — that would be huge. Instead it describes a whole range with three numbers:

1. where the inside numbers start  ·  2. where the matching outside numbers start  ·  3. how many numbers in a row the rule covers.

Our example table is (inside 0, outside 1000, count 32000). It reads: "inside-uid 0 lines up with outside-uid 1000, and the next 32000 numbers follow along in lockstep." So inside-5 is outside-1005, inside-33 is outside-1033, and so on — just add 1000. Translating any single id is one subtraction and one addition.

If you remember one thing

The mapping is a range: (containerID, hostID, size). Our example (0, 1000, 32000) makes container-root act as host-user-1000. That's the table. The next two mechanisms are just how it gets installed and where the number 1000 comes from.

Mechanism 2

Installing the table: write it into a file, once

Step 1 · Explain

Here's a pleasant surprise: you don't call some elaborate syscall to install the table. The kernel exposes it as a plain text file per process, /proc/<pid>/uid_map. You write your three numbers into it as a line — "0 1000 32000" — and from that instant the kernel applies the translation to that process forever. (There's a matching gid_map for group IDs.) You get exactly one write; after that the table is sealed.

Step 2 · The source

runc prepares that very line of bytes and hands it off to be written into the file:

The part that does the job

The kernel's interface for user-namespace mapping is a file you cat and echo. That's why, in the final inspect step, we can just read a container's /proc/self/uid_map and see its table in plain text. Nothing hidden.

Under the hood · one safety wrinkle (skip on first read) Before an unprivileged process may write the group table (gid_map), the kernel makes it first write the word deny into /proc/<pid>/setgroups. This turns off the setgroups() call inside the namespace, closing a trick where a mapped "root" could use supplementary groups to reach files it shouldn't. runc does this automatically; you'll never touch it. It's here only so the name isn't a mystery if you see it.
Mechanism 3

Where "1000" comes from — and how Docker flips it on

Step 1 · Explain

One question remains: who decides the outside number? You can't just claim any host uids you like — mapping container-root to host-uid-1000 means "I'm allowed to own things as user 1000," which is a privilege. Linux grants each user a block of spare IDs to hand out, listed in the file /etc/subuid. Each line reads name:start:count — "this user may use host IDs from start, count of them, as container IDs."

Docker automates the whole thing with one daemon setting: dockerd --userns-remap=default. On startup it makes a dedicated user called dockremap, reads that user's line in /etc/subuid, and turns it into the mapping table for every container. So the outside number isn't magic — it's whatever block /etc/subuid handed to dockremap.

Step 2 · The source
The whole chain, in our example numbers

/etc/subuid line dockremap:1000:32000  →  Docker builds the table (container 0 → host 1000, count 32000)  →  writes it into config.json as uidMappings  →  runc writes it into /proc/PID/uid_map. Four hops, same three numbers the whole way. (Real Docker installs usually pick a higher block like 165536 instead of 1000; the mechanism is identical.)

Under the hood · rootless helpers (skip on first read) When you (not root) run a container rootless, you can't write a ranged table yourself. Two tiny setuid programs, newuidmap and newgidmap, read /etc/subuid and write the table on your behalf, but only within the block you were granted. runc calls them automatically in the rootless case. That's all they are — the trusted tool that turns your /etc/subuid allowance into a real map.
Payoff

The experiment, resolved

Step 4 · Inspect it yourself

Now read the table straight out of a container, first with the feature off (the default), then on. The second output is the mechanism working; the third is our opening experiment giving a different answer.

That first line — 0 0 4294967295 — is the identity table: inside 0 maps to outside 0, for all four billion ids. It's the kernel's way of saying "no real translation is happening." Reading a container's uid_map is the single fastest way to answer "is this container's root really host root?"

The one thing people get backwards

By default, Docker installs no translator: container root is genuinely host root (uid_map = 0 0 4294967295). What stops that default-root from trivially owning your machine is not id translation — it's the other walls: the dropped capabilities (Lesson 11) and the seccomp syscall filter (Lesson 12). The user-namespace translator is an extra wall you switch on with --userns-remap. This is also why handing someone docker.sock is handing them host root (Lesson 46): they can ask the daemon to run a container as that default, untranslated root.

Why it's off by default (the honest catch). If container-root's files are owned by host uid 1000, then the container's own image files must also be owned by 1000, or the container can't read them — so Docker keeps a separate, re-owned copy of image layers per range, using more disk. And a host file owned by real root, bind-mounted in, becomes unreadable to the container's translated root. Those rough edges are why remap ships off, and why rootless Docker (Lesson 44) is often the nicer path to the same safety.
Where we are

Summary

A user namespace is a translator for ID numbers. Its table is three numbers — (containerID, hostID, size) — and translating is one line, host = hostID + (id − containerID); our example (0, 1000, 32000) makes container-root act as host-user-1000. The table is installed by writing it into the plain file /proc/PID/uid_map once. The outside numbers are handed out by /etc/subuid, and Docker wires it all up with --userns-remap=default via a dockremap user, so every container's root becomes a harmless host id. And the fact to keep above all: by default there is no translator — container root is real root, held in check by capabilities and seccomp, which are exactly where we head next.
