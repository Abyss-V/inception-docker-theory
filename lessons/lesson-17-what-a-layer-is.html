What an image layer physically is

We'll build this one idea at a time. By the end you'll be able to open a real layer, read its bytes, and explain every strange behavior that follows from what's inside.

The idea in one sentence

An image layer is just a tar archive holding the files that changed since the layer beneath it — a list of changes, not a full copy of the filesystem.

Everything below is that one sentence, unpacked slowly. Read it top to bottom; each part uses only what came before it.

1 Start here

A layer is a diff, not a copy

Plain version: a layer records only what changed, like a single "commit" in git or "track changes" in a document — not the whole document each time.

Imagine you start from the alpine base image and add your app on top. The new layer you create does not re-store all of Alpine. It stores only the files you added or changed — your app binary, maybe an edited config. Everything from Alpine is left untouched in the layer below. This is the single most important idea in this lesson, and the word the spec uses for it is changeset: a layer is a set of changes relative to what's underneath.

Why is it done this way? Because of Lesson 15. Layers get stacked by OverlayFS at runtime, and reads fall through to lower layers. So a layer never needs to repeat a file that a lower layer already has — the stack fills it in. A layer only carries the differences.

2 The format

That diff is literally a tar file

Plain version: a layer is an ordinary .tar (usually gzip-compressed) — the same kind of archive you'd make with the tar command. Nothing container-specific.

There's no exotic format here. A layer is a plain tar archive containing the changed files at their normal paths. It's normally compressed with gzip, which is why the OCI media type (its official label) is application/vnd.oci.image.layer.v1.tar+gzip — a tar payload, gzipped. (A newer +zstd variant exists too.) Adding or modifying a file needs no special marker: the file simply appears in the tar. Here's what an additive layer's tar contents look like:

# a layer that adds a binary + a config, and edits one file:
app/server   ← new file, just present
app/config.yaml   ← new file
etc/hosts   ← modified: the whole new version is included

That is the entire content of an add-only layer. Later in the lesson you'll run tar tvf on a real one and see exactly this.

3 The tricky operation

How do you delete a file in a tar? Whiteouts

Plain version: a tar can only hold files, not "delete this" instructions — so a deletion is faked by adding a tiny marker file with a special name.

Adds and edits were easy. Deletion is the interesting case, and it's where a clever trick lives. Suppose your layer needs to remove /etc/motd, which came from a lower layer. You can't put a "remove /etc/motd" command into a tar — a tar only holds files. So the spec (image-spec/layer.md) uses a convention: to delete a file named motd, the layer includes an empty file named .wh.motd — the prefix .wh. (short for "whiteout") plus the name of the thing to delete. When the layer is applied, the tooling sees .wh.motd, deletes motd from the built-up filesystem, and then hides the marker itself.

# lower layers have: file1, a/file2, b/, c/file3
# this layer deletes file1, a/file2, and the whole b/ dir — and adds file4:
.wh.file1   ← "delete file1"
a/.wh.file2   ← "delete a/file2"
.wh.b   ← "delete the b directory"
file4   ← a normal addition

One extra case: to wipe out everything a directory inherited from below (rather than naming each file), a layer puts a special marker .wh..wh..opq inside that directory — an opaque directory marker meaning "ignore everything from lower layers here."

4 A callback

The same delete-marker exists in two forms

Plain version: the "delete" marker looks different when an image is sitting on disk versus when a container is running — Docker converts between the two.

Back in Lesson 15, a deletion in a running container's OverlayFS was a strange character device numbered 0/0. Here, in an image layer on disk, a deletion is a .wh. file. These are the same idea wearing two costumes: the .wh. form is the portable one that travels inside images; the char-device form is the live one OverlayFS uses. containerd translates between them. When it unpacks a layer onto an overlay directory, its archive code (pkg/archive/tar_opts_linux.go) turns each .wh. entry into the real thing with Mknod(path, S_IFCHR, 0) — literally creating that 0/0 character device. Same concept, converted at unpack time.

5 Why it matters

The payoff: "rm" grows images, and deleted secrets survive

Plain version: because a delete is really an added marker, a later layer can hide things but never shrink or truly erase what an earlier layer wrote.

Hold concept 3 in mind — deletion is an addition (a whiteout file). Two of Docker's most infamous surprises fall straight out of it:

Deleting files doesn't shrink the image. If a Dockerfile runs rm -rf /big/thing where /big/thing was added in an earlier layer, nothing is reclaimed. A new layer is created containing a .wh. marker, while the original bytes still sit in the earlier layer's tar — which is still stored and still downloaded. The image gets slightly bigger, not smaller.

A "deleted" secret is still there. If you copy a secret into one layer and delete it in a later one, the secret is fully intact in the layer that added it. The later whiteout only hides it from the running container's view. Anyone who pulls the image can extract that earlier layer's tar and read the secret in plaintext. (We use and defend against this in Lessons 30 and 31.)

The rule to remember

A layer only ever adds to the tar — even a deletion is an added marker. So nothing in a layer can be shrunk or truly erased by a later layer; it can only be hidden. Image bloat and leaked secrets are the same fact seen twice.

6 Naming

A layer is named by a fingerprint of its bytes

Plain version: each layer's "name" is a sha256 hash of its contents — a fingerprint. Identical layers get the same fingerprint, so they're stored once.

A layer isn't referred to by a filename; it's referred to by a hash — a sha256 checksum of its bytes, which acts like a fingerprint. This is called content addressing: the content is the address. The immediate benefit is free deduplication. Two images built FROM alpine share Alpine's layers because those layers hash to the same fingerprint — one copy is stored, downloaded once. Pull an image whose layers you already have, and Docker skips them. No bookkeeping feature makes this happen; it's just what falls out of naming things by their hash.

7 The classic confusion

One layer, two fingerprints: diffID and digest

Plain version: a layer exists as two byte-streams — the raw tar and the gzipped tar — so it has two hashes. Don't panic when you see two different sha256s for "the same" layer.

This trips up almost everyone, so go slow. A layer can be hashed in two states: before compression (the raw tar) and after compression (the gzipped blob that actually gets shipped). Hash each and you get two different fingerprints for one layer:

The diffID is the sha256 of the uncompressed tar. It identifies the layer's content. (Spec wording, config.md: "the digest over the layer's uncompressed tar archive.") You'll find it in the image config, in a list called rootfs.diff_ids.

The digest is the sha256 of the compressed blob — the actual file stored in the registry. It identifies the stored bytes. You'll find it in the image manifest.

8 Naming a whole stack

ChainID — the name for Lesson 16's parent chain

Plain version: a diffID names one layer; a ChainID names a whole ordered stack of layers. It's the proper name for the parent→child chain you already met in Lesson 16.

In Lesson 16 you saw committed snapshots linked parent→child into a chain, and I said the snapshotter keys them on that chain — but I didn't name the key. Here it is: the ChainID. A diffID identifies one changeset; a ChainID identifies the result of stacking layers 0…N in order. It's built by folding the diffIDs together, one at a time (the spec's recursion: the first layer's ChainID is just its diffID; each next one hashes the running ChainID together with the new layer's diffID). The reason it exists: two images that share the same first three layers produce the same ChainID for those three, so that stacked result is stored once and reused — the dedup from concept 6, extended from single layers to whole stacks.

Inspect it yourself

Prove a layer is just a tar, find a whiteout inside one, and watch the two fingerprints differ:

Check yourself

  • A layer is a tar of changes (a changeset) relative to the layer below — not a full filesystem. Unchanged files are absent because the stack supplies them.
  • Adds and edits just appear as files in the tar. Deletes are faked with a whiteout file named .wh.<name> (and .wh..wh..opq to empty a directory).
  • Because a delete is an added marker, a later layer can only hide — never shrink or erase. That's why rm grows images and deleted secrets stay recoverable.
  • The .wh. marker (in the image) and the char-device 0/0 (in a running overlay) are the same idea in two forms; containerd converts between them at unpack.
  • A layer is named by a sha256 fingerprint of its bytes → identical layers are stored once (dedup).
  • One layer has two hashes: diffID = uncompressed tar (in the config), digest = compressed blob (in the manifest).
  • A ChainID names an ordered stack of layers — the proper name for Lesson 16's parent→child chain.
Where this corrects the familiar version

"A layer is a filesystem snapshot" — no, it's a diff; the full filesystem only exists once layers are stacked. "Deleting in a later step cleans it up" — no, it adds a whiteout; the bytes persist below. "A layer has a hash" — it has two (diffID and digest), which is exactly why the config and manifest you'll meet next show different sha256s for the same layer.
