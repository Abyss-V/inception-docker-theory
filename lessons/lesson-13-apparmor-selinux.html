AppArmor & SELinux: guarding which files, not which calls

Capabilities gate privileged operations; seccomp gates syscalls. Both are about the action. Linux Security Modules add a third gate about the object: even for an allowed syscall, which specific files and resources may a container touch?

Here's the gap the first two security walls leave open. open() is on the seccomp allowlist, and reading or writing a file needs no capability. So what stops a container from opening /proc/sysrq-trigger — a magic file where writing a single letter can reboot the host — or /sys/kernel/security, where it could tamper with the security policy itself? Nothing we've covered yet. Those are ordinary write()s to files that merely look normal but are actually kernel control knobs. Plugging that hole is the job of Linux Security Modules (LSMs), and Docker ships with one active by default.

The intuition

A mandatory gate on every object access

The Linux kernel has a built-in framework — the LSM framework — that places a hook at every security-relevant decision: open this file, ptrace that process, mount here, send that signal. A loaded security module gets consulted at each hook and answers allow or deny, according to a policy the administrator sets. The two mainstream modules are AppArmor and SELinux, and a system normally runs one of them.

The important word is mandatory. Ordinary file permissions are discretionary — the owner can chmod them, and root ignores them entirely. LSM policy sits on top and can't be relaxed by the process it constrains, not even by root inside the container. So an LSM is the one wall that still holds when a container is running as root and has somehow kept a dangerous capability: the policy simply refuses the specific file access, regardless of who's asking.

AppArmor and SELinux reach the same goal by opposite routes, and that difference is the whole lesson.

Mechanism 1

AppArmor: deny-list of dangerous paths

AppArmor identifies files by their path. A profile is a list of rules like "this program may read here, may write there, may not touch that." When Docker starts, it loads a profile named docker-default — the name is set in moby's daemon/apparmor_default.go, and the rules themselves live in a template in the moby/profiles/apparmor module. The profile is deliberately permissive about ordinary work (a container needs to read and write lots of files) and surgical about the dangerous exceptions.

Reading the template, the rules that matter are all denials aimed at the two pseudo-filesystems that are the classic escape surface — /proc and /sys, whose "files" are really kernel controls. It denies writes to @{PROC}/sysrq-trigger (a write here can crash or reboot the host), to @{PROC}/kcore (a window into live kernel memory), and to almost all of /proc/sys (kernel tunables). It denies writes under /sys — including /sys/firmware, the cgroup filesystem, and, tellingly, /sys/kernel/security, which is where the LSM's own policy lives, so a container can't disable the very wall confining it. It deny mounts. And it restricts ptrace to peers running under the same profile — so a container process can inspect its own children but never a host process.

Why AppArmor catches what caps and seccomp don't

Writing /proc/sysrq-trigger is an ordinary write() — allowed by seccomp, guarded by no capability. Only a rule that names the path can stop it. That's AppArmor's niche: object-level protection of specific dangerous files, layered after the syscall and capability checks.

Mechanism 2

SELinux: label everything, and give each container its own secret

SELinux takes the opposite approach: it ignores paths and instead stamps every process and every file with a label. A label looks like user:role:type:level, and the part that does the real work is the type. Container processes run as type container_t; their files are typed container_file_t. The system policy says container_t may access container_file_t and very little else — so a container process simply has no rule permitting it to read, say, a host file typed shadow_t (the password file). The access is denied not because of a path rule but because no policy rule connects those two labels.

But that raises a problem: every container runs as container_t with files typed container_file_t. If type were the whole story, one container could read another's files — they share the type. SELinux closes this with MCS (Multi-Category Security). When Docker creates a container it calls into the SELinux library (moby's label.InitLabels in daemon/daemon_unix.go) which assigns that container a unique random category pair, appended to the label as something like s0:c124,c675. The container's process label and its file labels all carry that same pair. The MCS rule is: a process may access a file only if the file's categories are a subset of the process's. Give each container a different pair and they become mutually blind — even though both are container_t/container_file_t.

Why bind mounts need :z / :Z on SELinux hosts. A host file you bind-mount in keeps its host label (e.g. etc_t), which container_t has no rule to access — so the container gets "permission denied" even though the file permissions look fine. The :z (shared) and :Z (private, with this container's category pair) mount options tell Docker to relabel the file to container_file_t so the container can reach it. If you've ever hit an inexplicable permission error on a bind mount on RHEL/Fedora, this is almost always why.
Mechanism 3

How the choice reaches runc — and which one you have

Both LSMs are carried to the runtime through the OCI spec. The runtime-spec defines process.apparmorProfile (a profile name like docker-default), process.selinuxLabel (the container's process label with its MCS categories), and linux.mountLabel (the label applied to the container's files). Docker fills in whichever set matches the LSM active on the host and leaves the other empty — runc then applies the profile or sets the labels just before executing your process.

Which LSM is active is a property of the distribution, and you almost never run both: AppArmor is the default on Debian and Ubuntu, SELinux on RHEL, Fedora, and CentOS Stream. Docker detects what's present and applies the corresponding default. This is why the same container can be confined by a path-based profile on an Ubuntu host and a label-based policy on a Fedora host, with no change to the image.

Where this corrects the familiar version

"AppArmor and SELinux both sandbox containers" is true but hides that they're not interchangeable in style: AppArmor reasons about paths, SELinux about labels, and that shapes everything — SELinux can isolate two containers from each other via MCS categories in a way path rules can't easily express, while AppArmor profiles are far easier to read and write. Also: this is the wall people most often disable by accident. --security-opt apparmor=unconfined, --security-opt label=disable, and (again) --privileged all switch the LSM off for that container. And the bind-mount permission trap on SELinux hosts (:z/:Z) trips up almost everyone once, because the failure looks like a file-permission problem when it's really a label mismatch.

Where we are

Summary

Linux Security Modules add a third, mandatory gate that the other primitives miss: control over which objects an allowed action may touch, unremovable even by root inside the container. AppArmor is path-based; Docker's docker-default profile denies writes to the dangerous /proc and /sys control files (sysrq-trigger, kcore, /proc/sys, /sys/kernel/security), blocks mount, and confines ptrace to same-profile peers. SELinux is label-based; containers run as type container_t over container_file_t, and MCS gives each container a unique category pair so they can't read each other's files despite sharing a type. Both reach runc through the runtime-spec's apparmorProfile, selinuxLabel, and mountLabel, with AppArmor default on Debian/Ubuntu and SELinux on RHEL/Fedora. That completes the three security primitives (capabilities, seccomp, LSMs) that harden the shared-kernel wall.
