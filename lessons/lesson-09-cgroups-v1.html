cgroups v1: putting a ceiling on what a container can use

Namespaces decide what a process can see. cgroups decide how much it can use — and enforce it in three surprisingly different ways: memory by killing, CPU by throttling, PIDs by refusing. The whole thing is driven through a filesystem.

Isolation isn't enough. A container with its own private filesystem and network can still call malloc until your machine swaps to death, or spin every CPU core, or fork-bomb the process table — starving every other container on the box. Namespaces don't stop any of that, because hiding the neighbors doesn't stop you from eating their food. The kernel feature that imposes limits is cgroups ("control groups"), and this lesson is the v1 design: what a cgroup is, why v1 splits into many separate trees, and — the part worth savoring — how three different controllers enforce their limits in three completely different ways.

A note on which version you have. There are two cgroup designs, v1 and v2. Most current Linux distributions have switched to v2 (Lesson 10), but v1 is still widely deployed and is the baseline v2 was built to reform — so we learn it first, honestly, then see what v2 changes and why.
The intuition

A cgroup is a labeled bucket of processes the kernel meters

Picture the kernel keeping a set of buckets. You drop some processes into a bucket and attach rules to it: "this bucket may use at most 512 MB of RAM," "at most half a CPU," "at most 100 processes." The kernel then accounts every process in the bucket against those rules and enforces them. That bucket is a cgroup.

Each kind of limit is handled by a controller (older docs say "subsystem") — a piece of kernel code that knows how to meter one resource. There's a memory controller, a cpu controller, a pids controller, a blkio controller for disk I/O, a cpuset controller for pinning to specific cores, and a handful more. A container is simply a cgroup with a few controllers configured, holding the container's processes.

What makes v1 v1 is a structural decision: every controller is its own independent tree. The memory controller has one hierarchy of buckets; the cpu controller has a totally separate hierarchy; and a process is placed into each tree separately. That flexibility (a process could be in bucket A for memory but bucket B for cpu) is exactly what later became a headache — and what v2 unifies. Let's see the mechanism, which is charmingly simple: it's all files.

Mechanism 1

Everything is a file: mkdir a bucket, echo a limit, write a PID

Step 1 · Explain

cgroups have no dedicated syscalls for the common operations. They're exposed as a virtual filesystem, normally mounted under /sys/fs/cgroup/. In v1 there's a subdirectory per controller — /sys/fs/cgroup/memory/, /sys/fs/cgroup/cpu/, and so on — and each is the root of that controller's tree. To operate them: create a cgroup by making a directory; set a limit by writing a number into one of the control files that appear inside it; add a process by writing its PID into the special file cgroup.procs. That last write is what actually binds a process to the bucket.

Mechanism 2 · enforcement style #1

memory → exceed the limit, get OOM-killed

Step 1 · Explain

The memory controller enforces with a hard wall and a kill. You write a byte count into memory.limit_in_bytes. The kernel tracks the cgroup's total memory use; when a process in the group tries to use more than the limit allows and the kernel can't reclaim enough (by dropping caches, swapping), it invokes the OOM killer — but scoped to that cgroup. It picks a victim process inside the bucket and kills it with SIGKILL. The blast radius is contained: your container dies, the host and its neighbors don't.

Step 2 · The source
The part that does the job

The limit is a number in memory.limit_in_bytes; the enforcement is the cgroup-scoped OOM killer. The EBUSY branch is a nice tell about the wall's hardness: you can't even set a limit below what the group is already using — the kernel rejects it outright. Docker's -m 512m / --memory flag is exactly this field, and an OOM-killed container shows exit code 137 (128 + signal 9).

Mechanism 3 · enforcement style #2

cpu → exceed your slice, get throttled (not killed)

Step 1 · Explain

CPU is enforced completely differently — nobody dies, the process just waits. The mechanism is CFS bandwidth control, set by two files. cpu.cfs_period_us defines a repeating window of time in microseconds (default 100000 = 100 ms). cpu.cfs_quota_us is how many microseconds of CPU time all the tasks in the cgroup are collectively allowed to run within each window. Use up your quota before the window ends and the kernel throttles the group — deschedules its tasks until the next period begins, then lets them run again. Quota ÷ period is your effective number of cores: 50000 / 100000 = 0.5 CPU.

Step 2 · The source
The part that does the job

Two numbers make a hard CPU cap: run for quota microseconds out of every period, then sleep until the window resets. Docker's --cpus=0.5 is pure sugar for "set quota to half of period." Note this is a ceiling. There's a separate file, cpu.shares, which sets a weight — how the CPU is divided proportionally when there's contention — and does nothing when the CPU is idle. Ceiling vs weight is a distinction that trips people up: --cpus caps, --cpu-shares prioritizes.

Mechanism 4 · enforcement style #3

pids → hit the cap, fork() is refused

Step 1 · Explain

The pids controller is the simplest and shows a third enforcement style: outright refusal. Write a number to pids.max. Once the cgroup holds that many processes, any further fork() or clone() from inside the group fails immediately with EAGAIN ("resource temporarily unavailable"). Nothing is killed and nothing waits — the kernel just declines to create the new process. This is the direct antidote to a fork bomb, which works by creating processes faster than you can kill them; with a pids cap it simply can't.

Step 2 · The source
The part that does the job

One file, pids.max, and the kernel converts "too many processes" into a failed syscall. Docker exposes it as --pids-limit. The runtime-spec field is pids.limit, with -1 meaning unlimited (written as "max").

The payoff

Three limits, three enforcement styles

This is the thing to carry out of the lesson. A "resource limit" is not one mechanism — each controller reacts to a breach in its own way, and knowing which is which explains every symptom you'll see in production:

Where this corrects the familiar version

Two clarifications. First, "cgroups isolate containers" is a category error — cgroups don't isolate anything (that's namespaces); they limit and account. A container out of memory and a container that can't see its neighbors are two different kernel features working together. Second, people conflate --cpus and --cpu-shares: the first is a hard ceiling (quota/period), the second is only a proportional weight under contention. And the v1 detail worth remembering: because each controller is its own tree, there is no single "the container's cgroup" in v1 — there are as many as there are enabled controllers, which is precisely the fragmentation v2 sets out to fix.

Where we are

Summary

A cgroup is a bucket of processes the kernel meters, and in v1 the whole interface is a filesystem: mkdir a directory to create one, write a number into a control file to set a limit, write a PID into cgroup.procs to add a process. v1's defining shape is one independent tree per controller, so a process is enrolled into each controller separately. The controllers enforce in three distinct ways — memory.limit_in_bytes kills via a scoped OOM, cpu.cfs_quota_us/cfs_period_us throttle by descheduling until the next window, and pids.max refuses new forks with EAGAIN — and these map straight onto Docker's --memory, --cpus, and --pids-limit. Next lesson takes the same controllers into cgroups v2, where the many trees collapse into one unified hierarchy — and we'll see exactly which problems that solves.
