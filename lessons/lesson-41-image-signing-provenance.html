Part 6 · Distribution · Lesson 41

Image signing & provenance

Lesson 40 gave us a stable identity: a digest names exact image content. This lesson adds two different things around that identity. Provenance says what happened during the build. A signature proves that a particular signing key approved a digest-bound claim. They are related, but they are not the same mechanism.

DEEP-CUT
governing idea

Do not sign a tag. Resolve the image to immutable content, then bind claims and signatures to the digest of that content.

We will use one example throughout:

registry.example.com/course/app:1.0

platform image manifest M = sha256:11aa…
provenance statement P    = sha256:22bb…
attestation manifest A    = sha256:33cc…
final image index I       = sha256:44dd…
signature artifact S      = sha256:55ee…

Those letters are only labels for this lesson. The important part is which digest points to which object.

Lessons 18–19 taught descriptors and content-addressed image graphs. Lesson 39 taught registry movement. Lesson 40 taught tag resolution and digest identity. We will use those mechanisms rather than re-teach them.

whole movement first

1. The complete pipeline

There are actually two pipelines. BuildKit creates provenance while exporting the image. A signer can later sign the finished published image digest.

Provenance becomes part of the exported image graph. The signature is created afterward and stored as a separate object that refers back to the final image digest.

First build the exact content graph. Then sign the digest of the graph you actually intend to publish.

2. First separate the three ideas

The words provenance, attestation, and signature are often thrown into one bucket. That makes the mechanism harder than it is.

ThingWhat it answersDoes it cryptographically prove who approved it?
ProvenanceWhat build inputs and build actions produced this result?No, not by itself.
Attestation objectHow are those claims packaged and attached to an image result?Attachment alone is not trust.
SignatureDid the holder of an accepted private key sign this digest-bound payload?Yes, if verification succeeds with the corresponding trusted public key or accepted identity material.
common mistake

A provenance document can be perfectly well formed and still be untrusted. A registry can store an artifact that claims to refer to your image. Cryptographic verification is the extra step that establishes who signed the claim.

pipeline A · build

3. Where provenance starts: the solved build graph

Consider a small build:

FROM alpine:3.22
COPY app /usr/local/bin/app
RUN chmod +x /usr/local/bin/app
ENTRYPOINT ["/usr/local/bin/app"]

By the time BuildKit is exporting the result, it has more information than the final root filesystem contains. It knows which source operations and execution operations were actually part of the solved build.

In pinned BuildKit 0.31.1, captureProvenance walks the build result's provider graph. It records information from source operations and execution operations. For example, source operations contribute source identity/pinning information; execution operations contribute selected execution facts such as network access and the IDs of secret or SSH mounts.

important boundary

The provenance capture code records a secret mount's ID and whether it was optional; this source path is not dumping the secret's value into provenance. The distinction matters.

The main relationship is:

actual solved build operations
        │
        │ BuildKit walks them
        ▼
structured provenance data
        │
        ▼
serialized provenance statement

This is why provenance cannot be reconstructed accurately just by looking at the final layer tar files. A layer tells you filesystem changes. Provenance records facts about how the build result was produced.

Source anchor: BuildKit v0.31.1 · solver/llbsolver/provenance.go · captureProvenance / ProvenanceCreator

4. What object does BuildKit say the provenance is about?

Now we need the most important digest relationship in the provenance half.

BuildKit packages its provenance inside an in-toto statement. For this lesson, that means a JSON claim envelope with three load-bearing pieces: subject says which content the claim is about; predicateType identifies the claim schema; predicate contains the build-specific facts. We need those names because they are the real fields you will inspect.

Assume BuildKit has created the runnable platform image manifest:

M = sha256:11aa…

That manifest already points to the image config and layer descriptors. BuildKit then creates a default subject for the provenance statement from that platform manifest descriptor.

Here, subject simply means: the content object this statement is making claims about.

provenance statement P
{
  "subject": [
    {
      "digest": {
        "sha256": "11aa…"
      }
    }
  ],
  "predicateType": "...",
  "predicate": {
      ... build facts ...
  }
}
load-bearing relationship

The provenance statement is not about the tag :1.0. In the pinned BuildKit export path, its subject is derived from the exact platform manifest descriptor M.

The source-level bridge is small but important: while exporting each platform, BuildKit constructs defaultSubjects from the just-created platform manifest's desc.Digest, then passes those subjects into its in-toto statement creation.

Source anchor: BuildKit v0.31.1 · exporter/containerimage/writer.go · defaultSubjects / MakeInTotoStatements

5. How provenance bytes become content-addressed image metadata

A statement is still only bytes. BuildKit has to place it into a registry-storable content graph.

1

serialize the statement

BuildKit marshals the in-toto statement to JSON. Call those bytes P.

P bytes → sha256:22bb…
2

store the statement as content

The exporter computes the digest from the statement bytes and writes those bytes into the content store. The descriptor for this payload carries its digest, size, and in-toto media type.

3

create an attestation manifest

BuildKit creates a separate manifest A whose payload descriptor points to P. This manifest is metadata, not another runnable Linux root filesystem.

A = sha256:33cc…
A ──descriptor──► P = sha256:22bb…
4

put the image and its attestation into the exported index

The exporter appends the attestation-manifest descriptor beside the runnable platform-manifest descriptor, then serializes the root image index.

I = sha256:44dd…

image index I
├── platform manifest M = sha256:11aa…
└── attestation manifest A = sha256:33cc…
       └── provenance statement P = sha256:22bb…
             └── subject digest = M

With attestations present, the image exporter has a reason to produce an index even for what you may think of as a single-platform build: the index is the container that can carry the runnable manifest descriptor and the additional attestation-manifest descriptor together.

why the root digest changes

If the provenance statement bytes change, P's digest changes. Then A's descriptor changes, which changes A's bytes and digest. The root index contains A's descriptor, so I changes too. This is normal content-addressed graph behavior from Lessons 18–19.

Source anchor: BuildKit v0.31.1 · exporter/containerimage/writer.go · commitAttestationsManifest and index assembly

6. Provenance is now attached — but it still is not a signature

At the end of the BuildKit pipeline we have:

tag :1.0
   │
   ▼
root index I
├── runnable platform manifest M
└── attestation manifest A
       └── provenance statement P
             subject = M

You can inspect the statement and learn what BuildKit recorded. But none of the steps above inherently says:

"a private key controlled by organization X signed this statement/image"

The pinned BuildKit path shown here captures, serializes, hashes, stores, and attaches provenance. Those operations should not be renamed “signing.”

source-over-folklore correction

“BuildKit generated provenance, therefore the image is signed” is false. Provenance supplies claims. A signature supplies cryptographic signer evidence.

inspect it yourself · provenance movement

Use a registry repository you can push to. This explicitly requests SLSA provenance v1, the provenance predicate schema BuildKit will place inside the in-toto statement. We name the schema only because the command must select a concrete version; it is not another component in the pipeline.

export IMAGE=registry.example.com/your-user/lesson41

docker buildx build \
  --platform linux/amd64 \
  --attest type=provenance,mode=max,version=v1 \
  --push \
  -t "$IMAGE:1.0" .

# 1. See the root manifest/index bytes.
docker buildx imagetools inspect --raw "$IMAGE:1.0" | jq .

# 2. Ask Buildx to extract the provenance it finds.
docker buildx imagetools inspect "$IMAGE:1.0" \
  --format '{{ json .Provenance.SLSA }}' | jq .

In the first command, look for multiple descriptors under the root index. In the second, inspect subject, predicateType, materials, invocation/build metadata, and the exact values your build produced.

pipeline B · signing

7. Why the signer should target the final root digest

After BuildKit has finished attaching provenance, our published tag resolves to:

registry.example.com/course/app:1.0
              │
              ▼
I = sha256:44dd…

If the goal is to approve the published image result including its attached BuildKit provenance graph, the clean target is the final root digest I.

Why not sign M here? Because M is only the runnable platform manifest. I is the published root that points to both the runnable manifest and the attestation manifest in our example.

Why not sign the text :1.0? Because Lesson 40 already established that the tag can be moved to another root digest.

Before signing
repo:1.0 → I
resolve the mutable name once
→
Signing target
repo@sha256:44dd…
exact root content identity
practical rule

Resolve the tag, record the digest, and sign the digest reference. Current Cosign documentation makes the same recommendation because a tag can change between resolution and signing.

8. What a cryptographic signature actually proves

For this lesson, we need only the minimal asymmetric-signature model:

private key Kpriv
      │
      │ signing algorithm over payload bytes
      ▼
signature bytes σ

public key Kpub + payload bytes + σ
      │
      │ verification algorithm
      ▼
valid / invalid

The private key is used to produce the signature. The corresponding public key can check it. Verification does not require the private key.

For an image, a signer does not need to cryptographically process every layer byte independently. The signed payload can contain the immutable image digest. Because that digest identifies the root content and the root descriptors identify their children, the digest is the compact identity being approved.

what a valid signature does not prove

It does not prove the software is bug-free, safe, or morally trustworthy. It proves that the accepted key signed the verified payload. Your trust decision is then: do I trust the holder/identity represented by this verification key or certificate?

9. Current Docker boundary: the signer is external

The course baseline is Docker CLI 29.6.2. Docker CLI v29 removed the old built-in docker trust signing commands. Therefore this lesson does not teach docker trust sign as the current Docker signing pipeline.

To inspect a concrete current signing implementation without changing the Docker/containerd/OCI source family, this lesson locally pins Cosign v3.0.6 as the external signer.

Docker / BuildKit responsibility in this lesson:
  build image + provenance → publish digest-addressed OCI graph

Cosign responsibility in this lesson:
  take exact image digest → build digest-bound signed payload
  → create signature material → store referring artifact
component boundary

Cosign is not secretly part of dockerd, containerd, shim, or runc. It is a separate client talking to the registry. No container-runtime process is involved in creating an image signature.

Source anchors: Docker Engine v29 release notes · Docker Content Trust removal; Cosign v3.0.6 · cmd/cosign/cli/sign/sign.go

10. The signing payload is bound to the image digest

Give Cosign the exact image reference:

registry.example.com/course/app@sha256:44dd…

In the v3.0.6 signing path, Cosign decomposes that digest and constructs an in-toto subject whose digest map contains the algorithm and hex digest value. Conceptually:

signed statement / payload
{
  "subject": [
    {
      "digest": {
        "sha256": "44dd…"
      }
    }
  ],
  ...
}

Then the signing machinery signs the digest-bound payload with the selected signer and prepares the resulting signature material for storage.

what is being vouched for

The key is not vouching for the characters course/app:1.0. The signed claim contains the immutable digest sha256:44dd….

If someone later changes the tag so that:

course/app:1.0 → sha256:99ee…

the old signature over 44dd… remains a valid signature for the old object. It does not become a signature for 99ee….

Source anchor: Cosign v3.0.6 · cmd/cosign/cli/sign/sign.go · signDigestBundle

11. Where the signature lives without changing the image digest

This is a subtle storage problem.

Suppose we tried to put the signature descriptor inside the already-signed index I. Adding the descriptor would change the index bytes, which would change I's digest. Then the signature would point to the old digest. Trying again would repeat the problem.

So the signature is stored as a separate registry object that refers to the signed digest.

signed image root
I = sha256:44dd…

signature artifact
S = sha256:55ee…
        │
        └── subject descriptor → I = sha256:44dd…

OCI Image Spec 1.1.1 gives a manifest an optional subject descriptor. The spec deliberately describes that link as a weak association: it is a reference relationship, not cryptographic proof.

do not confuse storage with trust

Anyone able to push an artifact could potentially push an object whose outer OCI subject says “I refer to 44dd….” That declaration alone proves nothing about who signed it. The verifier must still validate the cryptographic signature and its digest-bound claim.

Cosign v3 stores current container signature material as an OCI Image 1.1 referring artifact, so the registry can keep S separately while indexing it under subject digest I.

Source anchors: OCI image-spec v1.1.1 · manifest.md · subject; Cosign v3.0.6 release/source

12. How the registry finds artifacts that refer to a digest

Once a signature is separate, a verifier needs a discovery mechanism. OCI Distribution Spec 1.1.1 defines the referrers API:

GET /v2/course/app/referrers/sha256:44dd…

The registry returns an OCI image index containing descriptors for manifests that claim sha256:44dd… as their subject.

I = sha256:44dd…
      │
      │ registry referrers lookup
      ▼
[ descriptor for S, ... ]

This endpoint is a reverse lookup. Normal OCI descriptors point from a parent object to children. Referrers lets the registry answer the opposite question: “which stored manifests say they refer to this digest?”

Again, discovery and trust stay separate:

StepWho does it?What it proves
Referrers lookupregistryThese stored artifact descriptors claim this subject relationship.
Fetch signature artifactsigning/verifying clientObtains bytes to inspect.
Cryptographic verificationverifying clientThe accepted key/identity signed the payload.
Subject-digest claim checkverifying clientThe verified payload is actually about the image digest being verified.

Source anchor: OCI distribution-spec v1.1.1 · Referrers API · GET /v2/<name>/referrers/<digest>

13. Verification in real execution order

Assume a consumer wants to verify:

registry.example.com/course/app:1.0

With a mutable tag, the first job is still Lesson 40's job: resolve the tag to the digest that exists now.

1

resolve the image identity

course/app:1.0 → I = sha256:44dd…

The verifier now has the exact subject it intends to verify.

2

discover/fetch signature material associated with I

In the OCI 1.1 path, the client can obtain referring signature/bundle artifacts associated with I.

3

choose the trust material

For the simplest experiment, that is an explicit public key file. More elaborate identity/certificate systems exist, but we do not need them to understand the digest/signature mechanism.

4

cryptographically verify the payload

Cosign loads the verifier from the supplied public key/certificate path and invokes its image-signature/attestation verification machinery.

5

check the verified claim is about I

Current Cosign's v3 verification path for its OCI-stored signature material installs an in-toto subject claim verifier. The subject digest in the verified statement must correspond to the image reference being verified. Otherwise a valid signature over some other digest would be useless for this image.

A signature can be mathematically valid and still be irrelevant unless the signed subject is the image digest you intended to verify.

Source anchor: Cosign v3.0.6 · cmd/cosign/cli/verify/verify.go · VerifyCommand.Exec / IntotoSubjectClaimVerifier / VerifyImageAttestations

14. The two different “subject” fields you may encounter

Now that the core path is clear, we can safely distinguish two uses of the word subject.

LocationMeaningJob
Inside an in-toto statementThe digest the claim is semantically about.Lets verification check “this signed/attested statement concerns digest X.”
OCI manifest's outer subject descriptorThe OCI object this separate artifact says it refers to.Lets registries index/discover referrers.

Those two relationships often point to the same digest for a signature artifact, but they solve different problems:

outer OCI subject
   → registry discovery

inner in-toto subject
   → meaning of the claim + verification target

Do not treat the outer OCI subject as a replacement for checking the signed inner claim.

15. Why signing the final root also binds its provenance graph

Return to our BuildKit result:

I = sha256:44dd…
├── descriptor → M = sha256:11aa…
└── descriptor → A = sha256:33cc…
                  └── descriptor → P = sha256:22bb…

Suppose someone changes one byte in the provenance statement P.

  1. The changed statement no longer has digest 22bb….
  2. The attestation manifest would need the new statement descriptor, so A's bytes change.
  3. The root index would need the new A descriptor, so I's bytes change.
  4. The old signature's signed subject is still 44dd…, so it does not approve the newly changed graph.
transitive binding

A signature over the final root digest does not contain every descendant byte. It relies on the OCI graph's descriptor digests: changing a descendant requires changing each affected parent descriptor up to a different root digest.

but do not overclaim

This proves which exact provenance bytes were inside the signed graph. It does not independently prove that every factual claim inside the provenance is true. You still need to decide whether you trust the builder/signer and what policy you require.

inspect it yourself · sign and verify exact digest

This experiment deliberately uses a local key pair because it exposes the core cryptographic relationship without requiring a second identity system before the digest/signature mechanism is clear.

# Pin/check the lesson-specific signer version.
cosign version
# Lesson source pin: v3.0.6

# Create an asymmetric key pair.
cosign generate-key-pair

export IMAGE=registry.example.com/your-user/lesson41

# Resolve the tag once and capture the published root digest.
DIGEST=$(docker buildx imagetools inspect "$IMAGE:1.0" \
  | awk '$1 == "Digest:" {print $2; exit}')

echo "$DIGEST"

# Sign the immutable digest reference, not the tag string.
cosign sign --key cosign.key "$IMAGE@$DIGEST"

# Verify with the public key.
cosign verify --key cosign.pub "$IMAGE@$DIGEST"

# Inspect signature/referrer relationships exposed by Cosign.
cosign tree "$IMAGE@$DIGEST"

What to observe: the image digest is chosen before signing; verification requires only the public key; the signature metadata is stored separately from the image root.

inspect it yourself · prove a moved tag is a different target
OLD="$DIGEST"

# Change the Dockerfile or app content and push a new build to the SAME tag.
docker buildx build \
  --attest type=provenance,mode=max,version=v1 \
  --push -t "$IMAGE:1.0" .

NEW=$(docker buildx imagetools inspect "$IMAGE:1.0" \
  | awk '$1 == "Digest:" {print $2; exit}')

printf 'old=%s\nnew=%s\n' "$OLD" "$NEW"

# Old object can still have a valid old signature.
cosign verify --key cosign.pub "$IMAGE@$OLD"

# The new digest has not automatically inherited that signature.
cosign verify --key cosign.pub "$IMAGE@$NEW"

The final command should not be treated as verified merely because :1.0 used to point at a signed digest. The new content needs its own applicable signature.

16. Component ownership: who actually performs each job?

For the mechanism taught here, keep the ownership clear:

ComponentRole in this lesson
Docker CLI / BuildxStarts the build/export and can inspect resulting provenance.
BuildKitCaptures build provenance and packages it into the exported OCI image graph.
dockerd / containerdParticipate in ordinary image/content management and registry flows according to the build/image-store path; they are not the Cosign private-key signer.
registryStores immutable OCI content and supports discovery of referring artifacts.
CosignExternal signer/verifier used here to bind a cryptographic signature to the final digest.
shim / runc / Linux kernelNo role in creating an image signature. They matter later when a container is actually run.

17. Common wrong mental models

Wrong modelCorrect mechanism
“The tag is signed.”The signing claim is bound to a digest. A tag may merely be used as a starting reference before resolution.
“Provenance is the signature.”Provenance is build evidence/claims. A signature is cryptographic evidence from a key over a payload.
“If a registry returns a referrer, it is trusted.”Referrers is discovery. The client must verify cryptography and claim target.
“Signing encrypts the image.”No. Image content remains ordinary registry content. A separate signature proves a digest-bound payload.
“If the tag moves, the signature follows it.”No. The old signature remains tied to the old digest.
“A signature proves the provenance facts are true.”It proves the accepted signer signed those exact claims/content identity. Factual trust still depends on who/what you trust.
“runc verifies image signatures before start.”Not in this pipeline. Signature verification is a distribution/policy concern before runtime execution; runc consumes a runtime bundle, not registry signing metadata.

18. Primary-source proof

The Docker/BuildKit/OCI baseline stays on the course-pinned family. Cosign v3.0.6 is a lesson-specific external pin because Docker CLI 29 no longer supplies the old built-in DCT signing workflow.

Docker Engine 29 release notes BuildKit v0.31.1 · provenance.go BuildKit v0.31.1 · writer.go OCI image-spec v1.1.1 · manifest.md OCI distribution-spec v1.1.1 · spec.md Cosign v3.0.6 · sign.go Cosign v3.0.6 · verify.go
Exact audit anchors behind the explanation

Current CLI boundary: Docker Engine v29 release notes record removal of Docker Content Trust from the Docker CLI beginning with v29. This is why Lesson 41 does not present docker trust sign as the pinned current implementation.

Provenance capture: BuildKit v0.31.1 solver/llbsolver/provenance.go::captureProvenance walks solved operations/providers and records source and execution provenance. ProvenanceCreator constructs the requested provenance predicate.

Provenance subject: BuildKit v0.31.1 exporter/containerimage/writer.go creates default in-toto subjects from the platform image manifest's desc.Digest, then calls statement creation.

Attestation bytes/content graph: commitAttestationsManifest serializes statement JSON, computes its content digest, stores it as a payload descriptor, creates an attestation manifest, and returns that manifest descriptor. The writer appends attestation descriptors into the exported root index alongside platform manifests.

OCI attachment semantics: OCI Image Spec v1.1.1 manifest.md defines optional subject and explicitly characterizes it as a weak association to another manifest. Association is not verification.

Referrers discovery: OCI Distribution Spec v1.1.1 defines GET /v2/<name>/referrers/<digest>, returning an image index of referring manifest descriptors, with artifact-type filtering and a compatibility fallback mechanism.

Digest-bound signing: Cosign v3.0.6 cmd/cosign/cli/sign/sign.go::signDigestBundle splits the resolved image digest and places algorithm/value into the in-toto resource descriptor used as the signed statement subject before invoking signing/bundle logic.

Verification: Cosign v3.0.6 cmd/cosign/cli/verify/verify.go::VerifyCommand.Exec loads trust/verifier material, installs IntotoSubjectClaimVerifier for the new bundle path, retrieves/verifies image attestations, and transforms verified output from the in-toto subject digest.

19. Check yourself

  1. What is the difference between provenance and a signature?
  2. In the pinned BuildKit exporter path, what digest becomes the provenance statement's subject for one platform?
  3. Why does attaching provenance usually create/change a root image index digest?
  4. Why is the final published root digest a useful signing target after provenance has been attached?
  5. Does an OCI manifest's outer subject field prove the artifact is trustworthy?
  6. What does the registry referrers endpoint return?
  7. What two checks must not be collapsed during signature verification?
  8. If :1.0 moves from digest I to digest I2, does a signature for I cover I2?
  9. Why does signing one root digest indirectly bind descendants in the OCI graph?
  10. Does runc create or verify these registry image signatures?
Answers
  1. Provenance is structured evidence/claims about how a build result was produced. A signature is cryptographic evidence that an accepted private key signed a particular payload.
  2. The exact platform image manifest descriptor digest M.
  3. The provenance statement has its own digest, is referenced by an attestation manifest, and that attestation-manifest descriptor is placed in the root index. Changes propagate upward through descriptor bytes.
  4. That root digest identifies the published graph containing both the runnable platform manifest and the attached provenance object(s) in this export.
  5. No. It supplies an association used for storage/discovery. Cryptographic verification is separate.
  6. An OCI image index of descriptors for manifests/artifacts that refer to the requested subject digest.
  7. Verify the cryptographic signature with accepted trust material, and verify that the signed claim's subject digest is the image digest you intended to verify.
  8. No. The old signature remains about I.
  9. Each parent contains child descriptors with child digests. Changing a descendant forces changed descriptors up the affected path, producing a different root digest.
  10. No. runc operates at the OCI runtime-bundle/runtime stage, not the registry image-signing stage.

Recap: keep the two pipelines separate

PROVENANCE
solved BuildKit graph
      ↓ capture build facts
statement P ──subject──► platform manifest M
      ↓ package as content
attestation manifest A ──descriptor──► P
      ↓ append beside M
root image index I

SIGNING
root image digest I
      ↓ put I in signed claim
private key signs payload
      ↓
signature artifact S ──OCI subject/referrer──► I

VERIFICATION
resolve wanted image → I
      ↓
discover/fetch S
      ↓
verify cryptographic signature
      ↓
verify signed subject digest == I
      ↓
accepted key signed a claim about exact image I

If you remember only one distinction, make it this: provenance tells you what the builder claims happened; a signature tells you which accepted signing identity cryptographically vouched for a digest-bound payload.
