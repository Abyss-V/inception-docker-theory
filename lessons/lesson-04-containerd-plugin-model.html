Docker, From the Source · Part I — Foundations
04

containerd internals: it's a micro-kernel of plugins

We've been calling containerd "the container supervisor." Open it up and there's almost no monolith inside — just a tiny core that loads ~30 typed plugins and wires them together by declared dependencies. Learn that wiring and containerd stops being a black box.

In Lesson 2, dockerd handed work to containerd over a socket and we left it there. Now we go inside. The guiding question: when containerd "stores an image" and "runs a container," what parts of it do those jobs, and how are those parts assembled? The answer is a plugin architecture, and it's worth understanding because it explains why containerd can swap storage backends, swap low-level runtimes, and be embedded in tools that aren't Docker at all.

The intuition

Why a plugin system instead of one big program?

containerd has to do several very different storage and execution jobs, and for most of them there is more than one valid implementation. Layer storage can be done with OverlayFS, or Btrfs, or ZFS, or device-mapper — different filesystems suit different hosts. The low-level thing that actually creates the container could be runc, or a VM-based runtime like Kata, or a syscall-sandbox like gVisor. And containerd is meant to be embeddable: Docker uses it, but so do Kubernetes and others, and each wants to enable some parts and disable others.

If all of that were hard-wired into one binary, every new storage backend or runtime would mean surgery on the core, and you couldn't turn off the parts you don't use. So containerd is built the way an operating-system kernel handles drivers: a small core defines a set of plugin types (roles like "content store," "snapshotter," "runtime"), and concrete plugins register themselves to fill those roles. The core's job is mostly to load them in the right order and hand each one the others it needs. Let's see the roles first.

The taxonomy: what containerd is made of

Step 2 · The source
The part that does the job

Focus on the five highlighted types — they are the ones a container's life actually flows through. Content holds the raw image blobs addressed by their SHA-256 digest. Snapshot turns stacked layers into a mountable root filesystem (this is containerd's name for what Docker calls a storage driver). Metadata is a small embedded database that records which images, containers, and snapshots exist. Diff knows how to apply a layer tar onto a snapshot (unpacking) and how to produce a diff (committing). Runtime v2 is the piece that launches the shim. Everything else (GC, leases, gRPC, events) is supporting plumbing around those five.

Where this corrects the familiar version

containerd is usually introduced as "the container runtime." The type list shows that's misleading: the thing that literally runs a container is one plugin (runtime.v2, which just launches a shim), while the majority of containerd is storage and metadata — content, snapshots, diff, GC, leases. containerd is better understood as a content-and-execution supervisor that delegates the actual running downward, exactly as we saw in Lesson 2. Also note snapshotter.v1 is a role, not a specific filesystem — OverlayFS is just the most common plugin filling it (Lesson 16).

Mechanism 2

The contract: how a plugin registers itself

Step 1 · Explain

A plugin is just a value that fills in a standard form and hands it to a registry at program startup. The form has four fields that matter: what role am I (Type), which variant am I (ID), what other plugins do I need (Requires), and how do I start up (InitFn). That's the entire extension model.

Step 2 · The source
The part that does the job

Type + ID uniquely name a plugin — e.g. type io.containerd.snapshotter.v1 + id overlayfs. Requires is the dependency declaration that drives load order (next mechanism). InitFn is where the plugin actually constructs itself, and it receives an InitContext from which it can fetch its dependencies. And URI() = Type + "." + ID is quietly important: containerd uses that exact string as the plugin's directory name on disk, which is why the inspect step at the end will show folders like io.containerd.snapshotter.v1.overlayfs.

Mechanism 3

The wiring: dependencies decide load order

Step 1 · Explain

Here's where the plugin list becomes an actual architecture. A plugin can't initialize until the plugins it depends on already exist — a snapshotter needs nothing else, but the metadata database sits on top of content and snapshots and can't start before them. containerd figures out a safe order automatically by reading every plugin's Requires list and sorting so that dependencies come first. The part that does the job

Two ideas carry the whole mechanism. First, in the metadata registration, the Requires list is a literal statement of architecture: "metadata depends on content + snapshots," so you can read containerd's layering straight off these declarations. Second, in children(), the recursion emits each dependency into the ordered list before the plugin that needs it, and the panic(ErrPluginCircularDependency) guard fires if a plugin is ever found waiting on itself. The result is a startup order where, by the time any InitFn runs, everything it will ask for already exists. At init a plugin simply calls ic.GetSingle(ContentPlugin) and receives the ready instance.

This is dependency injection, kernel-style. No plugin constructs its own dependencies or knows where they came from; it declares the roles it needs and the core supplies concrete instances. That's exactly why you can replace the overlayfs snapshotter with btrfs without touching the metadata plugin — metadata asked for "a snapshotter," not "overlayfs."
Putting it together

Which plugins a single docker run touches

With the roles named, the path from Lesson 2 gets sharper. When an image is pulled and a container started, work flows across these plugins in turn:

pull image → content.v1 stores each layer blob under its sha256 digest → differ.v1 unpacks (applies) each layer tar… → snapshotter.v1 …into stacked snapshots = a mountable rootfs → metadata.v1 (bolt) records the image, container, snapshot records create/run → runtime.v2 launches containerd-shim-runc-v2 → runc (Lesson 5) throughout → lease.v1 + gc.v1 keep in-use blobs alive, sweep the rest (Lesson 22) API access → grpc.v1 the services dockerd actually calls over the socket

Every noun in that flow is a plugin from the type list, wired in by Requires. containerd's "magic" is just this set of roles talking to each other in dependency order.

Where we are

Summary

containerd is a small core that hosts ~30 plugin types — roles like content store, snapshotter, metadata DB, differ, and runtime. Each concrete plugin registers a Registration declaring its Type, ID, its Requires dependencies, and an InitFn. The core reads those Requires lists, topologically sorts them (panicking on cycles), and initializes each plugin only after its dependencies exist — so a plugin can just ask for "a content store" and receive one. A container's life is that handful of plugins cooperating: content stores blobs, differ+snapshotter build a rootfs, metadata records everything, runtime.v2 launches the shim. Next we follow that last one all the way into the shim itself, and finally answer how a container keeps running when containerd restarts.
