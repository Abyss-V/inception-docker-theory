Contexts & remote daemons: pointing the client somewhere else

Mostly this is stored configuration — and I'll say so honestly. But buried inside "run Docker over SSH" is one genuinely clever mechanism worth going all the way down to.

Lesson 2 ended on a single fact: the docker command is just an HTTP client aimed at a socket, and the target is whatever DOCKER_HOST says. This lesson is about changing that aim — pointing the same client at a daemon on another machine — and about "contexts," the feature that saves those aims by name.

Honest scope note A "context" itself has almost no mechanism: it is a named bundle of connection settings saved as files on disk, and using one just sets the same target we already understood in Lesson 2. I'll cover that quickly and truthfully rather than dress it up. The part that does have real depth is how the client reaches a remote daemon over SSH without exposing any network port — so that's where this lesson spends its time.
The config part (told straight)

What a context actually is: a name → a target + some certs

Step 1 · Explain

Typing DOCKER_HOST=… and passing TLS certificate flags every time you want to talk to a remote daemon is tedious. A context is just a saved, named copy of those settings: "prod" means this host, these certs; "default" means your local socket. Switching context swaps which target the client uses. That's the whole idea — it's a bookmark, not a new capability.

The source confirms it's plain storage. Contexts live as files under ~/.docker/contexts/, split into metadata and TLS material, and the metadata each context stores is essentially a host string plus TLS settings:

The mechanism (all the way down)

Three transports — and why ssh:// is the clever one

Step 1 · Explain

A Host string carries a scheme that picks how the client connects. There are three that matter:

unix:// — connect to a local socket file (the Lesson 2 default). tcp:// — connect to the daemon over a real network port, almost always wrapped in mutual TLS: the daemon presents a certificate the client verifies, and the client presents a certificate the daemon verifies, so both sides prove who they are. That's a normal secured network connection; conceptually nothing new.

ssh:// is the one that's worth understanding, because it pulls off remote access without opening any Docker network port at all. Think about what you'd need: the remote daemon only listens on its local /var/run/docker.sock, which isn't reachable from your laptop. How do you get your HTTP requests to a socket that only exists on the far side? The answer Docker chose is delightfully low-tech: run ssh as a subprocess and treat that subprocess's stdin/stdout as the connection. On the far end, SSH launches a hidden Docker command whose only job is to shovel bytes between its own stdin/stdout and the remote's local socket.

The part that does the job

Three highlighted lines carry the whole mechanism. On the client, commandconn.New(ctx, "ssh", …) means the network connection object is really a running ssh process — the CLI writes HTTP into its stdin and reads HTTP from its stdout. On the remote, dial-stdio opens the remote's local docker socket and runs two copier loops that splice stdin→socket and socket→stdout. Put together, your request flows:

docker (local, HTTP) → writes into → ssh subprocess stdin → [encrypted ssh channel] → remote docker system dial-stdio stdout/stdin → /var/run/docker.sock → remote dockerd
Why this is a nice design. No Docker port is exposed to the network — the daemon still only listens on its private local socket. Authentication, encryption, and access control are entirely SSH's job, which every server already has hardened. You reuse your existing SSH keys and get remote Docker "for free," with a smaller attack surface than opening a tcp:// port. The cost is that every request pays SSH's per-connection overhead.

Subtlety

The precedence gotcha the code reveals

Step 1 · Explain

You now have two ways to aim the client: pick a saved context, or set DOCKER_HOST directly. What happens when both are set? The documentation lists a tidy order, but the actual resolver has a short-circuit worth knowing, because it silently overrides your selected context.

Step 2 · The source
The part that does the job

The two highlighted lines are the trap: if --host or DOCKER_HOST is set, the function returns DefaultContextName before ever looking at DOCKER_CONTEXT or your saved current context. So a stray DOCKER_HOST in your shell profile will quietly send commands to default (your local daemon) even though docker context use prod made "prod" current. And setting --context and --host together is rejected as ambiguous.

Where this corrects the familiar version

People assume "the current context always wins unless I override it for one command." The code says otherwise: DOCKER_HOST isn't a peer of contexts, it bypasses them by forcing default. If a remote command mysteriously runs locally, the first thing to check is echo $DOCKER_HOST — not your context.

Where we are

Summary

A context is a saved name for a connection target — a Host string plus TLS material, stored as JSON under ~/.docker/contexts/. Selecting one just changes what the Lesson-2 client connects to. The one real mechanism here is the ssh:// transport: instead of exposing a network port, the CLI runs ssh as a subprocess, uses its stdio as the "connection," and has the remote run the hidden docker system dial-stdio byte-pump into the remote's own local socket — so remote Docker rides entirely on SSH's existing security. And watch the precedence: DOCKER_HOST silently forces the default context, ahead of DOCKER_CONTEXT and your saved selection.
