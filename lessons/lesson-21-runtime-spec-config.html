config.json: the blueprint runc executes

One file pulls the whole course together. The image's defaults, your run flags, and every isolation primitive — namespaces, cgroups, capabilities, seccomp — all land here, as the exact instructions runc follows to build one container.

The idea in one sentence

The runtime spec config.json is the fully resolved blueprint for one container — what to run, which filesystem, and every isolation setting — assembled from the image's defaults plus your docker run flags.

1 Start here

Image config vs runtime spec: template vs instructions

Plain version: the image config says what the image prefers; config.json says what this one container will actually do. Defaults vs. the final order.

Don't confuse the two "configs." The image config (Lesson 18) is a set of defaults baked into the image — "by default, run nginx, as this user, with this PATH." The runtime spec config.json is the resolved, concrete instruction set for a single container: the exact command, the exact uid, the exact rootfs path, the exact namespaces and limits. The daemon produces the runtime spec by taking the image's defaults and overlaying your choices (docker run -e, -v, --memory, -u…) plus its own built-in defaults. One is a template; the other is the order runc carries out.

2 What to run

The process section

Plain version: this is the "what command, as whom, with what environment" part — and it's mostly filled from the image config.

The process object (config.md#process) holds args (the command — from the image's Entrypoint + Cmd), env (from the image's Env plus your -e flags), cwd (from WorkingDir), and user (from User, or your -u). On Linux it also carries capabilities (Lesson 11) and rlimits. So the image config's runtime defaults from Lesson 18 land here, resolved against your flags.

3 The filesystem

The root and mounts sections

Plain version: this is where the whole storage half of the course plugs in — the merged overlay directory becomes the container's root.

The root object (config.md#root) has a path — and this is the payoff of all of Part III: root.path is the merged OverlayFS directory that the snapshotter's recipe produced (the pipeline we traced). The mounts array (config.md#mounts) then adds everything else the container needs mounted: the pseudo-filesystems /proc, /sys, /dev, plus any volumes or bind mounts you asked for. So "images at rest" (Lessons 15–20) connect to "container running" right here — as two fields.

4 The convergence

The linux section — where the whole course meets

Plain version: every isolation feature you've learned is a single field in here. This one section is Part II.

The linux object (config-linux.md) is the striking one: it collects every isolation primitive from the course into named fields. namespaces (Lessons 6–8) lists which namespaces to create; uidMappings/gidMappings (Lesson 7) define the user-namespace mapping; resources (Lessons 9–10) holds the cgroup limits; seccomp (Lesson 12) holds the syscall filter; and maskedPaths/readonlyPaths hide or protect sensitive kernel files. Everything you studied as a separate mechanism is, to runc, one field in this object.

5 Who builds it

The bundle: config.json + rootfs

Plain version: the daemon writes config.json next to the rootfs; that pair is a "bundle," and a bundle is exactly what runc takes as input.

The daemon (via containerd) assembles config.json by merging three sources — the image config's defaults, your docker run flags, and its own built-in defaults (a default seccomp profile, a default capability set, the standard /proc and /sys mounts, the standard masked paths). It writes the result into a directory alongside the container's root filesystem. That directory — config.json + rootfs — is an OCI bundle, and a bundle is precisely runc's input: point runc at a bundle and it builds the container the spec describes.

Why this file is the center of everything

Every earlier lesson was really describing a field in this file. Namespaces, cgroups, capabilities, seccomp, the rootfs, the process — separate mechanisms in the kernel, but one JSON document to runc. If you understand config.json, you understand what a "container" concretely is: a process launched against this exact set of instructions.

Where this corrects the familiar version

"Docker configures the container" is vague; concretely, the daemon writes a single config.json and runc does the rest. And the two configs are genuinely different files with different jobs — mixing them up is why people expect docker run flags to change the image (they don't; they change this container's runtime spec). The image is immutable defaults; the runtime spec is where your intent for one container actually lives.

Where we are

Summary

The runtime spec config.json is the resolved blueprint for a single container, and it's where the whole course converges. process holds the command, environment, user, and capabilities (largely from the image config); root.path is the merged OverlayFS directory from the storage pipeline and mounts adds the pseudo-filesystems and volumes; and linux gathers namespaces, uid/gid mappings, cgroup resources, and seccomp — every isolation primitive as a field. The daemon merges the image's defaults, your run flags, and built-in defaults into this one file, writes it beside the rootfs to form a bundle, and hands the bundle to runc.
