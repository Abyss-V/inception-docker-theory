Build context & .dockerignore

What the dot in docker build . means, which files BuildKit may read, and why “available to the build” is not the same as “copied into the image.”

The idea in one sentence

The build context is the outer boundary of files the build may use; the Dockerfile asks for paths inside that boundary, and .dockerignore removes paths before the local context is synchronized to BuildKit.

1 Start with one project

Four files, three different decisions

Imagine this directory:

shop/ ├── Dockerfile ├── app.py ├── notes.txt └── secret.env

And this Dockerfile:

FROM python:3.13-slim WORKDIR /app COPY app.py . CMD ["python", "app.py"]

You run:

docker build . ↑ this dot selects shop/ as the context root

Now separate three questions that are often mixed together:

1

What is inside the allowed source boundary?

Everything under shop/. A path outside it, such as ../private.txt, is not an available local source.

2

What does this build actually ask for?

The local COPY asks for app.py. Merely being inside the context does not put a file into the image.

3

What does the ignore policy remove?

If .dockerignore excludes secret.env, that path is removed from the default local context available to ordinary COPY and ADD.

files synchronized = paths requested by the reachable build ∩ context boundary − ignored paths
Most important distinction. The context is not “the files that become the image.” It is the source filesystem from which build operations are allowed to obtain files.
2 The dot and the Dockerfile

The context and the Dockerfile are separate inputs

The command shape is:

docker build [OPTIONS] PATH | URL | - ↑ the final argument selects the context

With docker build ., the current directory is the default context root. A source in local COPY or local ADD is interpreted relative to that root.

The Dockerfile can live somewhere else:

docker build -f docker/prod.Dockerfile . Dockerfile ↑ ↑ context root

The instructions come from docker/prod.Dockerfile, but COPY app.py /app/ still reads ./app.py from the context root—not from ./docker/.

Keep this pair separate

Dockerfile: what operations to perform.
Context: which source filesystem those operations are allowed to address.

Parent traversal does not grant access outside the boundary. A source such as COPY ../private.txt /x is cleaned as a context-relative path; it does not expose the parent directory of the context.

3 What BuildKit does

It reads the plan first, then requests the needed source

First-read version: BuildKit does not have to upload the whole directory before it understands the Dockerfile. It obtains the Dockerfile first, resolves the part of the build graph that will run, then requests a filtered view of the local context.

1
Obtain the Dockerfile and applicable ignore file
These control files are requested separately so the frontend can understand the build before requesting the main source tree.
2
Resolve the reachable build stages
Only stages needed for the selected target contribute operations to the graph.
3
Collect default-context paths used by local COPY and ADD
COPY app.py . asks for a narrow path. COPY . . asks for the context root, which makes every nonignored path eligible.
4
Apply .dockerignore and synchronize the filtered filesystem
The client-side filesync provider combines the requested paths with exclusions before sending the source over the BuildKit session.

Return to the example. With COPY app.py ., BuildKit can follow the path for app.py. The unused notes.txt and secret.env do not need to be synchronized as requested source content. Change the instruction to COPY . ., and the request becomes the root of the context, so both files become eligible unless ignored.

Correction to the old mental model

“Docker always tars the complete directory and uploads it before reading the Dockerfile” describes the legacy builder model, not the general modern BuildKit path. BuildKit uses a session-backed filesystem synchronization with path-following and exclusion filters. A broad COPY . . can still produce a whole-context-sized transfer, but that happens because the build requested the root.

You can stop here on a first read. The remaining sections explain the ignore file precisely, then cover the less-common context forms and source-level edge cases.
4 The ignore file

.dockerignore removes paths from the default context

Add this file beside the context root:

notes.txt secret.env

Now the default context seen by local build operations no longer contains those two paths. The result for the sample tree is:

Dockerfile
Control input. BuildKit obtains it through the entrypoint request.
app.py
Not ignored; available to COPY app.py ..
notes.txt
Excluded from the default context by .dockerignore.
secret.env
Excluded from the default context by .dockerignore.

This matters even if the Dockerfile currently copies only app.py. Ignore rules protect against a later broad wildcard such as COPY . ., reduce source work, and remove irrelevant files from cache inputs.

Not a secret manager. Ignoring a credential is a useful boundary, but a typo can admit it. Build credentials should use BuildKit secret mounts rather than being copied into the context and image layers.
5 Pattern rules

Read the file from top to bottom; the last matching rule wins

The most useful patterns are:

node_modules # exclude a matching path or directory *.log # * matches inside one path component temp? # ? matches one non-separator character **/generated/** # ** may cross directory levels !logs/keep.log # include this path again

Example:

*.log # first: exclude every matching log !logs/keep.log # later: include this one again

logs/keep.log matches both lines. The second match comes later, so its final state is included. That is the practical meaning of last matching rule wins.

Small differences from .gitignore

A leading / is removed, so /foo/bar and foo/bar are equivalent relative to the context. A line is a comment only when # is the first character before trimming. The special pattern . does not exclude the context root.

6 One Dockerfile can have its own policy

The sidecar ignore file replaces the root file for that build

Suppose the project has:

shop/ ├── .dockerignore └── docker/ ├── prod.Dockerfile └── prod.Dockerfile.dockerignore

When the selected Dockerfile is docker/prod.Dockerfile, BuildKit checks for docker/prod.Dockerfile.dockerignore. If that sidecar exists, it is the ignore policy for the build. The root .dockerignore is only the fallback; the two files are not merged.

7 Two filters that solve different problems

.dockerignore is global; COPY --exclude is local to one instruction

.dockerignore

Removes a path from the default context. Later local COPY and ADD operations cannot obtain that path from the default context.

COPY / ADD --exclude

Keeps the path in the source but omits it from this one file-copy operation. Another operation may still use it.

# tests still exist in the context COPY --exclude=tests src/ /app/ COPY tests/ /tests/ # still possible

If tests were in .dockerignore, the second instruction could not retrieve it from the default context.

8 Context is a role, not always a directory

Local paths are common, but not the only source

Context formMeaning
local pathThe client exposes a local filesystem to BuildKit over the session.
local tar / stdinThe archive becomes the context. Plain Dockerfile text on stdin can mean no filesystem context.
Git URLA Git checkout becomes the source filesystem.
remote tar URLThe BuildKit daemon host downloads the archive; with a remote builder, that may not be the CLI machine.
named context--build-context docs=./docs creates another separately-addressed source.

Named contexts are useful when one build graph needs several sources without making one giant default boundary. A Dockerfile can address a named context with COPY --from=docs or a build mount.

Inspect it yourself

Watch one narrow request become broad, then narrow again

This experiment creates one small file and one 16 MiB file. The Dockerfile first requests only the small file, then requests the context root, then ignores the large file.

Observe the relationship, not an exact byte count. Progress formatting and metadata reuse vary by Docker/Buildx version. The broad case should include the large file; the ignored case should not.

Check yourself

  • The final argument in docker build . selects the context root.
  • The context is the builder's permitted source filesystem, not the set of files automatically copied into the image.
  • The Dockerfile and context are separate inputs; local source paths are rooted at the context.
  • Modern BuildKit reads the plan, derives paths used by reachable local COPY/ADD, applies ignore rules, then synchronizes the filtered source.
  • COPY . . requests the root and therefore makes every nonignored path eligible.
  • A Dockerfile-specific <Dockerfile>.dockerignore replaces the root ignore policy for that build.
  • Ignore rules are ordered: the last matching rule wins, and ! re-includes.
  • .dockerignore is global to the default context; COPY --exclude affects one file operation.

Summary

The context answers “what source filesystem may this build use?” The Dockerfile answers “which operations should use it?” For the local BuildKit path, the frontend obtains the build definition first, resolves the reachable graph, derives the local paths requested by COPY and ADD, combines them with .dockerignore, and synchronizes the filtered result.
