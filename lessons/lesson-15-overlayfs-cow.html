OverlayFS & copy-on-write: how a container gets a filesystem

An image is a stack of read-only layers. This is the filesystem trick that lets fifty containers share those layers instantly, each writing to its own thin top layer — and it's the substrate every image concept in this part sits on.

Start with the problem. You run fifty containers from the same nginx image. Its root filesystem is a couple hundred megabytes. Copying that fifty times would waste gigabytes of disk and make every docker run slow. What you actually want: all fifty containers share the same read-only image files, and each gets a private, thin writable layer on top for whatever it changes. That's a union filesystem — stack several directories and present them as one — and OverlayFS is the one built into the Linux kernel that Docker uses by default. Two ideas do all the work: stacking (many layers appear as one) and copy-on-write (nothing is copied until it's changed).

Where we are on the map. OverlayFS is a kernel filesystem — right at the boundary where "Docker" ends and "the kernel" begins. We stop at how the kernel behaves and don't go inside its implementation, but you must understand this behavior, because Docker's storage driver is built entirely on top of it and every image layer in the next lessons is defined by it.
Mechanism 1

Four directories: lower, upper, work, merged

An overlay mount is assembled from a small set of directories, and containerd's overlay snapshotter (plugins/snapshots/overlay/overlay.go) builds it by handing the kernel a mount of type overlay with three options — lowerdir=, upperdir=, workdir= — producing a fourth directory, the merged view:

The lowerdir is the read-only stack — the image's layers, listed bottom-to-top and separated by colons. Every container started from that image points its lowerdir at the same layer directories, which is how sharing happens. The upperdir is a single writable directory, unique to this container; every change the container makes lands here. The workdir is an empty directory the kernel uses internally for atomic operations (it must sit on the same filesystem as upperdir) — you never touch it. And merged is the unified result: the directory the container actually sees as its root filesystem.

Reads follow a simple rule: to resolve a path, overlay looks in the upperdir first, then each lowerdir from top to bottom, and the first layer that has the file wins. A file in an upper layer therefore shadows the same path in a lower one — which is exactly how a later image layer can replace a file baked into an earlier layer.

One-layer edge case, from the source. Overlay needs at least two directories to union, so when a snapshot has no parent layers, containerd doesn't build an overlay mount at all — it returns a plain bind mount instead (the len(ParentIDs) == 0 branch). A tidy reminder that the overlay only exists once there's something to stack.
Mechanism 2

Copy-on-write: the first write copies the whole file up

The upperdir is writable and the lowerdirs are not — so what happens when the container modifies a file that only exists in a read-only lower layer? Overlay can't write to the lower layer, so it performs a copy_up: it copies the entire file up into the upperdir, then applies your change to that copy. From then on, the upper copy shadows the lower original, and all further reads and writes hit the upper copy. The lower layer is never touched — which is precisely what makes it safe for many containers to share.

The consequence to remember

Copy-on-write is why containers start instantly and share disk — but it means the first modification of any lower-layer file pays the cost of copying the whole file, no matter how small the edit. For a large file baked into an image, that first write is expensive. The same is true for a chmod, a chown, or creating a hard link — all of them trigger a copy_up. This is the concrete reason big, frequently-written data belongs in a volume, not in the image.

Mechanism 3

Deletes you can't really do: whiteouts

Now the strangest case. The container deletes /etc/nginx/nginx.conf, but that file lives in a read-only lower layer — overlay can't remove it from there. So instead of deleting anything, it creates a whiteout in the upperdir: per the kernel's OverlayFS documentation, a whiteout is a character device with device number 0/0 placed at the deleted path. When overlay sees a whiteout in the upper level, it hides any matching name in the lower levels — the container sees the file as gone, even though it still physically exists in the layer below. Deleting an entire directory that came from a lower layer uses a related trick: an "opaque directory," marked with the xattr trusted.overlay.opaque, which hides the whole lower directory of that name.

Why this matters more than it looks

Because a delete is really an addition (a whiteout marker on top), removing a file never reclaims the space it occupied in a lower layer. This is the seed of two facts you'll meet soon: a RUN rm -rf ... in a Dockerfile doesn't shrink the image — the data still sits in the earlier layer (Lesson 31), and a secret written and then deleted in a later layer is still recoverable from the layer that added it (Lesson 30). The whiteout hides; it doesn't erase.

Where this corrects the familiar version

The everyday phrase "each container gets its own copy of the filesystem" is exactly backwards: containers get their own writable layer and share everything else read-only, copying individual files up only on first write. Two practical corrections fall out. First, deleting files inside a container (or in a Dockerfile layer) doesn't free the underlying space — it writes a whiteout on top. Second, the "first write is cheap" intuition is wrong for large files: the entire file is copied up before your edit lands, which is why write-heavy big data belongs in a volume. Overlay makes containers cheap by not copying — right up until you force it to.

Where we are

Summary

A container's filesystem is a union: OverlayFS stacks the image's read-only layers (lowerdir, colon-separated, searched top-down) under a single writable upperdir, with a hidden workdir for atomic operations, and presents the result as merged — the container's root. containerd's overlay snapshotter builds exactly this mount. Reads resolve to the first layer that has the file, so upper shadows lower; writes to a lower-layer file trigger copy_up, duplicating the whole file into the upperdir before editing (cheap sharing, but an expensive first write on large files); and deletes are whiteouts — character devices numbered 0/0 that hide a lower file without erasing it. Those three behaviors — union reads, copy-up writes, whiteout deletes — are the entire physics of container storage, and they set up everything ahead: next, the landscape of snapshotters and storage drivers that manage these layers, and then, in Lesson 17, what an image layer physically is as bytes on disk — where whiteouts reappear as tar entries.
