Part 6 · Distribution · Lesson 40

Tags vs digests, content-addressed transfer & dedup

The important transition is simple: Docker starts with a human name such as course/app:stable. The registry turns that mutable name into a descriptor for exact bytes. From that moment onward, the digest in the descriptor is the key used to find, verify, store, reuse, and push those bytes.

CORE
governing idea

A tag answers “which object do you mean right now?” A digest answers “which exact bytes do you mean?”

This lesson needs only one relationship to stay in your head:

mutable name
course/app:stable
        │ registry resolves the name
        ▼
root descriptor
{ digest: sha256:7f3a…, size: ..., mediaType: ... }
        │ digest now names exact root bytes
        ▼
content graph
manifest → config + layer descriptors

Lessons 18 and 19 already taught descriptors, manifests, and indexes. Lesson 22 taught containerd's content store. Lesson 39 taught the registry HTTP endpoints. We are not repeating those lessons. We are connecting them around one question: when does an object's byte body actually need to move?

whole movement first

1. The entire pull, with only one root manifest

We will first use a single-platform image so there is no image index to distract from the core mechanism.

Assume the registry currently has this relationship:

repository:  registry.example.com/course/app

tag:         stable
              │
              └── points to root manifest bytes
                     digest sha256:7f3a…

root manifest sha256:7f3a… contains descriptors for:
  config      sha256:19bc…
  layer A     sha256:52de…
  layer B     sha256:8a41…

The important split is before the body transfer: the descriptor arrives first; its digest lets containerd decide whether the body is needed.

Resolution gives containerd an expected identity before the content body is transferred.

2. Tag resolution: what exactly happens to :stable?

Start with:

docker pull registry.example.com/course/app:stable

The Docker CLI sends that image reference to dockerd. dockerd starts the image pull through containerd. The important work for this lesson begins in containerd's registry resolver.

1

containerd sees a tag, not a digest

The reference has an object name stable, but no @sha256:... digest. In containerd v2.2.6, dockerResolver.Resolve therefore builds a manifests path using the tag:

/v2/course/app/manifests/stable
2

containerd asks the registry what object that tag selects now

The normal request is a HEAD. No image layer bytes are involved. This is a name-resolution request.

HEAD /v2/course/app/manifests/stable
3

the registry returns metadata for the selected root bytes

The useful response metadata includes the content digest, content length, and media type. containerd turns those values into an OCI descriptor:

Descriptor {
    Digest:    sha256:7f3a…
    Size:      742
    MediaType: application/vnd.oci.image.manifest.v1+json
}

This descriptor is the result of resolving the tag. The tag text itself is not hashed to produce 7f3a…. The digest identifies the manifest bytes that the registry says stable currently selects.

important correction

Do not imagine a tag as another OCI blob sitting above the manifest. In this lesson, the tag is a registry-level name used at the manifests endpoint. Resolution produces a descriptor for the root content. After that, the content graph is followed through descriptors and digests.

If the registry does not provide enough metadata for containerd to build the descriptor—specifically the digest or usable size—containerd falls back to GET and hashes the returned manifest bytes to establish the digest. That fallback does not change the model: the end product of resolution is still a descriptor for exact root bytes.

Source anchor: containerd v2.2.6 · core/remotes/docker/resolver.go · dockerResolver.Resolve

3. Why a tag can move but the digest cannot keep identifying changed bytes

Suppose today the registry has:

stable → manifest bytes A → sha256:7f3a…

Tomorrow you push a new release under the same tag:

stable → manifest bytes B → sha256:c901…

The name stable stayed the same. The selected bytes changed, so the digest changed.

Tag
stable
registry-controlled mapping; can be changed to another root object
→
Digest
sha256:7f3a…
calculated from one byte sequence

If even one byte of that manifest changes, recalculating its hash produces a different digest. That is what gives the digest its role as a content identifier.

what “immutable digest” really means

It does not mean somebody placed a lock bit on a digest string. It means the digest is derived from the bytes. Changed bytes no longer match the old digest. The old digest continues to identify the old byte sequence.

Source anchor: OCI Image Spec v1.1.1 · descriptor.md · Digests / Verification

4. Pull dedup: the digest is checked before the registry body is opened

Now containerd has the root descriptor:

expected digest = sha256:7f3a…

The next question is not “download the manifest.” The next question is:

Does the local content store already contain sha256:7f3a… ?
1

Fetch opens the destination first

containerd's remotes.Fetch calls content.OpenWriter(..., content.WithDescriptor(desc)) before it calls fetcher.Fetch. The expected descriptor therefore reaches the content store before any registry response body is requested.

2

the local store converts the digest to its content path

For the expected digest, the local store derives a path of this form:

<content-root>/blobs/sha256/<encoded digest>

for our example:
<content-root>/blobs/sha256/7f3a…

If that final blob path already exists, store.writer returns ErrAlreadyExists.

3

ErrAlreadyExists short-circuits the fetch

FetchHandler treats that result as success. Because OpenWriter failed with “already exists,” execution never reaches fetcher.Fetch for that object.

dedup point

This is the exact pull-side dedup decision: expected descriptor digest → digest-derived local path → path exists → do not request that object's body.

A tag lookup may still have crossed the network. Dedup here means the object body is not transferred again; it does not mean the entire pull operation becomes network-silent.

Source anchors: containerd v2.2.6 · core/remotes/handlers.go · FetchHandler / Fetch; plugins/content/local/store.go · writer / blobPath

5. If the object is missing: the same digest becomes the verification target

Assume sha256:7f3a… is not local. Only now does containerd need the body.

expected descriptor digest: sha256:7f3a…
            │
            ▼
registry sends manifest bytes
            │
            ▼
containerd writes bytes into an ingest file
and updates a SHA-256 digester as bytes arrive
            │
            ▼
Commit(expected = sha256:7f3a…)
            │
      calculated digest?
       /            \
  7f3a…              anything else
   │                      │
 accept                  reject
   │
   ▼
move ingest data to final digest-derived blob path

There are two different uses of the digest here, and keeping them separate matters:

MomentWhat the digest does
Before transferIt is the expected identity: “I need exactly 7f3a….”
After bytes arrivecontainerd independently hashes the received bytes and checks that the calculated digest equals the expected one.

In the local writer, Write writes the bytes and feeds the same bytes to the digester. At Commit, containerd compares the calculated digest with the expected descriptor digest. A mismatch is rejected. Only verified content is moved to the final path derived from its digest.

not one vague “hash step”

The digest participates in lookup before transfer and in verification after transfer. Those are different decisions at different times.

Source anchor: containerd v2.2.6 · plugins/content/local/writer.go · Write / Commit

6. How the same decision walks the whole image graph

Once the root manifest bytes are local—either reused or freshly fetched—containerd can read that JSON. The manifest contains child descriptors, for example:

root manifest sha256:7f3a…

config descriptor
  digest = sha256:19bc…

layer descriptor A
  digest = sha256:52de…

layer descriptor B
  digest = sha256:8a41…

Now the exact same per-object loop repeats for each child:

descriptor arrives
      ↓
use desc.Digest as expected identity
      ↓
check local content store
      ├─ present → reuse → no body transfer
      └─ missing → fetch body → hash → verify → commit

This is why saying “Docker deduplicates layers” is incomplete. The mechanism is not special to layers. The content store and transfer handlers operate on descriptors. A manifest, config blob, or layer blob can all be reused when the exact descriptor digest is already present.

where an image index fits

If the tag resolves to an image index instead of directly to an image manifest, nothing fundamental changes. The root descriptor identifies the index bytes. containerd obtains the index, selects the platform manifest descriptor as taught in Lesson 19, then runs the same digest-driven loop for that manifest and its children. The index adds one graph hop; it does not add a different dedup mechanism.

7. Four jobs performed by the same descriptor digest

At this point the phrase “content-addressed” should be concrete. For a descriptor such as sha256:52de…, that digest participates in four distinct operations:

JobQuestion answeredWhere
IdentityWhich exact layer/config/manifest bytes does this descriptor refer to?OCI descriptor
Local lookupDo I already have those exact bytes?containerd content store, digest-derived blob path
VerificationDid the bytes I received actually hash to the expected identity?containerd ingest + Commit
Remote existenceDoes the destination registry already expose this exact content?registry HEAD during push

One digest value can serve all four jobs because all four are asking about the same byte identity.

8. Dedup cases on pull: exactly what is compared, and what moves?

Case A — two tags point to the same root manifest

stable ─┐
        ├──→ sha256:7f3a…
prod   ─┘

Pulling :stable first stores the graph. Later, pulling :prod still requires resolving prod, because a tag is mutable. Suppose that resolution also returns root digest 7f3a….

containerd checks its local path for 7f3a…. It is already present, so the root manifest body need not move again. When the graph is walked, the same is true for the existing child digests.

Case B — two different manifests share one config blob

manifest A → config sha256:19bc…
manifest B → config sha256:19bc…

The manifests themselves may have different digests. When traversal reaches the config descriptor in manifest B, its expected digest is exactly the same 19bc…. The local content-store lookup finds that object and skips a second config-body transfer.

Case C — two images share a layer

image A manifest → layer sha256:52de…
image B manifest → layer sha256:52de…

Same mechanism. The compared identifier is the layer descriptor's digest. If it matches an already-local blob path, those layer bytes do not move again.

Case D — “same files” but different blob bytes

Suppose two compressed layer archives would unpack to equivalent files, but their stored archive bytes differ. Then their descriptor digests differ.

layer archive bytes A → sha256:52de…
layer archive bytes B → sha256:aa90…

For this transfer/content-store mechanism, they are two different objects. There is no semantic filesystem comparison that says “these unpack to the same thing, so merge them.”

precise rule

Transfer dedup happens at exact content identity. Same descriptor digest → same referenced bytes → reusable object. Different descriptor digest → distinct object for this mechanism.

9. Push dedup: ask the registry before opening the local payload

Lesson 39 showed that child blobs are made available before their parent manifest. Zoom in on one layer descriptor:

layer descriptor
Digest = sha256:52de…

containerd's registry pusher first checks the destination repository:

HEAD /v2/course/app/blobs/sha256:52de…
1

registry returns 200 OK

The pusher marks that exact descriptor as already present and returns ErrAlreadyExists.

2

the higher push handler stops before reading the payload

In remotes.push, pusher.Push(desc) occurs before provider.ReaderAt(desc). If the pusher reports “already exists,” the function returns success before opening the local content body.

descriptor sha256:52de…
        ↓
registry HEAD by exact digest
        ├─ 200 → already exists → STOP
        │                       payload bytes read: 0
        │
        └─ 404 → destination lacks it
                 → mount or upload path

Again, dedup does not mean zero traffic. The HEAD request and response are network traffic. What is avoided is retransmitting the blob payload.

Source anchors: containerd v2.2.6 · core/remotes/docker/pusher.go · push; core/remotes/handlers.go · push

10. Pushing a second tag: why a manifest may still move

Suppose the registry already has:

stable → sha256:7f3a…

You push the same local root under a new tag:

prod → sha256:7f3a…

All child blobs may already be present, so their HEAD checks can skip every child payload. But the registry still needs the new name prod to select the root object.

For a tagged manifest/index push, containerd checks the manifests path for that target object. If the tag does not already resolve to the desired digest, it sends the root manifest/index bytes with a PUT to establish that tag mapping.

important distinction

Content dedup and name creation are different jobs. “The registry already has every blob” does not automatically mean “the registry already has this new tag pointing to the desired root.”

11. Cross-repository blob mount: reuse when the blob exists elsewhere on the same registry

This is the one dedup case that is different from “the target repository already has it.”

Assume you are pushing to:

registry.example.com/course/app

The target repository does not expose layer sha256:52de…, but Docker knows that the same registry previously had that exact blob through another repository:

registry.example.com/course/base

The OCI Distribution Spec allows the client to ask the registry to reuse it:

POST /v2/course/app/blobs/uploads/
     ?mount=sha256:52de…
     &from=course/base
ResultMeaningBlob payload from this client?
201 CreatedThe registry mounted/reused that exact blob for the target repository.No.
mount not completed; upload session continuesThe client must use the normal upload path.Yes, if the upload proceeds.

The split of responsibility on the pinned Docker Engine path matters:

  1. dockerd looks at previously recorded distribution-source metadata and identifies missing non-manifest content that may be mountable from another repository on the same registry.
  2. containerd's registry pusher receives that source-repository candidate and sends the actual mount request containing the exact descriptor digest and the source repository.
  3. The registry decides whether the mount succeeds. If not, normal upload remains the fallback.
do not overgeneralize

Docker is not asking the registry, “search all repositories for similar layers.” It has a specific source-repository candidate and a specific blob digest. The registry is asked to reuse exactly that content.

Source anchors: OCI Distribution Spec v1.1.1 · Mounting a blob from another repository; Docker Engine docker-v29.6.2 · daemon/containerd/image_push.go · findMissingMountable / canBeMounted; containerd v2.2.6 · core/remotes/docker/pusher.go · mount branch

13. Pulling by digest: what changes compared with pulling by tag?

Compare:

registry.example.com/course/app:stable

registry.example.com/course/app@sha256:7f3a…

With :stable, containerd must ask the registry which root digest that mutable tag selects now.

With @sha256:7f3a…, the desired root identity is already in the reference. containerd validates the digest and requests that identity. There is no mutable tag-to-root choice to resolve.

The content may still need to be fetched if it is not local. A digest reference removes the mutable name-selection step; it does not magically make missing bytes local.

mental model

:stable means “tell me which root object this name selects now.” @sha256:7f3a… means “the selected root object must be this exact content identity.”

14. Inspect it yourself

The cleanest experiment is a local registry because its logs let you separate name-resolution/existence traffic from payload transfer.

terminal 1 — run a local registry and watch requests
docker run -d --rm --name lesson40-registry -p 5000:5000 registry:2
docker logs -f lesson40-registry
terminal 2 — push one image under two tags
docker pull alpine:latest

docker tag alpine:latest localhost:5000/course/app:stable
docker push localhost:5000/course/app:stable

docker tag alpine:latest localhost:5000/course/app:prod
docker push localhost:5000/course/app:prod

On the second push, look for existence checks for content already in the repository. The child blobs should not need a second payload upload. The new tag may still require a manifest/index PUT.

Prove the two tags currently resolve to the same root digest

curl -sI \
  -H 'Accept: application/vnd.oci.image.index.v1+json, application/vnd.oci.image.manifest.v1+json, application/vnd.docker.distribution.manifest.list.v2+json, application/vnd.docker.distribution.manifest.v2+json' \
  http://127.0.0.1:5000/v2/course/app/manifests/stable \
  | grep -i docker-content-digest

curl -sI \
  -H 'Accept: application/vnd.oci.image.index.v1+json, application/vnd.oci.image.manifest.v1+json, application/vnd.docker.distribution.manifest.list.v2+json, application/vnd.docker.distribution.manifest.v2+json' \
  http://127.0.0.1:5000/v2/course/app/manifests/prod \
  | grep -i docker-content-digest

If the headers match, you have directly observed two different tag names selecting the same root content identity.

Observe containerd's local content identities

sudo ctr namespaces list
sudo ctr -n moby content ls | head -30

On a typical Docker Engine installation the containerd namespace is moby. The exact content-store root is installation dependent, but the implementation's final blob-path suffix is digest-derived:

blobs/<algorithm>/<encoded-digest>

Pull both tags and compare the registry log

docker pull localhost:5000/course/app:stable
docker pull localhost:5000/course/app:prod

The second pull can still contain tag-resolution metadata traffic. Objects already present in the local content store can skip their body transfer because containerd already knows their expected digests.

Exact audit anchors behind the explanation

Tag definition: OCI Distribution Spec v1.1.1, Definitions: a tag is a custom human-readable pointer to a manifest; a manifest digest may have zero, one, or many tags.

Digest meaning: OCI Image Spec v1.1.1, descriptor.md, Digests: descriptor digest acts as the content identifier, and untrusted bytes are verified by independently recalculating the digest.

Tag → root descriptor: containerd v2.2.6 core/remotes/docker/resolver.go::dockerResolver.Resolve. For a tag, the resolver uses the manifests path and normally issues HEAD. It uses Docker-Content-Digest, response size, and media type to assemble the descriptor; if digest/size metadata is insufficient, it falls back to GET and derives the digest from the body.

Local dedup before fetch: containerd v2.2.6 core/remotes/handlers.go::Fetch calls content.OpenWriter before fetcher.Fetch. plugins/content/local/store.go::writer maps the expected digest through blobPath and returns ErrAlreadyExists when that target already exists.

Verification: containerd v2.2.6 plugins/content/local/writer.go::Write feeds incoming bytes into the digester; Commit compares the computed digest with expected before targeting the digest-derived final blob path.

Push-side skip: containerd v2.2.6 core/remotes/docker/pusher.go::push sends a remote HEAD for the descriptor. core/remotes/handlers.go::push returns on ErrAlreadyExists before provider.ReaderAt, proving the local payload is not opened on that path.

Tagged manifest existence: containerd v2.2.6 pusher.go::getManifestPath uses the tag path when pushing to a tag. When a HEAD succeeds on a tag path, the pusher only considers the desired manifest already present when Docker-Content-Digest equals the descriptor digest being pushed.

Cross-repository mount: OCI Distribution Spec v1.1.1 defines POST /v2/<name>/blobs/uploads/?mount=<digest>&from=<other_name>. Docker Engine docker-v29.6.2 daemon/containerd/image_push.go::findMissingMountable and canBeMounted prepare eligible same-registry non-manifest candidates; containerd's pusher sends the mount request and falls back to upload when needed.

  1. When you pull course/app:stable, is stable itself a content digest?
  2. What concrete object does tag resolution produce for containerd?
  3. Does containerd hash the string stable to obtain the root digest?
  4. Why can containerd decide not to fetch a body before it has that body?
  5. On a local content-store hit, what exact event prevents fetcher.Fetch from being reached?
  6. After missing bytes arrive, what is compared at commit time?
  7. If two images share a layer, what must be equal for this transfer dedup mechanism to reuse it?
  8. Why can two tags share every image byte yet still require two separate tag-resolution requests?
  9. On push, why does a successful remote existence check avoid even opening the local payload?
  10. How is cross-repository mount different from “the target repository already has the blob”?

Answers
  1. No. It is a mutable repository-level lookup name.
  2. A root OCI descriptor containing the selected content's digest, size, and media type.
  3. No. The digest identifies the selected root bytes. In the normal HEAD path it comes from registry metadata; the GET fallback can derive it from the returned content.
  4. Because the descriptor arrives first and already contains the expected digest. The local store can check the digest-derived final path before requesting the body.
  5. store.writer finds the expected digest path and returns ErrAlreadyExists; FetchHandler treats that as success.
  6. The digest calculated from the received bytes is compared with the expected descriptor digest.
  7. The layer descriptor digest must be exactly the same.
  8. Because each tag is mutable; containerd must ask what each name selects now. Dedup skips repeated content bodies, not mutable-name resolution.
  9. The pusher returns ErrAlreadyExists from the existence check, and the higher push function returns before provider.ReaderAt.
  10. Target-repository existence is proven directly with HEAD. A mount asks the registry to make an exact blob known from a different repository available to the target without client re-upload.
  11. The content may already exist, but the new tag mapping may not. The root manifest/index PUT can establish that mapping.

If you remember only one sentence, remember this: the tag is used to select the first content identity; the digest then becomes the reusable key for the content itself.
