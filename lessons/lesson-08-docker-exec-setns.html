docker exec: joining a container you already have

Lesson 6 built namespaces from nothing with clone. This is the exact mirror: a new process that joins the namespaces a running container already owns, using one syscall — setns(2). It's the same primitive from the other direction, and the ordering rules flip to match.

When you run docker exec -it web sh and get a shell that sees the container's files, its network, its processes — you are not making a new container. You are dropping a brand-new process into the existing namespaces of a running one. Understanding how turns out to reinforce everything from Lessons 6 and 7, because "joining" is just "getting the same namespace inode you saw before," and the privilege ordering is the userns rule running in reverse.

The intuition

Why joining needs a different syscall than creating

Think about what you actually want from docker exec. Not a fresh, empty network namespace — you want the container's own network, with its interfaces and its IP. Not a new PID namespace numbering from 1 — you want to see the container's running processes. So clone(CLONE_NEWNET) is exactly wrong: it would manufacture a new empty namespace, when you need to attach to a specific existing one.

That's the whole reason a second syscall exists. setns(2) means "take this process and make it a member of an already-existing namespace, identified by a file descriptor." You get the fd by opening the target namespace as a file — and Lesson 6 already showed where those files live: /proc/<pid>/ns/. So docker exec reduces to: find the container's init process, open its namespace files, and setns a new process into each. Let's watch runc make exactly that decision.

Mechanism 1

One if: create a container, or join one

Step 1 · Explain

runc uses the same code to start a container's first process and to exec into a running one. A single boolean, p.Init, decides which. If this is the container's init process, runc builds a clone-based process that creates namespaces (Lesson 6). Otherwise — a runc exec — it builds a setns process that joins them.

Step 2 · The source
The part that does the job

The two return statements are the entire fork in the road. newInitProcess is the Lesson-6 path: clone() with CLONE_NEW* flags, making fresh namespaces. newSetnsProcess is this lesson: no new namespaces created, just joins. Everything else about the two paths — passing the config, wiring stdio — is shared. Create vs join is this one branch.

Mechanism 2

The target is a set of /proc/PID/ns/ files

Step 1 · Explain

To join the container's namespaces, runc needs to point at them. It knows the container's init PID (saved in the container's state when it started), and it turns each namespace into a path with a trivial helper — the same paths you inspected by hand in Lesson 6. It opens each path to get an fd, then calls setns(fd, type). Membership achieved.

Step 2 · The source
The part that does the job

GetPath produces /proc/<container-init-pid>/ns/<type> — the very symlinks whose inodes you compared in Lesson 6. Opening one and passing its fd to setns makes the new process share that exact namespace instance (same inode), which is why an exec'd shell sees the container's network and not a fresh one. The setresuid(0,0,0) after a userns join is a small but vital detail: joining the container's user namespace switches your credential context, so runc immediately re-asserts root within that namespace or, as the source note warns, "lots of things can break."

Mechanism 3

The join ordering: the userns rule, mirrored

Step 1 · Explain

Lesson 6's creation rule was "user namespace first, because it grants the privilege to make the others." Joining has the same principle but a more delicate execution, for two reasons. First, once you setns into the container's mount or user namespace, your view of /proc changes and you may no longer be able to open the remaining namespace paths — so all the fds must be opened up front, before any join. Second, joining the container's user namespace switches your credentials to the container's (possibly unprivileged) user: some namespaces you can only join before that switch (while you still hold host privileges), and — for rootless containers — some you can only join after it (because you gain CAP_SYS_ADMIN inside the new userns). The only way to satisfy both is to split the joins into passes.

Step 2 · The source
The part that does the job

Read the three __join_namespaces calls as three passes: non-userns → userns → leftovers. Pass 1 grabs what needs host privilege before the credential switch; pass 2 enters the userns (flipping you to the container's user); pass 3 catches anything that only became joinable afterward. The __open_namespaces(...) at the top is the safety move — grab every fd while the paths are still reachable, because after pass 2 they may not be. This is the exact inverse of the creation ordering, and the comment even notes it mirrors what nsenter(1) does.

create (Lesson 6): userns first → then the rest # gain privilege, then use it join (this lesson): non-userns → userns → leftovers # before switch, switch, after switch
Mechanism 4

Why exec forks — and gets a normal PID, not 1

Step 1 · Explain

Recall the PID-namespace quirk from Lesson 6: setns into a PID namespace does not move the calling process — it only affects the caller's future children. So after joining the PID namespace, runc must fork; the forked child is the process that actually becomes a member of the container's PID namespace, and that child is what runs your sh. Because it's an ordinary new process joining an already-populated namespace, it gets the next available PID in the container's numbering — something like 14 — not PID 1. Only the container's init process is PID 1; exec'd processes are just additional members.

It's not only namespaces — the cgroup comes too. newSetnsProcess also runs addIntoCgroup, placing the exec'd process into the container's cgroup. So a shell you exec in is bound by the same memory and CPU limits as the container (Lessons 9–10), not just its namespaces. Joining is full confinement, not partial.

The part that does the job

The matching net:[4026532567] inodes are the proof that "join" means "same namespace," exactly as Lesson 6 defined identity. $$ = 14 confirms the fork-and-join produces an ordinary member of the PID namespace, not a second init. And nsenter -t <pid> -m -u -i -n -p is the pure primitive: each flag opens one /proc/<pid>/ns/* file and setnses into it — docker exec with the plumbing stripped away.

Where this corrects the familiar version

"docker exec starts a shell in the container" makes it sound like the container runs the shell. It doesn't. The daemon (via containerd's shim Exec and runc exec) spawns a new host process that setnses into the container's namespaces and cgroup. Two consequences worth holding: the exec'd process is not a child of the container's PID 1 (it's injected from outside), so it isn't reaped by your app's init — and if the container's PID 1 exits, the PID namespace is destroyed and your exec'd shell dies with it. The container didn't launch your shell; the runtime injected it.

Where we are

Summary

docker exec is setns(2). runc chooses between creating and joining with a single branch (p.Init → newInitProcess vs newSetnsProcess). To join, it forms the container's namespace paths /proc/<init-pid>/ns/<type>, opens them, and setnses a new process into each — acquiring the same namespace inodes you compared in Lesson 6. The ordering is the userns rule in reverse: open every fd up front (before mnt/user joins cut off access), then join non-userns, then userns, then leftovers, becoming root inside the userns along the way. Because the PID namespace "only applies to children," runc forks so the exec'd process is a true member of the container's PID namespace — with a normal PID, not 1 — and it's dropped into the container's cgroup too, so limits apply. That completes the namespace arc. Next, Part II turns from isolation to limitation: cgroups, starting with v1.
