The run pipeline, end-to-end

Every mechanism in this course, in the order they fire, for a single docker run. This is the lesson where the whole machine finally turns over in one motion.

The idea in one sentence

docker run is a relay: the CLI asks the daemon, the daemon asks containerd, containerd starts a shim, the shim runs runc — and runc turns the runtime spec into a live, isolated process.

You've met every part separately. This lesson runs them in sequence so you can see the handoffs. We'll assume the image isn't present yet, so the full chain fires.

1 The shape

A relay of processes

Plain version: no single program runs your container. Each layer does one job and hands off to the next.

The architecture chain from Lesson 2 is now a sequence of actions: the docker CLI sends an HTTP request to the daemon (dockerd); the daemon drives containerd; containerd launches a shim (Lesson 5); the shim runs runc; and runc becomes — briefly — the parent of your process. Keep this relay in mind; every step below is one hop along it.

2 Get the filesystem

Make the image available (Part III, compressed)

Plain version: before anything can run, the image's layers have to be on disk as snapshots. That's the whole of Part III, in one step.

If the image isn't present, the daemon pulls it — and this is everything from Part III: resolve the tag through its index to the right manifest (Lessons 18–19), download the config and layer blobs by digest into the content store, then unpack each layer bottom-up into a snapshot keyed by its ChainID (Lesson 17 + supplement). When this finishes, the layers exist on disk as committed snapshots, ready to stack.

3 Build the rootfs recipe

Prepare the writable layer and its mounts

Plain version: containerd stacks the image's snapshots and adds a writable layer on top, producing the mount recipe for this container's root.

containerd asks the snapshotter to Prepare an active snapshot on the image's top ChainID — the container's writable layer (Lesson 16). The snapshotter walks the parent chain and returns the mount recipe (lowerdir/upperdir/workdir). That recipe becomes the container's root.path and overlay mount in the runtime spec — the storage-to-runtime bridge from Lesson 21.

4 Assemble the order

The runtime spec and the bundle

Plain version: the daemon writes the one config.json that says exactly what to run and how to isolate it, next to the rootfs.

The daemon merges the image config's defaults (Entrypoint, Env, User…), your docker run flags, and its built-in defaults (seccomp profile, capability set, standard mounts) into the runtime spec config.json (Lesson 21). That file plus the rootfs is the bundle — runc's input.

5 Create, then start

Where namespaces are born, and where your program runs

Plain version: "create" builds the isolated but empty container; "start" flips the switch that runs your program. Two distinct steps.

This is the crux we grounded earlier. containerd's NewTask launches the shim, and the shim runs runc create against the bundle: runc clones with the CLONE_NEW* flags from the spec's namespaces, sets up cgroups, and leaves an init process waiting — the container is now in the created state (moby daemon/start.go: NewTask → initializeCreatedTask). Namespaces and cgroups are made here, at create. Then the daemon calls tsk.Start(), which drives runc start: it calls Exec() to unblock the waiting init, which execves your actual program. Your process is now PID 1 inside all those namespaces.

Why the split matters. Because namespaces exist after create, you can wire up a container (join its network, inspect it) before its program ever runs. And it's why docker start on a stopped container rebuilds everything: it runs a fresh create (new namespaces) then start — the live instance was gone, only the spec survived.
6 After launch

The shim stays; runc leaves

Plain version: runc's job ends once your program is running; the shim sticks around to be the container's parent.

runc is a fork/exec tool — it does its work and exits. The shim (Lesson 5) remains: it's the resident parent of your process, holds the container's I/O, waits for the exit, reaps the zombie, and reports the exit status back up to containerd. This is why the container keeps running with no runc process in sight, and why killing the daemon doesn't kill your container — the shim, not the daemon, is holding it.

The whole course, in firing order

images (III) → snapshot + recipe (15–16) → runtime spec (21) → shim (5) → namespaces + cgroups at create (6–10) → capabilities + seccomp applied (11–12) → your process at start. Every lesson was one stage of this single motion.

Inspect it yourself

Watch the relay: the shim process, no runc in sight, and the bundle runc was given:

Check yourself

  • docker run is a relay: CLI → daemon → containerd → shim → runc → your process.
  • First the image is made available (Part III pull → snapshots on disk), if not already present.
  • containerd Prepares an active snapshot and gets the mount recipe, which becomes the container's root.
  • The daemon assembles config.json; config.json + rootfs = the bundle.
  • create makes the namespaces and cgroups (container "created"); start execs your program (PID 1).
  • runc exits after start; the shim stays as the container's parent and reaps its exit.
Where this corrects the familiar version

"Docker runs the container" hides six actors and two phases. Two corrections worth keeping: namespaces are made at create, not start — start only execs your program into the already-isolated shell; and no long-lived Docker process runs your container — the per-container shim does, which is why containers survive a daemon restart. If you internalize the create/start split and the shim's role, the rest of Docker's runtime behavior stops being surprising.

Where we are

Summary

A single docker run is a relay down the stack: the CLI calls the daemon, which ensures the image is unpacked into snapshots (Part III), has containerd Prepare a writable snapshot and produce the mount recipe, and assembles the runtime spec plus rootfs into a bundle. containerd launches a shim, the shim runs runc create — where namespaces and cgroups are born and the container enters the created state — and then runc start execs your program as PID 1. runc exits; the shim remains as the container's parent.
