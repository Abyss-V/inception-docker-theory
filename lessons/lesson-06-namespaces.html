Namespaces: the eight private views that make a container

A namespace is how the one shared kernel gives a process its own private copy of some global resource. There are eight of them, each one flag. This lesson reads all eight out of runc, the three syscalls that wield them, and the two subtleties that trip everyone up: why the user namespace goes first, and why one process has two PIDs.

Lesson 1 said a container is a process placed in a configured environment, and that the isolation is "a dial." Namespaces are that dial. Now we make it concrete: what a namespace is, the eight kinds, how the kernel creates and joins them, and the two behaviors that seem like magic until you see the source — the user-namespace ordering rule and the "same process, two PIDs" effect.

The intuition

What is a namespace, really?

Normally every process on a machine shares one global version of certain resources. There is one list of process IDs. One filesystem tree rooted at /. One set of network interfaces. One hostname. When you run ps, you see everyone's processes, because PIDs are global.

A namespace is the kernel's mechanism for taking one of those global resources and giving a process a private, independent copy of it. Put a process in a new PID namespace and it now sees its own numbering of processes, starting fresh from 1, with no visibility of anyone outside. Put it in a new network namespace and it gets its own empty network stack — no interfaces except what you add. The kernel maintains each of these private copies internally and tags every process with which copy it belongs to.

The critical thing: namespaces are per-resource. There isn't one "container namespace." There are eight separate namespace types, one for each kind of global resource the kernel learned to partition, and you mix and match them. A container is usually a process placed in a fresh instance of most or all eight at once. Let's see the definitive list — from runc, not memory.

Flag/proc nameThe global resource it gives a private copy of
CLONE_NEWNSmntThe set of mount points — the filesystem tree. This is what lets a container have its own /. (Named "NEWNS" because in 2002 it was the first namespace and there were no others to disambiguate from.)
CLONE_NEWPIDpidProcess IDs. A fresh numbering starting at 1; processes inside can't see or signal processes outside.
CLONE_NEWNETnetThe network stack — interfaces, routing tables, firewall rules, port space. A new net namespace starts with nothing but a loopback. (Covered in Lessons 33–34.)
CLONE_NEWIPCipcInter-process communication objects: System V message queues/semaphores/shared memory and POSIX message queues.
CLONE_NEWUTSutsThe hostname and NIS domain name. (UTS = "UNIX Time-sharing System," the struct these fields historically lived in.) This is why a container can have its own hostname.
CLONE_NEWUSERuserUser and group IDs, and the capability sets. Maps UIDs inside to different UIDs outside — root in the container can be an unprivileged UID on the host. The keystone of the ordering rule below.
CLONE_NEWCGROUPcgroupThe view of the cgroup hierarchy — it virtualizes what the process sees as the cgroup root, so it can't see the host's cgroup layout. (Distinct from cgroups-the-limiter, Lesson 9–10.)
CLONE_NEWTIMEtimeOffsets for the boot and monotonic clocks (Linux 5.6+). Lets a container present a different uptime/boot time. The one most tutorials forget.
Where this corrects the familiar version

The internet's stock answer is "six namespaces": mnt, pid, net, ipc, uts, user. The source lists eight — cgroup (Linux 4.6) and time (Linux 5.6) are the two that get dropped because they arrived later. runc creates all of them; we teach all of them.

Mechanism 2

Three syscalls: create, move, join

Step 1 · Explain

Those CLONE_NEW* flags are used by three different syscalls, and the difference between them is the difference between the whole operations Docker performs. clone() creates a new child process that is already inside fresh namespaces — this is how a container's first process is born. unshare() moves the calling process into new namespaces without forking (with one exception we'll hit). setns() makes the caller join an already-existing namespace, given a file descriptor pointing at it — this is how docker exec steps into a running container (Lesson 8).

Step 2 · The source

All three appear in nsexec.c, the tiny C program runc runs before Go starts, precisely so namespace setup happens at the lowest level:

The part that does the job

Three verbs, three jobs. clone(... CLONE_PARENT | SIGCHLD ...) spawns the container's process directly inside its new namespaces. unshare(flags) relocates the current process. setns(fd, type) takes an fd — which you get by opening /proc/PID/ns/net and friends (next mechanism) — and drops the caller into that already-live namespace. Keep these straight: "create with clone," "move with unshare," "join with setns."

Mechanism 3

Namespaces are files: /proc/self/ns/

Step 1 · Explain

How do you see which namespaces a process is in, or get the fd that setns() needs? The kernel exposes every process's namespaces as magic symlinks under /proc/<pid>/ns/, one per type. Each link "points at" a string like net:[4026531840] — the number in brackets is the namespace's inode, a unique id for that particular namespace instance. Two processes in the same network namespace show the same inode; processes in different ones show different inodes. That single fact is your entire toolkit for verifying isolation: compare the inode numbers.

Step 2 & 4 · The source is the filesystem — inspect it
The part that does the job

The inode in brackets is identity. The plain container gets a fresh net inode (isolated); --net=host yields the host's inode, proving that "host networking" isn't a special mode — it's just not creating a new net namespace, so the process stays in the host's. Every Docker network/pid/ipc mode reduces to "make a new one" vs "reuse an existing inode."

Mechanism 4 · subtlety #1

Why the user namespace must go first

Step 1 · Explain

Here is the ordering rule everyone eventually trips on. Creating almost any namespace requires the capability CAP_SYS_ADMIN — effectively, being root. An unprivileged user doesn't have it, so they can't make a PID or network namespace directly. Except: creating a user namespace requires no privilege at all. And the moment you're inside a new user namespace, the kernel makes you root within it, handing you a full capability set scoped to that namespace. With those capabilities you can now create the other seven.

So the user namespace is the key that unlocks the rest: enter it first, and you gain the privilege to build everything else — even starting as an ordinary user. That is the whole foundation of rootless containers (Lesson 44). Which is exactly why runc pins its order:

The part that does the job

Two facts, one rule. Rule: the user namespace is created/entered before the others, because it is what grants the capabilities needed to create the others. Implementation wrinkle: runc can't simply unshare(CLONE_NEWUSER) in the parent, because unshare immediately strips that parent's capabilities in its old namespace and caps it at a single uid/gid mapping — so runc clone()s a child first and does the userns work in the child. The comment's "all hell breaks loose" is the source telling you, in plain English, why the ordering isn't optional.

The mirror rule for joining. When joining existing namespaces with setns() (the docker exec path), nsexec.c does the reverse dance: join every non-user namespace first, then the user namespace, then anything left — because for rootless containers you "don't get setns(2) permissions until we join the userns and get CAP_SYS_ADMIN." Same principle (userns carries the privilege), opposite direction. We pick this apart in Lesson 8.
Mechanism 5 · subtlety #2

Same process, two PIDs

Step 1 · Explain

The PID namespace has a quirk the source calls out directly: it only applies to children. Calling unshare(CLONE_NEWPID) does not move the caller into the new PID namespace — the caller keeps its old PID. Instead, the caller's next forked child becomes the first process in the new namespace, and the kernel assigns it PID 1 there. This is why runc has to fork to enter a PID namespace at all.

The consequence is the thing that confuses newcomers: that child process now has two PIDs simultaneously. Inside its own PID namespace it is PID 1. Out on the host, in the global PID namespace, it has some ordinary number like 4141. One process, two identities, because it's a member of two nested namespaces at once and each numbers it independently. The host can see and signal it by 4141; inside, your app sees itself as 1.

This dual-PID fact is what makes "PID 1 in a container is your app" true, and it's the setup for Lesson 28, where being PID 1 turns out to carry real kernel responsibilities.

Where we are

Summary

A namespace is a private copy of one global kernel resource, and there are eight — mnt, pid, net, ipc, uts, user, cgroup, time — each a CLONE_NEW* flag in runc's source. Three syscalls wield those flags: clone() creates a child already inside new namespaces, unshare() moves the caller, setns() joins an existing one via an fd. You can see and compare any process's namespaces as inode-bearing symlinks under /proc/<pid>/ns/, which is how --net=host is revealed to be nothing but "reuse the host's inode." Two subtleties live in the source: the user namespace must come first because it's the unprivileged key that grants the capabilities to create the rest (runc clones-then-unshares to pull this off, as its "quite annoying" comment attests), and the PID namespace only applies to children, so a container's first process holds two PIDs at once — 1 inside, its real number on the host. Next: the flip side of setns() — how docker exec joins these exact namespaces to step inside a running container.
