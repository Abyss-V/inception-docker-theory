Networking II: user-defined bridges, embedded DNS, macvlan/ipvlan

Keep the Lesson 33 packet model, then change one thing at a time: first the Docker network object, then name resolution, then the kernel interface type used to attach the container.

Governing idea

A Docker network driver chooses how an endpoint is attached to networking; Docker's embedded DNS is a separate libnetwork service that resolves names for the sandbox.

Carry-over from Lesson 33: a libnetwork Network, Endpoint, and Sandbox are control-plane objects inside dockerd. The Linux bridge, veth, macvlan/ipvlan device, routes, and netfilter rules are kernel/networking state used to realize those objects.

1 User-defined bridge

A user-defined bridge is a new Docker Network backed by its own Linux bridge

Start with the mechanism you already know. If you create:

Create one user-defined bridge network
docker network create appnet

Docker creates a new libnetwork Network whose driver is bridge. The important point is that this is not merely a new label on the old docker0 bridge. In Moby 29.6.2, when the bridge driver has no explicit bridge name and the network is not the legacy default bridge, bridge_linux.go · parseNetworkOptions chooses:

Current Moby rule

br-<first 12 characters of network ID>

If that bridge device does not already exist, the bridge driver records that libnetwork must create it and queues the bridge-device setup before configuring its addresses, forwarding, and firewall state. The containers attached to this network still use the Lesson 33 topology: each endpoint gets a container-side interface and a host-side veth peer, and the host peer is attached to this particular Linux bridge.

Docker Network

br-<network-id-prefix>the bridge device that switches frames for this network

veth peer → bridge portsame kernel mechanism as Lesson 33, but attached to this network's bridge
Do not collapse these two levels. appnet is the Docker/libnetwork Network. br-... is one Linux device used by the bridge driver to implement that Network.
2 Why names work

The bridge moves frames; it does not resolve container names

Suppose two containers join appnet:

Two endpoints on one user-defined network
docker run -d --name api --network appnet IMAGE ...
docker run -d --name web --network appnet IMAGE ...

If web asks for the address of api, the Linux bridge cannot answer that question. A bridge understands Ethernet forwarding information such as destination MAC addresses. It does not maintain Docker container-name records.

The name lookup is handled by a different part of libnetwork: the sandbox's embedded DNS resolver. Current Moby describes daemon/libnetwork/resolver.go · Resolver as Docker's embedded DNS server, and the resolver backend searches the Docker networks to which that sandbox is attached.

A
The endpoint joins a Docker Network
Libnetwork records the endpoint's DNS names and IP addresses in that Network's service-record maps.
B
The application asks for api
The DNS query goes to the sandbox's internal resolver, not to the Linux bridge.
C
The resolver searches connected Docker networks
Sandbox.ResolveName → Network.ResolveName searches aliases/names and the per-network service records.
D
If a Docker-local record exists
The resolver returns that endpoint IP. Only after the application has an IP does normal routing/ARP/bridge forwarding carry the actual application traffic.

This gives you a useful separation:

Two different jobs

DNS: “What IP belongs to api?”   Bridge: “Which bridge port should receive the Ethernet frame for this destination?”

3 Embedded DNS

Inside the container, Docker advertises the resolver as 127.0.0.11

For a sandbox using Docker's embedded resolver, Moby uses the fixed address 127.0.0.11. The resolver is associated with the sandbox and operates on the container's loopback side of that network namespace. Moby rebuilds the container's /etc/resolv.conf so the internal resolver becomes the nameserver, while the nameservers that were replaced are retained as upstream servers.

What you can observe in a container on a user-defined network
docker exec web cat /etc/resolv.conf

# Expected key line:
nameserver 127.0.0.11

Now distinguish two queries. If the query is for a Docker-local name such as api, Resolver.handleIPQuery asks its backend to resolve the name from Docker network state. If there is no local answer, Resolver.serveDNS → forwardExtDNS can forward the query to the sandbox's configured external resolvers.

External DNS forwarding follows connectivity. In startResolver, Moby initializes the forwarding policy from whether the sandbox currently has external access. A sandbox connected only to an internal network does not automatically get host-side upstream DNS access.
Source-over-folklore correction

The legacy default bridge network is not simply “the same thing with a different bridge name.” Moby's DNS path explicitly states that the legacy bridge network has no internal nameserver. The embedded resolver behavior discussed here is therefore a real distinction, not a property of Linux bridging itself.

First-read checkpoint

You should now be able to say: a user-defined bridge still uses veth + a Linux bridge for packets, but Docker-local name resolution is provided separately by libnetwork's sandbox resolver.

4 Second read: why 127.0.0.11:53 is not the literal listening socket

Moby listens on an ephemeral port, then NATs 127.0.0.11:53 to it

The simple mental model “Docker's resolver listens on 127.0.0.11:53” is good for using the system, but current Moby has one extra implementation layer. Sandbox.startResolver runs resolver.SetupFunc(0) inside the sandbox network namespace. Port 0 asks Linux to choose available UDP and TCP ports.

Then resolver_unix.go · setupNAT installs DNS NAT rules in that networking context. Queries addressed to 127.0.0.11:53 are DNATed to the resolver's actual UDP/TCP socket port, and replies are SNATed so the application still sees source port 53.

Application sees
→
127.0.0.11:53stable DNS endpoint written into resolv.conf
Inside netns
→
DNAT → 127.0.0.11:<ephemeral>actual UDP/TCP socket selected by SetupFunc(0)
Reply
→
SNAT source port back to :53preserves the normal DNS endpoint seen by the client

This NAT is not the published-port DNAT from Lesson 33. It is an internal implementation detail of Docker's embedded DNS inside the sandbox networking context.

5 Change the driver: macvlan

Macvlan removes the veth + Docker bridge attachment and creates a child of a parent link

Now change the driver rather than the network name:

Macvlan network shape
docker network create -d macvlan \
  --subnet 192.0.2.0/24 \
  -o parent=eth0 \
  macnet

The important word is parent. In the bridge driver, an endpoint is realized as a veth peer attached to a Linux bridge. In the macvlan driver, macvlan.Join asks createMacVlan to create a netlink.Macvlan device whose ParentIndex is the chosen host interface.

DriverHost-side relationshipContainer-facing device
bridgeveth host peer becomes a port on a Linux bridgethe veth peer moved/created in the container netns and renamed
macvlanmacvlan device is a child of the selected parent interfacethat macvlan child is handed to the sandbox and renamed, normally to eth0

Macvlan also gives the endpoint an L2 identity of its own. In current Moby, macvlan_endpoint.go · CreateEndpoint generates a MAC address when the endpoint did not already receive one. At the kernel boundary, Linux's macvlan implementation hashes destination Ethernet addresses and selects the matching macvlan device; in bridge mode it can also deliver frames directly between macvlan peers on the same lower device.

The structural change

bridge driver: container ↔ veth ↔ Linux bridge
macvlan driver: container ↔ macvlan child ↔ parent link

Because the parent is typically a physical NIC or VLAN subinterface, macvlan is useful when containers should participate more directly in an existing Layer-2 network rather than hide behind Docker's bridge/NAT topology.

6 Change the driver again: ipvlan

IPvlan also creates a child of a parent link, but shares Layer 2 and separates endpoints by Layer 3

IPvlan has a similar outer shape:

IPvlan network shape
docker network create -d ipvlan \
  --subnet 192.0.2.0/24 \
  -o parent=eth0 \
  -o ipvlan_mode=l2 \
  ipnet

ipvlan.Join → createIPVlan creates a netlink.IPVlan whose ParentIndex points at the chosen parent interface. The kernel IPvlan documentation gives the defining distinction from macvlan: IPvlan uses Layer 3 to multiplex/demultiplex the slave devices, allowing the master and its slaves to share Layer 2.

This is why current Moby does not allow you to assign an independent custom MAC address to an IPvlan endpoint. ipvlan_endpoint.go · CreateEndpoint returns an error if the endpoint already carries a requested MAC address.

7 IPvlan modes

L2, L3, and L3S change where the kernel makes the forwarding decision

Current Moby supports three IPvlan modes, matching the kernel API: l2, l3, and l3s. Do not reduce this to a two-mode story.

In L2 mode, the slave behaves most like an interface participating in the parent's Layer-2 network: multicast and broadcast are available, and Moby supplies the configured gateway to the endpoint. In L3 mode, the kernel's documentation says L3 processing is performed on the slave and traffic is switched to the master-side stack for L2 processing/routing; multicast and broadcast are not delivered to the slaves. Moby reflects that topology by installing connected default routes for the endpoint rather than a normal gateway address. L3S is the symmetric L3 variant whose kernel documentation explicitly exists so conntrack/iptables can work.

Do not confuse two uses of “bridge.” IPvlan's bridge flag is an IPvlan port-mode flag controlling communication among slaves. It is not a Linux bridge device such as docker0 or br-....
8 What happened to -p?

Macvlan/ipvlan do not implement the bridge driver's published-port DNAT path

Lesson 33's -p HOST:CONTAINER mechanism belonged to the bridge driver's host-port firewall/NAT architecture. Macvlan and IPvlan attach endpoints through a parent link instead of through Docker's bridge gateway path, so their endpoint drivers do not build that bridge-style port-mapping machinery.

Correction to the research checkpoint

The checkpoint said current Moby “rejects” port mappings for macvlan/ipvlan. The pinned source is more precise: macvlan_endpoint.go and ipvlan_endpoint.go label port mapping as unsupported and log a warning when mappings are supplied; those functions do not themselves return an error for the mapping. The primary source wins, so the lesson records the corrected behavior.

The practical model is: if a macvlan/ipvlan container is reachable on the surrounding network, peers normally address the container's own IP directly. Docker is not translating a host-published port through the bridge driver's DNAT rules for that endpoint.

Check yourself

  • What changes when you create a user-defined bridge? Libnetwork creates a separate Docker Network and, normally, the bridge driver backs it with its own br-<id> Linux bridge; endpoint packet plumbing is still veth + bridge.
  • Does the Linux bridge provide container-name DNS? No. The sandbox's libnetwork resolver does.
  • What is 127.0.0.11? The stable address Docker writes as the embedded resolver endpoint inside the sandbox; current Moby NATs port 53 to its actual ephemeral UDP/TCP sockets.
  • How does macvlan differ from bridge networking? The endpoint is a macvlan child of a chosen parent interface rather than one side of a veth pair attached to a Docker Linux bridge.
  • How does ipvlan differ from macvlan? It shares Layer 2 with the parent and uses Layer 3 to distinguish/multiplex slaves; Moby therefore does not allow independent custom endpoint MACs.
  • How many IPvlan modes matter here? Three: L2, L3, and L3S.
  • Does macvlan/ipvlan use Lesson 33's bridge-driver -p DNAT path? No; the drivers report port mappings as unsupported and do not construct that bridge publication path.
