Part 6 · Distribution · Lesson 39

Registries & the OCI Distribution HTTP API

Follow one image across the network. First a name moves. Then a manifest or index moves. That metadata tells containerd which config and layer blobs to fetch. Push runs the same idea in reverse: send the bytes that a manifest depends on, then commit the manifest.

CORE
governing idea

A registry never needs to send “the image” as one giant Docker file. It serves the OCI objects you already learned in Lessons 18–20: index, manifest, config, and compressed layers. The Distribution API is simply the HTTP protocol used to move those objects.

This lesson has one job: answer exactly what moves, who moves it, and which HTTP request moves it during docker pull and docker push.

scope rule for this rebuild

Lesson 40 owns tag-vs-digest identity and deduplication. Lesson 41 owns signing/provenance artifacts. This lesson will not introduce those mechanisms early. When a tag or digest is needed as an HTTP input, we define only enough to follow the request.

1. First, name the things on each side

A registry is the HTTP service that stores and serves OCI content. A repository is one named collection inside that registry.

For:

registry.example.com/team/app:1.4
PartMeaning here
registry.example.comThe registry server.
team/appThe repository name inside that registry.
1.4A tag: a human-friendly name used here to ask for a manifest or index. Lesson 40 explains why tags can move.

You already know a descriptor from Lesson 18: it is a small record containing a content object's digest, size, and mediaType. Here, media type simply means “what kind of OCI object are these bytes?”

We also need one HTTP word: an endpoint is a particular method + path that performs one operation. For example:

GET /v2/team/app/blobs/sha256:...

GET asks for the response body. HEAD asks for the response headers without the body. POST starts an operation or creates temporary server-side state. PUT sends the final bytes to a known destination.

whole mechanism first

2. Keep this picture in your head

Read this as two different kinds of movement: control information first, content bytes later. On pull, metadata tells containerd what bytes to fetch. On push, bytes are made available before the metadata that references them.
pull

3. docker pull begins with a name, not layer bytes

Suppose you run:

docker pull registry.example.com/team/app:1.4
1

Docker CLI → dockerd

The moving thing is the image reference registry.example.com/team/app:1.4, plus options such as platform and registry credentials. No layer stream is moving through the CLI.

2

dockerd → containerd

dockerd prepares the pull and asks containerd to perform it. On this pinned Engine path, it asks containerd to pull and unpack. “Unpack” means that after compressed layer content arrives, the snapshotter from Lesson 16 prepares filesystem snapshots that containers can mount.

3

containerd → registry

containerd is now the component that performs the registry HTTP requests. Its first problem is: what OCI object does the name team/app:1.4 currently identify?

Primary anchors: Docker Engine 29.6.2 source repository, daemon/containerd/image_pull.go; containerd v2.2.6, client/pull.go.

4. Resolve the name: containerd asks the manifest endpoint

To fetch an object graph, containerd needs a root descriptor: the descriptor for the first manifest or index.

With a tag such as 1.4, containerd v2.2.6 normally starts with:

HEAD /v2/team/app/manifests/1.4

Remember: HEAD asks for headers but no response body. Three headers are enough to describe the object:

  • Docker-Content-Digest — which content digest identifies it;
  • Content-Length — how many bytes the object contains;
  • Content-Type — whether those bytes are a manifest, index, or another accepted representation.

containerd uses those values to construct the descriptor. If the registry does not provide enough information, containerd falls back to GET, reads the manifest body, and computes the missing digest/size itself.

what moved in this step?

Usually only HTTP headers. The image layers still have not moved.

The request also carries an Accept header. Accept means “these are the manifest/index formats I know how to understand.” That matters because the same tag can resolve to a single-platform manifest or to an index containing several platform manifests.

Primary anchor: containerd v2.2.6, core/remotes/docker/resolver.go::Resolve. It issues a manifest HEAD, uses response metadata when sufficient, and falls back to GET when digest/size must be derived.

5. Fetch the metadata object, then follow its child descriptors

Now containerd knows the root descriptor. It must fetch the actual root object.

If the descriptor says the object is a manifest or index, containerd fetches it through the manifest endpoint:

GET /v2/team/app/manifests/sha256:<digest>

The response body is JSON. That JSON contains more descriptors.

For a normal single-platform image manifest, the children are:

  • one descriptor for the image configuration JSON;
  • one descriptor for each compressed filesystem layer.

Those child objects are blobs. A blob here simply means raw content fetched from the blob endpoint by digest:

GET /v2/team/app/blobs/sha256:<config-digest>
GET /v2/team/app/blobs/sha256:<layer-1-digest>
GET /v2/team/app/blobs/sha256:<layer-2-digest>
important distinction

A digest does not by itself tell containerd which URL family to use. The descriptor's media type tells containerd whether the object is manifest/index metadata or ordinary blob content. Manifest/index objects use /manifests/...; config/layer bytes use /blobs/....

If the root is a multi-platform index, containerd reads its platform descriptors, chooses the requested/default platform, then fetches that platform's manifest and follows its config/layer descriptors. That is the network use of the OCI graph you already learned in Lesson 19.

6. Where the downloaded bytes go

At the network boundary, the moving thing is an HTTP response body. containerd writes those bytes into its content store, which you learned in Lesson 22.

registry response body
        ↓
containerd
        ↓
content store object identified by digest

The expected descriptor travels with the operation, so containerd knows which digest and size it expects. The registry specification also tells clients to verify downloaded content against the requested/declared digest.

Once the necessary config and layer blobs are local, the Engine's pull path has also requested unpack. The snapshotter can then turn the selected image layers into the local snapshot state that a later container filesystem will use.

pull in one sentence

Name → root descriptor → manifest/index JSON → child descriptors → config/layer bytes → content store → unpacked snapshots.

push

7. docker push walks the same graph in reverse

Now run:

docker push registry.example.com/team/app:1.4

Docker CLI again sends a request to dockerd; it does not itself stream every layer to the registry. dockerd finds the local target OCI descriptor and prepares the remote operation. containerd's registry code performs the HTTP transfer.

The key rule is:

push invariant

Make a manifest's children available before committing the manifest that points to them.

Why? An image manifest claims that certain config/layer descriptors are available. If the registry accepted the manifest first but did not have those children, a client could fetch metadata that points to missing content. OCI Distribution allows a registry to reject such a manifest.

containerd v2.2.6 therefore pushes ordinary child content first, then manifests, then parent indexes. Its source explicitly records the ordering rule that the parent is uploaded after the child.

Primary anchors: Docker Engine 29.6.2 source repository, daemon/containerd/image_push.go; containerd v2.2.6, core/remotes/handlers.go::PushContent.

8. Upload one blob: check → start session → send bytes → commit

Take one local layer blob. Before sending its bytes, the registry client can ask whether that exact blob is already present in the target repository:

HEAD /v2/team/app/blobs/sha256:<digest>

If the registry says it already exists, no upload is needed. Why that is possible and how digest identity enables transfer reuse is Lesson 40. For now, treat this as a simple branch: present → skip; missing → upload.

If the blob must move, the pinned containerd path starts an upload session. An upload session is temporary registry-side state for one in-progress blob upload:

POST /v2/team/app/blobs/uploads/

→ 202 Accepted
  Location: /v2/team/app/blobs/uploads/<session-id>

The response header Location tells the client exactly where that temporary upload continues. Location is not the final blob identity. It names the upload operation.

containerd then sends the whole blob body to that location and includes the expected digest of the completed blob:

PUT <Location>?digest=sha256:<digest>

<whole blob bytes>

→ 201 Created

After successful commit, the temporary upload session is finished. The content is later fetched through the ordinary blob URL:

/v2/team/app/blobs/sha256:<digest>
keep these two identities separate

Location = temporary “where do I continue this upload?” state. sha256:... = identity of the completed content bytes.

9. After the blobs exist, commit the manifest

Once the config and layer blobs referenced by a manifest are available, containerd can upload the manifest JSON:

PUT /v2/team/app/manifests/<reference>
Content-Type: application/vnd.oci.image.manifest.v1+json

<manifest JSON bytes>

→ 201 Created

The registry stores the exact manifest byte representation supplied by the client. This matters because the manifest's digest is calculated over those exact bytes.

For a multi-platform image, each platform manifest must be available before the parent index that points to those manifests is committed.

config/layers ─→ platform manifest ─┐
config/layers ─→ platform manifest ─┼─→ parent index last
config/layers ─→ platform manifest ─┘

This is the entire push dependency rule. We do not need deduplication theory yet to understand it: children first, metadata that points to them second.

10. Authentication is wrapped around the HTTP API

Before or during any registry request, the server may reply:

401 Unauthorized
WWW-Authenticate: ...

WWW-Authenticate is a challenge telling the client what authentication scheme is required. containerd has a registry authorizer: a helper that processes the challenge, obtains or applies credentials/token information, adds an Authorization header, and retries the registry request.

source-over-folklore correction

OCI Distribution Spec v1.1.1 does not define the registry authentication protocol itself. It defines the content-transfer HTTP API and explicitly leaves authentication/authorization outside its scope.

So when you watch registry traffic, keep two mechanisms separate:

authentication challenge/retry
            wraps
manifest + blob distribution requests

11. One spec branch Docker does not use on this pinned path

You now understand the pinned Docker/containerd blob upload path: POST → Location → one PUT containing the whole blob.

The OCI Distribution Spec also defines chunked upload. A chunk is simply one consecutive byte range of a larger blob. The protocol can send several chunks before final commit:

POST  → create upload session
PATCH → send bytes 0..N
PATCH → send bytes N+1..M
PUT   → close session and verify whole-blob digest

PATCH here means “append another portion to this existing upload.” Content-Range tells the registry which byte positions this chunk contains. Chunks must arrive in order. The final PUT still names the digest of the whole blob, not the digest of the final chunk.

why this is separated

This is protocol completeness, not another pipeline you must hold in your head while learning Docker's actual path. containerd v2.2.6's pusher source still contains the note TODO: Support chunked upload; the pinned path described above uses the monolithic whole-body upload.

12. Inspect the movement yourself

Use a local registry so TLS and external authentication do not obscure the protocol.

terminal 1 — registry
docker run -d --rm --name lesson39-registry \
  -p 5000:5000 registry:2

docker logs -f lesson39-registry
terminal 2 — push
docker pull alpine:latest
docker tag alpine:latest localhost:5000/course/lesson39:demo
docker push localhost:5000/course/lesson39:demo

In the registry log, do not try to memorize every line. Find only these phases:

  1. HEAD requests asking whether content exists;
  2. POST .../blobs/uploads/ creating an upload session for missing content;
  3. PUT requests committing blob bytes;
  4. the final manifest PUT.

Observe the pull-side metadata request directly

curl -i -X HEAD \
  -H 'Accept: application/vnd.oci.image.index.v1+json, application/vnd.oci.image.manifest.v1+json, application/vnd.docker.distribution.manifest.list.v2+json, application/vnd.docker.distribution.manifest.v2+json' \
  http://127.0.0.1:5000/v2/course/lesson39/manifests/demo

Look for Docker-Content-Digest, Content-Length, and Content-Type. Those are the values that can let a resolver construct the root descriptor without downloading the manifest body during the initial resolution step.

Then fetch the manifest JSON

curl -s \
  -H 'Accept: application/vnd.oci.image.index.v1+json, application/vnd.oci.image.manifest.v1+json, application/vnd.docker.distribution.manifest.list.v2+json, application/vnd.docker.distribution.manifest.v2+json' \
  http://127.0.0.1:5000/v2/course/lesson39/manifests/demo

Find the descriptors inside it. If the response is an index, choose one platform descriptor and fetch that manifest. If it is an image manifest, identify its config descriptor and layer descriptors. You are now manually following the same graph containerd follows.

13. Primary-source proof

The mechanism above remains pinned to the established course baseline: Docker Engine/Docker CLI 29.6.2, containerd 2.2.6, OCI Distribution Spec 1.1.1, and OCI Image Spec 1.1.1.

OCI distribution-spec v1.1.1 containerd resolver.go containerd fetcher.go containerd pusher.go containerd handlers.go containerd authorizer.go
Exact audit anchors — open only when you want the implementation proof

Pull ownership: Docker Engine 29.6.2 source repository, daemon/containerd/image_pull.go, configures containerd pull options and adds WithPullUnpack.

Resolve: containerd v2.2.6 core/remotes/docker/resolver.go::Resolve starts manifest resolution with HEAD; it reads response size/media type and Docker-Content-Digest, and falls back to GET if digest or size is unavailable.

Fetch endpoint choice: containerd v2.2.6 core/remotes/docker/fetcher.go::dockerFetcher.Fetch distinguishes manifest/index media types from blob content and builds the corresponding registry path.

Push ordering: containerd v2.2.6 core/remotes/handlers.go::PushContent dispatches child content before saved manifests/indexes; its index loop records that the parent is uploaded after the child.

Blob upload: containerd v2.2.6 core/remotes/docker/pusher.go handles the registry upload session and the current whole-body writer path; the source still records TODO: Support chunked upload.

Authentication: containerd v2.2.6 core/remotes/docker/authorizer.go handles registry authentication challenges separately from OCI Distribution's content API.

14. Check yourself

  1. Immediately after you type docker pull ..., what is moving from Docker CLI to dockerd: layer bytes or a request describing the image?
  2. Why does containerd first need a root descriptor?
  3. What is the difference between HEAD and GET during manifest resolution?
  4. Why does containerd fetch a manifest/index through /manifests/... but config/layers through /blobs/...?
  5. Where do downloaded config/layer bytes live after pull?
  6. Why does push upload children before their manifest/index parent?
  7. What does the upload-session Location identify?
  8. What does the final blob digest identify?
  9. Why can you see 401 during a valid registry operation?
  10. Does the pinned containerd pusher normally use OCI's chunked PATCH path?
Answers
  1. A request containing the image reference/options/auth material. Layer bytes are not flowing through Docker CLI.
  2. It gives containerd the digest, size, and media type needed to identify and interpret the root OCI object.
  3. HEAD retrieves headers without the body; GET retrieves the body. containerd can fall back to GET if response metadata is insufficient.
  4. The descriptor media type tells containerd what kind of object it is. Registry manifests/indexes and ordinary blobs use different endpoint families.
  5. In containerd's content store, identified by content digest; the Engine pull path also requests unpack into snapshotter state.
  6. The parent metadata claims its child content exists. Children first prevents committing ordinary image metadata whose dependencies are missing.
  7. Temporary server-side state for one in-progress upload and the URL where that upload continues.
  8. The identity of the completed content bytes.
  9. Authentication can wrap the registry content request; OCI Distribution leaves the auth protocol itself outside its scope.
  10. No. OCI defines it, but this pinned containerd path uses the whole-body monolithic path.

Recap

Pull: image name → Docker CLI → dockerd → containerd → resolve root descriptor → fetch manifest/index JSON → follow child descriptors → fetch config/layer blobs → content store → unpack.

Push: local descriptor graph → containerd → check/upload child blobs → commit manifest → commit parent index last.

The relationship to remember: metadata tells containerd which content bytes exist and where they fit in the graph. The registry HTTP API moves those metadata objects and content blobs separately.
