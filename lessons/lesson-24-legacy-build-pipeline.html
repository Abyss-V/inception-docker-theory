The legacy build: run a container, commit, repeat

Before BuildKit, docker build was almost embarrassingly literal: for each Dockerfile line it ran a container and froze the result as an image. Understanding this makes the layer/cache rules obvious — and shows exactly what BuildKit fixed.

The idea in one sentence

The classic builder runs the Dockerfile top to bottom and, after every instruction, freezes the result as an intermediate image — so a build is a straight chain of commits.

Note. This is the legacy builder, now removed from current Docker in favor of BuildKit (Lesson 25). It's still worth knowing: it's the simplest possible build model, and every Dockerfile rule you've internalized comes straight from it.
1 Start here

A build is a chain of commits

Plain version: think of the builder as a person typing each Dockerfile line, then running docker commit after each one to save progress.

The classic builder holds a current image and walks the Dockerfile line by line (moby builder/dockerfile/dispatchers.go). For each instruction it does the work, then commits the result as a new intermediate image, and the next instruction builds FROM that. So the build is a linear chain: base → img1 → img2 → … → final, one image per line. That single fact explains why images have one layer per instruction, and why instruction order matters so much.

2 The RUN mechanism

RUN = create a container, run it, commit it

Plain version: a RUN line literally starts a container, runs your command inside, and saves the changed filesystem as a layer.

The most revealing instruction is RUN. The builder (dispatchRun) takes the current image, creates a container from it, runs your command inside that container, waits for it to exit, and then commits the container's filesystem changes as a new layer (internals.go: b.commit). That's the exact same mechanism as docker commit on a stopped container. So RUN apt-get install curl is: spin up a container on the current image, run apt, freeze the diff. Every RUN is a real container launch.

3 COPY and metadata

The other instructions: layers vs. config-only

Plain version: COPY adds files as a layer; ENV/CMD/WORKDIR just change settings and add an empty layer.

COPY/ADD (performCopy) don't run a command — they make a fresh writable layer (NewRWLayer), copy files in, and commit it (exportImage). The metadata instructions — ENV, CMD, ENTRYPOINT, WORKDIR, USER, EXPOSE, LABEL — don't touch the filesystem at all. They mutate the in-progress image config (d.state.runConfig) and commit an empty layer: a new image with the same rootfs but an updated config. That's the source-level reason those instructions add a history entry but no filesystem layer.

4 The cache

Why changing one line rebuilds everything after it

Plain version: before each line, the builder asks "have I already built this exact step on this exact parent?" — if yes, it reuses the old image; if no, everything downstream is rebuilt.

Before doing each instruction's work, the builder runs probeCache: it looks for an existing image already built from the same parent image plus the same instruction (for COPY/ADD, also the same file contents). A match is a cache hit — reuse that image, skip the work. But the cache is linear: because each step's parent is the previous step's image, changing an early line changes that image's ID, which misses the cache for it and every step after it. This is the mechanical reason for the golden rule — put rarely-changing instructions (dependency installs) before frequently-changing ones (copying your source).

The whole model in one line

Legacy build = for each Dockerfile line, probe the cache; on a miss, do the work (run a container for RUN, add a layer for COPY, or edit config for metadata) and commit a new intermediate image; then move to the next line on top of it.

5 The limits

What this model couldn't do

Plain version: it was simple but rigid — one line at a time, coarse caching, and no way to use secrets or caches without baking them in.

The chain-of-commits model is easy to understand but has hard limits, and these are exactly what motivated its replacement. It's strictly sequential — no independent steps run in parallel. Its cache is linear and coarse — one early change invalidates everything downstream, even unrelated steps. Every RUN is a full container create + commit, with the overhead that implies. And there's no way to mount a secret or a build cache for a single step without it ending up in a layer. Lesson 25's BuildKit rethinks the build as a graph to fix all four.

Check yourself

  • A legacy build is a linear chain of commits — one intermediate image per Dockerfile instruction.
  • RUN = create a container, run the command, commit the diff (same as docker commit).
  • COPY/ADD add a filesystem layer; ENV/CMD/WORKDIR/etc. change only config and commit an empty layer.
  • The cache reuses an image built from the same parent + same instruction; it's linear, so an early change rebuilds everything after.
  • That linearity is why stable instructions go first, volatile ones (COPY source) last.
  • Limits — sequential, coarse cache, heavy RUN, no secret/cache mounts — are what BuildKit (Lesson 25) fixes.
Where this corrects the familiar version

"The builder is magic" — it isn't; it's a loop that runs a container and commits, per line. Two things people misremember: metadata instructions like ENV and CMD do create images (empty-layer commits), they just add no filesystem layer — which is why they still show in docker history. And "the cache is smart about what changed" overstates the legacy builder: it's a linear parent-plus-instruction match, so it can't reuse a later step when an earlier one changes, even if that later step is unrelated. BuildKit's graph is what finally makes caching truly dependency-aware.

Where we are

Summary

The classic docker build is a straight chain of commits: for each Dockerfile instruction the builder probes the cache and, on a miss, does the work — RUN creates a container and commits its diff, COPY/ADD adds a filesystem layer, and metadata instructions edit the config and commit an empty layer — then builds the next line on top. The cache is a linear parent-plus-instruction match, which is exactly why instruction order dictates rebuild cost. This model is simple but rigid: sequential, coarsely cached, heavy per-RUN, and unable to mount secrets or caches. Next, Lesson 25 opens BuildKit — which recompiles the whole idea of a build into a content-addressed graph (LLB), unlocking parallelism, precise caching, and secret/cache mounts.
