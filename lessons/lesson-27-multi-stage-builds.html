Multi-stage builds: build fat, ship thin

Compile in an image full of tools, then copy only the finished artifact into a clean, minimal image. The toolchain never ships — and thanks to the build graph, unused stages never even run.

The idea in one sentence

Put several FROMs in one Dockerfile: build in a heavy stage, then COPY --from just the finished artifact into a minimal final stage — and only that last stage becomes the image.

1 Start here

The problem: your toolchain ships with you

Plain version: if you compile inside the image, the compiler and all the build junk end up in the image you ship — even though the running app doesn't need any of it.

Say you build a Go binary in a single-stage image. To compile, you need the Go toolchain, source, and dependencies — hundreds of megabytes. But to run the result, you need just the compiled binary. In a single-stage build, all that build machinery stays in the final image: bigger downloads, slower deploys, and a much larger attack surface (a shipped compiler and package manager are gifts to an attacker). You want to build in a rich environment but ship almost nothing.

2 The mechanism

Multiple FROMs = multiple stages

Plain version: each FROM line starts a fresh, independent build — a "stage" — and you can give it a name.

A multi-stage Dockerfile simply has more than one FROM. Each FROM begins a new stage — in the frontend (Lesson 25), each one becomes its own dispatchState, an independent branch of the LLB graph (convert.go: one dispatch state per parsed stage). You name a stage with AS:

3 The copy

COPY --from: take only the artifact

Plain version: the final stage starts clean and pulls just the one file it needs out of the build stage.

The pivot is COPY --from=build. It copies a path out of an earlier stage's filesystem into the current stage. The final stage starts from a minimal base — alpine, a distroless image, or even scratch (an empty image) — and copies in only the compiled artifact. Everything in the build stage that you didn't copy — the Go toolchain, the source, the module cache — simply isn't part of the final image.

4 What ships

Only the last stage becomes the image

Plain version: the final image is just the last FROM's stage; earlier stages are scaffolding.

By default, only the last stage becomes the image you get (convert.go: the stage is marked Default when it's the final one in the file). Earlier stages are intermediate scaffolding — their layers are never part of the output unless something COPY --froms out of them. So the build stage's toolchain isn't "cleaned up" at the end; it was simply never in the final image's layer list to begin with. You can also build up to a specific stage with --target build, which is handy for debugging or for a shared test stage.

5 The graph payoff

Unused stages never even run

Plain version: because stages are graph branches, BuildKit skips any stage the target doesn't need — and runs independent ones in parallel.

Here's where Lesson 25 pays off again. Since each stage is a branch of the LLB graph, BuildKit only builds the stages that the target actually depends on — the frontend computes allReachableStages from the target and prunes the rest. Build a Dockerfile with a test stage and target the final stage, and the test stage doesn't run at all. Independent stages (say, building two separate binaries) run in parallel. The old builder, by contrast, executed every stage top to bottom regardless of need. Multi-stage is not just a size trick — it's a graph the solver can prune and parallelize.

The pattern in one line

Heavy build stage produces an artifact → minimal final stage COPY --froms just that artifact → only the final stage ships, and unreachable stages never run. Build fat, ship thin, waste nothing.

Check yourself

  • A single-stage compiled build ships the whole toolchain; multi-stage fixes that.
  • Each FROM starts a new stage (its own graph branch); name them with AS.
  • COPY --from=stage pulls just the artifact into a minimal final base (alpine / distroless / scratch).
  • Only the last stage (or --target) becomes the image; earlier stages ship nothing unless copied from.
  • BuildKit builds only stages reachable from the target and runs independent ones in parallel.
  • The toolchain isn't cleaned up — it was never in the final image to begin with.
Where this corrects the familiar version

"Multi-stage cleans up the build tools at the end" is the wrong mental model — nothing is cleaned. The final image is a different image built from a minimal base, into which you copied one artifact; the build stage's layers were never in its layer list. This also corrects the old rm -rf habit from Lesson 17: you can't shrink an image by deleting build tools in a later layer (the bytes persist below), but you can by simply not putting them in the shipping stage. Multi-stage is the real answer to "how do I get build tools out of my image."

Where we are

Summary

Multi-stage builds put several FROMs in one Dockerfile: a heavy build stage compiles the artifact, and a minimal final stage uses COPY --from to take only that artifact, starting from alpine, distroless, or scratch. Only the last stage (or the --target stage) becomes the shipped image — earlier stages are scaffolding whose layers never ship unless copied from. Because stages are branches of the LLB graph, BuildKit prunes stages unreachable from the target and runs independent ones in parallel. This is the correct way to keep toolchains out of images — not deleting them afterward, but never shipping them.
