01

What containerization actually is

A container is not a small virtual machine and not a box. Read literally from the OCI spec, it is an environment for a process — and everything else in this course follows from taking that sentence seriously.

Almost every Docker tutorial opens by drawing a container as a little box sitting on your operating system. That picture is not wrong so much as it hides the mechanism. Before we touch docker at all, we are going to fetch the actual specification that defines the word "container" and let it tell us what the thing is. When the spec and the folk model disagree, the spec wins — and it disagrees immediately.

Mechanism 1

A container is an environment, not an object

Step 1 · Explain

Start from processes, which you already understand. On Linux, everything that runs is a process: it has a PID, an address space, open file descriptors, a view of the filesystem, a set of privileges, and it makes system calls into the kernel to do anything real — open a file, send a packet, fork a child. Normally, every process shares one global view of the machine: the same filesystem tree rooted at /, the same list of PIDs, the same network interfaces, the same hostname.

A "container" is what you get when you start an ordinary process but first reconfigure what that process can see and use: give it its own root filesystem, its own PID numbering, its own network stack, and a ceiling on the CPU and memory it may consume. The process is still a normal process on your host. It has simply been handed a customized environment. That is the entire idea, and — remarkably — it is almost verbatim how the standard defines it.

Step 2 · The source Step 3 · Read it line by line
  • "An environment for executing processes" The spec never calls a container a machine, an image, or a box. It is an environment, and its whole reason to exist is to run processes. The container is the costume; the process is the actor.
  • "configurable isolation" Isolation is a dial, not a wall. You choose how much the process is separated from the host. That configurability is the namespaces we cover in Lesson 6.
  • "resource limitations" The second half: capping CPU, memory, PIDs, I/O. That is cgroups, Lessons 9–10.
  • "namespaces, resource limits, and mounts" The spec names its own three ingredients. There is no fourth magic ingredient. A container is exactly: (isolation) + (limits) + (a filesystem to run in).
  • Runtime "launches a process inside the container" Confirms the direction of causation: the runtime first builds the environment, then launches a process into it. Environment precedes process.
Where this corrects the familiar version

The popular teaching — "a container is a lightweight VM" — inverts the relationship. A VM is a thing (a virtual computer) that then runs processes. A container is not a thing at all: it is a set of adjustments to how one host process sees the world. There is nothing to "boot." When people say a container is "running," what is literally running is a process on your kernel that has been placed in namespaces and cgroups. Hold onto this; it explains every security property later.

Mechanism 2

Shared kernel: the one fact that separates containers from VMs

Step 1 · Explain

Here is the mechanism that defines the whole category. When the process inside a container makes a system call — read(), clone(), connect() — that syscall is serviced by your host's kernel. The exact same kernel that services syscalls from your text editor. There is no second kernel inside the container. The isolation (different filesystem, different PIDs) is bookkeeping within that one kernel, not a separate operating system.

Contrast a virtual machine. A VM runs a full guest kernel on top of virtualized hardware provided by a hypervisor. A syscall inside a VM is handled by the guest kernel; only when the guest kernel touches virtual hardware does control drop to the hypervisor and then the host. Two kernels, two boundaries.

Step 3 · Read it line by line
  • CLONE_NEW* Each is a flag to the Linux clone(2) / unshare(2) syscall. Setting one asks the host kernel to give the new process a fresh instance of that subsystem. The kernel doing the giving is the shared kernel — proof that no guest kernel is involved.
  • "cgroup" … "uts" These are the string names you'll see under /proc/self/ns/. Eight of them. Note the count: eight, not six.
  • CLONE_NEWTIME The time namespace (Linux 5.6+). Routinely omitted by tutorials that teach "the six namespaces." It's here in the real source, so we teach it.
  • CLONE_NEWCGROUP The cgroup namespace — also frequently dropped. Distinct from cgroups-the-limiter; it isolates the view of the cgroup tree.
Source vs folklore · the count is 8

Our very first grep of runc contradicted the common "six namespaces" list. The kernel and runc support eight: mnt, pid, net, ipc, uts, user, cgroup, and time. We will not round down to the familiar number anywhere in this course. Lesson 6 walks all eight from this same file.

Consequence

One wall vs two: the security cost of a shared kernel

Step 1 · Explain

The shared kernel is what makes containers fast and light — no second OS to boot, near-native syscall speed, megabytes instead of gigabytes. It is also their central security limitation, and it falls directly out of the diagram above.

A containerized process is separated from the host by exactly one boundary: the kernel's own isolation logic (namespaces + cgroups + capabilities + seccomp). If an attacker inside a container finds a bug in that kernel — a namespace escape, a privilege-escalation syscall bug — they are on the host, as whatever privilege they can reach. One wall, and it's the same wall the host stands on.

A VM adds a second, independent boundary. Break the guest kernel and you own the guest — but you're still trapped inside the hypervisor's virtual hardware. To reach the host you must also break the hypervisor, a much smaller and more hardened interface. Two walls, made of different material.

Design takeaway. "Container vs VM" is not "better vs worse." It's a trade: containers spend a security boundary to buy speed and density. This is why hostile-multi-tenant workloads often run each container inside a lightweight VM (Firecracker, Kata, gVisor's re-implemented kernel) — restoring the second wall while keeping most of the ergonomics. Every security primitive in Lessons 11–13 (capabilities, seccomp, AppArmor/SELinux) exists to harden that single shared-kernel wall.

Caveat

"Runs anywhere" has an architecture asterisk — and it's in the spec

Step 1 · Explain

Because there's no guest OS, the binaries inside an image are real machine code for a real CPU architecture, executed directly by your host processor. An amd64 image ships x86-64 instructions; an arm64 image ships AArch64 instructions. The host kernel doesn't translate them — it hands them to the silicon. So a container image is portable across machines, but not automatically across architectures. Pull an arm64 image onto an x86-64 host and the CPU literally cannot decode the instructions.

This isn't a Docker quirk — it's written into the image specification, which makes the CPU architecture a required field of every image config.

Step 2 · The source Step 3 · Read it line by line
  • architecture · REQUIRED Every image must declare its CPU target. There is no "architecture-neutral" container image of native code. The word REQUIRED is the spec forbidding you from pretending otherwise.
  • "binaries … built to run on" The spec is explicit that these are binaries — compiled machine code — not portable bytecode. That's why the host CPU must match.
  • GOARCH / GOOS The allowed values reuse Go's identifiers: amd64, arm64, 386, ppc64le… / linux, windows. A pair like linux/amd64 is the "platform."
  • os · REQUIRED Same story for the OS. A windows image expects a Windows kernel; it cannot run on your Linux host, shared-kernel being the whole point.
  • variant · OPTIONAL Fine-grained CPU sub-targets (e.g. ARM v6/v7/v8). Optional because the coarse arch is usually enough to decide runnability.
Where this corrects the familiar version

"Build once, run anywhere" is marketing shorthand. The spec's own REQUIRED architecture/os fields say the honest version: build once per platform, run anywhere with that platform. The way Docker appears to run "anywhere" is that a single tag (e.g. alpine) is often a manifest list pointing at several per-architecture images, and the daemon picks the one matching your host. And when you deliberately run a foreign-arch image, it only works because an emulator (qemu-user via binfmt_misc) transparently interprets the instructions — at a real speed cost. We build manifest lists apart in Lesson 19.

Where we are

What you now know, stated precisely

A container is not a virtual machine and not a box. It is an ordinary host process placed in a configured environment — the runtime-spec says so in the glossary. That environment is built from kernel features (eight namespaces, cgroups, mounts) requested through syscalls like clone(), serviced by the one shared host kernel. Sharing that kernel is what makes containers cheap (no guest OS to boot, native syscall speed) and what makes them one wall instead of a VM's two. And because the process runs native machine code on your CPU, portability is bounded by architecture — a fact the image-spec enforces with REQUIRED architecture and os fields.
