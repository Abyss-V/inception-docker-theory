Multi-arch: one tag, every CPU

How docker pull nginx gives you an arm64 image on your Mac and an amd64 image on your server — with the same command. There's one more document sitting above everything in Lesson 18.

The idea in one sentence

An image index is a document above the manifest that lists one manifest per platform, so a single tag can carry an amd64 build, an arm64 build, and more — and your machine automatically picks the right one.

1 Start here

Why one manifest isn't enough

Plain version: a manifest is built for one CPU. But one tag has to work on many CPUs. So something above the manifest has to choose.

Remember from Lesson 18 that an image's config pins an architecture and os — a manifest is built for one platform, say linux/amd64. But nginx:1.25 has to run on Intel servers and Apple Silicon laptops and Raspberry Pis. A single manifest can't do that. So there needs to be a document one level up that holds several manifests — one per platform — and lets the puller choose the one that matches its machine. That document is the image index.

2 The document

The image index: manifests labeled by platform

Plain version: the index is a list where each entry is "a manifest + which platform it's for."

The image index (media type application/vnd.oci.image.index.v1+json, from image-index.md) has a manifests array, and each entry is a familiar descriptor from Lesson 18 (mediaType, digest, size) with one thing added: a platform object holding architecture (amd64, arm64, ppc64le…), os (linux, windows), and optionally variant (e.g. v7/v8 for ARM). So the index is really a lookup table: platform → manifest digest.

Two names, one thing. Docker's older schema called this a manifest list; OCI calls it an image index. Same document, same job. You'll see both terms; they're interchangeable.
3 Resolution

How your machine picks the right build

Plain version: pull the index, match your own CPU/OS to a platform entry, follow that manifest — then it's exactly Lesson 18.

When you pull a multi-arch tag, your daemon fetches the index, reads its own platform (its GOOS/GOARCH), finds the matching entry, and takes that entry's manifest digest. From there it's the Lesson 18 flow unchanged: manifest → config + layers. So multi-arch adds exactly one hop on top of what you already know:

4 A caveat

Not every tag has an index

Plain version: single-architecture images skip the index entirely — the tag points straight at a bare manifest.

An index only exists when an image was built for multiple platforms. A single-arch image is just a bare manifest (Lesson 18), and its tag points directly at that manifest — no index in sight. This is why docker manifest inspect sometimes shows a list of platforms and sometimes shows one plain manifest: it depends on whether that image was published multi-arch. You create an index by building for several platforms at once — docker buildx build --platform linux/amd64,linux/arm64 — which produces the per-platform manifests and the index tying them together.

5 Pinning

Pin the index, not a single manifest

Plain version: pinning the index digest stays multi-arch; pinning one manifest digest locks you to a single CPU.

You can pin either level by digest. Pinning the index digest (nginx@sha256:<index>) is reproducible and still resolves per-platform — the right choice for a deployment that runs on mixed hardware. Pinning a specific manifest digest locks you to exactly one architecture, which is occasionally what you want (a single-arch node) but usually not. So the rule of thumb: pin the index unless you have a reason to nail down one platform.

Check yourself

  • A manifest is built for one platform; a tag must serve many — so an image index sits above manifests.
  • The index's manifests array is descriptors + a platform (architecture, os, variant) — a platform → manifest lookup.
  • Resolution adds one hop: tag → index → (match your platform) → manifest → config + layers.
  • "Manifest list" (Docker) and "image index" (OCI) are the same thing.
  • Single-arch images have no index — the tag points straight at a manifest.
  • Pin the index digest to stay multi-arch; pinning a manifest digest locks one CPU.
Where this corrects the familiar version

People assume "the image" is always the manifest — but for the images you use daily, the tag usually points at an index, and the manifest you actually run is chosen for your CPU behind the scenes. That's why the same nginx:1.25 "just works" everywhere. It also explains a common confusion: an arm64 laptop and an amd64 server pulling the identical tag end up with different manifest digests and different layer bytes — because they resolved to different entries in the same index.

Where we are

Summary

Multi-arch works by adding one document above the manifest: an image index (a.k.a. manifest list). Its manifests array holds one descriptor per platform, each tagged with {architecture, os, variant}, so it's a platform → manifest-digest table. Pulling a multi-arch tag resolves tag → index → your-platform manifest → config + layers — one extra hop on top of Lesson 18, with the rest unchanged. Not every tag has an index (single-arch images are bare manifests), and for reproducibility you pin the index digest to stay portable across CPUs.
