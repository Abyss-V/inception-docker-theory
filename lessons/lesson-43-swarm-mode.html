Part 7 · Orchestration · Lesson 43

Swarm mode

Swarm adds a long-running cluster control loop inside dockerd. It decides which node should execute each desired task; it does not replace the container runtime underneath that node.

DEEP-CUT
one sentence first

A Swarm service is replicated desired state; a task is one scheduled attempt to realize part of that state; only the worker finally turns an assigned task into an ordinary Docker container.

1. See the complete pipeline first

Use one example for the whole lesson:

docker network create --driver overlay appnet

docker service create \
  --name web \
  --replicas 2 \
  --network appnet \
  --publish published=8080,target=80 \
  nginx:1.27-alpine

2. What changes when Swarm mode is enabled?

docker swarm init does not launch a new container daemon. The Docker CLI calls the Engine Swarm API; dockerd's cluster layer starts a Swarm node inside the daemon.

Every Swarm node runs the agent: the worker-side component that receives tasks and reports status. A node whose role is manager also runs the manager control plane. The pinned source states this directly: a node “handles workloads and may also run as a manager.” So manager and worker execution are not mutually exclusive roles; managers can execute tasks unless scheduling availability prevents it.

piecejob
manager store + Raftreplicate cluster objects such as services, tasks, nodes, networks, secrets, and configs
leader orchestratorscompare desired service state with current tasks and create/remove/restart/update tasks
leader schedulerchoose a node for an unassigned task
dispatcherstream each node its assignments and required dependencies
agent/executorturn an assigned task into local Docker resources and report task status

Node identity is also part of this path: the dispatcher derives the caller's Swarm node identity from the authenticated connection before serving that node's assignments. We do not need the full certificate-rotation machinery here; the load-bearing point is that a worker does not simply ask for another node's task list.

3. Service → Task → container: keep these three objects separate

For --replicas 2, the command does not create two containers in the manager API handler.

Service "web"
  desired replicas = 2
  task template = image + command + networks + resources + ...
              ↓ orchestrator
Task A (slot 1)        Task B (slot 2)
              ↓ scheduler assigns nodes
Task A → node X        Task B → node Y
              ↓ worker execution
container for A        container for B

Service. A durable desired-state object. It contains the task template and service mode. For our replicated service, it says the cluster should maintain two replica slots.

Task. One concrete execution attempt generated from that service template. Tasks have their own IDs, status, desired state, and eventually a node assignment.

Container. The local Docker object created by the worker executor after a task reaches that worker.

source microscope

The Engine handler ends by calling the embedded control API:

state.controlClient.CreateService(...)

The control API stores a Service. Separately, the replicated orchestrator creates missing tasks:

store.CreateTask(tx, orchestrator.NewTask(...))

That separation is the implementation proof that “service” is not another word for “container.”

Before the service is stored, the Engine path can resolve a tag such as nginx:1.27-alpine to a digest and place the digest-qualified reference into the task template. That reuses the image-identity mechanism from Lessons 39–40; it is not a Swarm-specific image format.

Anchors: Docker Engine 29.6.2 · daemon/cluster/services.go::CreateService; SwarmKit pinned commit · manager/controlapi/service.go::Server.CreateService; manager/orchestrator/replicated/services.go::reconcile/addTasks.

4. Why Raft is in the middle

If the desired service existed only in one manager's RAM, losing that manager would lose the cluster's intent. Swarm managers therefore replicate control-plane mutations through Raft.

The important implementation chain is:

CreateService / UpdateService / task mutation
                ↓
MemoryStore.Update(...)
                ↓ builds StoreAction records
Raft Node.ProposeValue(...)
                ↓ consensus / committed log entry
manager stores apply the committed change

The in-memory store is therefore a working view kept in sync with the Raft log. The Raft node also persists log/snapshot state so a manager can restart and recover the replicated state.

correction

Raft does not schedule containers and does not replicate container processes. It replicates control-plane state. The leader-only scheduler/orchestrators react to that state after it is committed.

When a manager becomes leader, the pinned manager code starts the replicated orchestrator and scheduler. Losing leadership stops those leader-only subsystems. That is why there is one active decision-maker for reconciliation/scheduling while the manager set still holds replicated state.

Operationally, a manager set needs a majority to make progress on Raft writes. A three-manager cluster needs two reachable managers; a five-manager cluster needs three. Workers are not votes in this manager quorum.

source microscope
MemoryStore.Update → proposer.ProposeValue(...)
Node.ProposeValue → underlying Raft proposal + wait for commit

Anchors: SwarmKit pinned commit · manager/state/store/memory.go::MemoryStore.Update/update; manager/state/raft/raft.go::MemoryStore/Run/ProposeValue; manager/manager.go::becomeLeader.

5. The orchestrator creates work; the scheduler only places it

Once the service says replicas = 2, the replicated orchestrator compares desired slots with existing tasks.

wanted slots:   1, 2
current tasks:  only slot 1
                 ↓
create a Task for missing slot 2

If there are too many replicas, the orchestrator moves excess tasks toward removal. If a task needs replacement, the restart/update machinery creates a new task object rather than trying to “teleport” the old process.

The scheduler sees unassigned tasks and evaluates candidate nodes. Placement constraints, availability, and resource fit matter here. Its decisive output is much smaller than people often imagine:

source microscope
newT.NodeID = node.ID
newT.Status.State = ASSIGNED

Then it writes the updated task back to the manager store. The scheduler has still not created a container. It has converted:

Task: "someone must run this"
        ↓
Task: "node X must run this"

Anchors: SwarmKit pinned commit · manager/orchestrator/replicated/services.go::reconcile; manager/scheduler/scheduler.go scheduling decision path.

6. Assignment is the bridge from cluster state to one worker

After the scheduler writes NodeID = X, the dispatcher watches tasks for node X. Its Assignments RPC sends a full initial set and then incremental changes.

That stream contains more than a command to “start nginx.” The worker may need task dependencies too. The pinned worker assignment path deliberately reconciles secrets and configs before task state, then volumes. This closes the manager/distribution half that Lesson 36 deferred.

manager store
   ↓ tasks assigned to node X + required dependencies
Dispatcher.Assignments stream
   ↓
worker Agent
   ├── reconcile secrets/configs
   ├── reconcile task state
   └── reconcile volumes
   ↓
exec.Resolve(task, executor)
   ↓
local task controller

The controller advances the task through preparation/start states. In Docker Engine's Swarm container executor, preparation ensures the local task's networks/volumes/image, then the adapter calls:

source microscope
CreateManagedContainer(...)
ContainerStart(...)

This is the runtime handoff. From here, container creation/start follows the already-taught Docker path through containerd → shim → runc → Linux kernel. Swarm remains above that path as the control loop observing the task's reported state.

Anchors: SwarmKit pinned commit · manager/dispatcher/dispatcher.go::Assignments; agent/worker.go::Worker.Assign/newTaskManager; agent/exec/controller.go::Do. Docker Engine 29.6.2 · daemon/cluster/executor/container/controller.go::Prepare/Start; adapter.go::create/start.

7. Reconciliation: failure, scale, and update all come back to Tasks

The worker reports task status back to the manager. That makes Swarm a feedback loop rather than a one-shot launcher:

Service desired state
      ↓
Tasks → scheduled → workers → task status
  ↑                              ↓
  └──── orchestrator compares ───┘

Failure

If a task becomes terminal and the restart policy says it should be replaced, the restart supervisor marks the old task for shutdown, creates a new Task with a new task ID, and lets that replacement enter scheduling/execution.

correction

Swarm does not move a live container from a dead node to another node. A replacement task is created, scheduled, and realized as a new container wherever the scheduler places it.

Scale

docker service scale web=3 updates the service's desired replica count. The replicated orchestrator then notices one missing slot and creates its task. Scaling down drives excess tasks toward removal.

Update

A changed service specification is again desired-state mutation. The updater identifies dirty replica slots and creates replacement tasks from the new service spec. Update order can be stop-first or start-first; either way the unit being replaced is a task, and task status feeds failure monitoring/rollback decisions.

source microscope
Restart: old DesiredState → SHUTDOWN
         NewTask(...) → store.CreateTask(...)

Update:  NewTask(new ServiceSpec) → store.CreateTask(...)

Anchors: SwarmKit pinned commit · manager/orchestrator/restart/restart.go::Supervisor.Restart; manager/orchestrator/update/updater.go::Updater.worker/updateTask.

8. Networking is a second pipeline after placement

Scheduling answers which node runs the task. Networking answers how packets reach that task. Do not merge the two mechanisms.

Our service attaches to appnet, a Swarm-scoped overlay network. On a Linux worker that needs the network, Docker's overlay driver creates an overlay-network sandbox containing a bridge and a VXLAN device. VXLAN is the kernel tunnel device that carries overlay Ethernet frames between participating hosts over the underlay IP network.

container endpoint
      ↓ local virtual Ethernet / bridge side
Swarm overlay sandbox
      ↓ VXLAN device
host underlay network
      ↓ UDP VXLAN traffic between nodes
remote host overlay sandbox
      ↓
remote task endpoint

For service-level virtual-IP load balancing, the pinned Linux service code creates an IPVS service and adds task endpoint IPs as destinations. IPVS is a Linux kernel load-balancing facility; Swarm/libnetwork programs it, but the kernel performs packet forwarding.

The published 8080:80 path adds another network: Swarm creates a special ingress network when the cluster is first initialized. In ingress publish mode, the routing mesh uses that ingress plumbing so a published port can accept traffic through Swarm's ingress path instead of requiring the client to know which node currently hosts a replica.

kernel boundary

Swarm decides desired network/service state; dockerd's network code realizes VXLAN/IPVS/firewall objects; the Linux kernel carries the live packets. Lessons 33–34 already taught the namespace/veth/kernel-packet foundations, so they are not repeated here.

Anchors: Docker Engine 29.6.2 · daemon/libnetwork/drivers/overlay/ov_network.go::setupSubnetSandbox (bridge + VXLAN); daemon/libnetwork/service_linux.go::addLBBackend (IPVS VIP/backend programming). SwarmKit pinned commit · manager/manager.go::becomeLeader creates the default ingress network for a fresh cluster.

9. Inspect it yourself: watch the objects appear in order

Linux Engine experiment

Use a disposable Docker host. If the host is already in a Swarm, do not re-initialize or leave it just for this experiment.

# 1. Start a one-node Swarm control plane.
docker swarm init

docker node ls

# 2. Create the overlay, then the desired Service.
docker network create --driver overlay appnet

docker service create \
  --name web \
  --replicas 2 \
  --network appnet \
  --publish published=8080,target=80 \
  nginx:1.27-alpine

# 3. Service is one desired-state object.
docker service inspect web --format '{{json .Spec.Mode}}'

# 4. Tasks are separate objects/attempts.
docker service ps web --no-trunc

# 5. The local worker finally has ordinary Docker containers.
docker ps --filter label=com.docker.swarm.service.name=web

# 6. Change desired replica count; watch the task set change.
docker service scale web=3
docker service ps web --no-trunc

# 7. Force an update and compare old/new Task IDs.
docker service update --force web
docker service ps web --no-trunc

# 8. On a rootful Linux Engine, inspect persisted manager Raft state.
ROOT=$(docker info --format '{{.DockerRootDir}}')
sudo find "$ROOT/swarm/raft" -maxdepth 2 -type f -print

# 9. Optional: inspect Docker network namespaces for VXLAN devices.
for ns in /var/run/docker/netns/*; do
  echo "--- $ns"
  sudo nsenter --net="$ns" ip -d link show type vxlan 2>/dev/null || true
done

# Cleanup.
docker service rm web
docker network rm appnet
docker swarm leave --force

On a one-node Swarm, all replicas may be scheduled on that same node. That does not change the object chain; multi-node placement merely makes the scheduler's NodeID choices visible across hosts.

What you should be able to predict

  1. Why does docker service create --replicas 2 produce one Service but multiple Tasks?
  2. At what exact step does a task gain a node assignment?
  3. Which component finally creates the local Docker container?
  4. Why can a manager survive a process restart without forgetting the cluster's desired state?
  5. Why is “Swarm moved my container to another node” technically inaccurate?

If you remember only one distinction, make it this:

load-bearing relationship

Compose (Lesson 42) is a client-side reconciler that stops at the Engine API. Swarm is a server-side, long-running cluster reconciler inside dockerd. Both eventually create ordinary Docker containers; neither replaces containerd, shim, runc, or the Linux kernel.
