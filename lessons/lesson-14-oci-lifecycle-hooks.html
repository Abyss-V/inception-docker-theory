The OCI lifecycle & hooks: the choreography of a container

We've built all the pieces — namespaces, cgroups, capabilities, seccomp, LSMs. This lesson is the timeline that assembles them: the four states a container moves through, the ordered steps between them, and the six points where the runtime will run your code.

Everything in Part II answered "what is a container made of?" This lesson answers "in what order does it come together, and where can I intervene?" The OCI runtime-spec doesn't leave that to each runtime's whim — it defines a precise state machine: four named states, thirteen ordered steps to move between them, and six hook points where the runtime pauses to execute programs you supply. This is the spec that makes runc, crun, and every other OCI runtime behave identically, and it's how tools like GPU runtimes and network plugins splice themselves into container startup.

The intuition

A container is a state machine, built in two phases

The most important idea here is a split most people never notice: creating a container and starting it are separate operations. The create operation builds the entire runtime environment — it creates the namespaces, applies the cgroups, performs the mounts, prepares the capabilities, seccomp filter, and LSM labels — everything from the last eight lessons. But it stops short of running your program. The container now sits in a stable state called created: fully assembled, not yet alive. Only the separate start operation executes your program, moving it to running.

Why split it? Because that pause between "environment exists" and "user code runs" is a priceless window. The runtime has reached a controlled pre-exec state, but the spec deliberately limits what an early hook may assume is already active — so it's the safe moment to customize the container (wire up its network, inject a device, tweak a mount) before it comes to life. The hooks live in exactly this window. And the split is visible to you every day: docker create leaves a container in created; docker start runs it. It's also why the shim from Lesson 5 could hold a ready-but-not-started container — its Task API's Create and Start are these two operations.

Mechanism 1

Four states, and what each really means

The runtime-spec's State.status field (in runtime.md) is REQUIRED to be one of exactly four values, each pinned to a step in the lifecycle. creating means the runtime is in the middle of building the environment (step 2). created means the create operation finished and the container process has neither exited nor executed the user program — assembled but dormant. running means the user program has been executed and hasn't exited (after step 8). stopped means the process has exited (step 10). Alongside the status, the State carries the container id, its pid (REQUIRED once created/running), and the bundle path.

The subtlety worth holding onto is that created is not a fleeting transition — it's a genuine resting state a container can sit in indefinitely. That's the whole basis of the two-phase model.

Mechanism 2

Six hooks — and the detail everyone misses: where they run

At defined points, the runtime executes external programs you list in config.json. There are six kinds, and the spec (config.md, hooks section) is emphatic about something most explanations skip: each hook runs in a specific namespace context. A hook in the runtime namespace sees the host's world (host PIDs, host network); a hook in the container namespace runs inside the container's isolated view. That single fact determines what each hook can usefully do.

HookRuns inWhen & what it's for
createRuntimeruntime nsDuring create, after the mount namespace and configured mounts exist but before pivot_root. Runtime-namespace view; cgroup placement and LSM labels are not guaranteed yet.
createContainercontainer nsDuring create, after createRuntime, in the container namespace before pivot_root. Mounts are available; cgroup placement and LSM labels are not guaranteed yet.
startContainercontainer nsDuring start, the last thing before the runtime execs your program. In-container, last-second setup your program will see.
poststartruntime nsRight after your program starts running. For notifications / bookkeeping on the host side.
poststopruntime nsAfter the OCI container has been deleted, but before delete returns. Cleanup or debug remaining host-side resources.
prestartruntime nsDeprecated. Replaced by the three granular create/start hooks, which give finer control. Still honored for backward compatibility.
OCI v1.3.0 precision

“The runtime environment has been created” does not mean every configured mechanism is active at the early create hooks. Hook authors may rely on the mount namespace and configured mounts; cgroup placement and SELinux/AppArmor labels might still be pending. poststop is tied to the OCI delete operation: it runs after the container has been deleted but before delete returns.

Why the namespace split matters

Networking is the canonical example: a createRuntime hook runs in the runtime namespace, so it can see the host network and create a veth pair that straddles host and container — something a container-namespace hook couldn't do because it can't see the host side. Conversely, a setup step that must be visible to your program from its very first instruction belongs in startContainer, inside the container, immediately before exec. Pick the wrong namespace and the hook is looking at the wrong world.

You've used hooks without knowing it. The NVIDIA container runtime injects GPU devices and driver libraries into a container through an OCI hook at create time; CNI network plugins are wired in the same way. When you run --gpus all, a hook fires in the runtime namespace and edits the container's device access before your program starts.
Mechanism 3

Hooks can veto the container

Hooks aren't passive callbacks — their exit status steers the lifecycle. The spec requires that if any hook from prestart through poststart fails, the runtime MUST generate an error, stop the container, and jump straight to the destroy step (undoing the environment) followed by poststop. In other words, a failing setup hook aborts the whole launch — a network hook that can't attach the interface will prevent the container from ever running your program, which is exactly what you want.

There's one deliberate exception. If poststop fails, the runtime only logs a warning and continues, because by then the container is already being torn down — there's nothing left to abort, so a cleanup error mustn't wedge the teardown. This asymmetry (setup failures are fatal, teardown failures are warnings) is a small but telling piece of the spec's design.

Where this corrects the familiar version

Two things. First, "docker run starts a container" hides the two-step reality: run is create + start, and the created state in between is real and stable, not a blink. Second, hooks are usually described as "scripts that run around the container," which misses the load-bearing detail: which namespace a hook runs in decides what it can do, and the spec fixes this per hook (createRuntime/poststart/poststop in the runtime namespace; createContainer/startContainer inside the container). That's not trivia — it's why network setup is a createRuntime hook and not a startContainer one. And note the prestart hook is deprecated; new integrations should use the three granular hooks.

Where we are

Summary & end of Part II

The OCI runtime-spec defines a container as a state machine: four states — creating → created → running → stopped — traversed by thirteen ordered steps, split into a create phase (build the whole environment, stop at created) and a start phase (exec the user program, reach running). That split creates a window in which six hooks can run your code, and the crucial detail is where: createRuntime, poststart, and poststop run in the runtime namespace (host view); createContainer and startContainer run inside the container; prestart is the deprecated ancestor. A failing setup hook aborts the launch; a failing poststop is only a warning. This is the timeline into which all of Part II slots — step 2, "build the environment," is namespaces, cgroups, capabilities, seccomp, and LSMs, all at once. That closes Part II.
