Snapshotters & the storage-driver landscape

Something has to manage the stack of layers — unpack them, track parent-child chains, and hand a rootfs to each container. Docker has done this two ways: the old graphdriver model, and containerd's newer snapshotter model. This is the map of both.

Lesson 15 showed the kernel mechanism (OverlayFS) that unions layers. But something above the kernel has to drive it: decide where each layer's directory lives, remember which layer is the parent of which, produce the writable top layer for a new container, and clean it all up. That management job has had two designs in Docker's history — the original graphdriver and containerd's snapshotter — and the difference between them explains everything from why overlay2 is the name you usually see to how modern registries can start a container before the image finishes downloading.

The intuition

Two eras of the same job

In Docker's original architecture, the daemon owned an image/layer store and delegated the filesystem work to a graphdriver. The driver's contract was coarse: "given this stack of layers, mount it and give me back a root filesystem." The daemon managed layer identity and metadata itself; the driver just materialized directories. overlay2, aufs, btrfs, devicemapper, and vfs are all graphdrivers.

containerd redesigned this as the snapshotter. Instead of returning a mounted rootfs, a snapshotter deals only in snapshots and their parent relationships, and its job is to return mount descriptors — the exact lowerdir/upperdir/workdir recipe from Lesson 15 — which containerd then applies. That sounds like a small change, but moving from "hand me a rootfs" to "hand me a description of how to mount one" is what makes remote and lazy-loading backends possible, as we'll see at the end.

Mechanism 1

The snapshotter model: Prepare, Commit, and a parent chain

The whole model lives in one interface (core/snapshots/snapshotter.go). A snapshot represents a filesystem state, and every snapshot has a parent — and, as the source puts it, "a diff between a parent and its snapshot generates a classic layer." Snapshots come in three kinds (KindView, KindActive, KindCommitted), and two verbs move between them:

Prepare creates an active snapshot on top of a committed parent — a writable layer you can mount and change. Commit freezes an active snapshot into a committed one, which is immutable and can itself serve as a parent for the next layer. The rules are strict and clarifying: active snapshots can never be a parent, committed snapshots can never be written, and one never turns into the other — Commit always produces a fresh committed snapshot. (A view is just a read-only mount of an existing snapshot.)

Why this framing is the whole game

Both of Docker's core storage activities are the same two verbs. Building an image is Prepare → run a build step → Commit, repeated once per layer, growing the committed chain. Running a container is a single Prepare that creates an active snapshot on top of the image's committed chain — the writable layer — which is simply discarded (never committed) when the container is removed. Image layers and container scratch space are the same object in two states.

Mechanism 2

The graphdriver model, and how it differs

Docker's classic image store still uses a graphdriver, selected by a priority list. On Linux that list is, verbatim from the source (daemon/graphdriver/driver_linux.go), overlay2,fuse-overlayfs,btrfs,zfs,vfs — the daemon walks it and picks the first supported, non-deprecated driver, which on almost every modern host is overlay2. The functional difference from a snapshotter is that a graphdriver exposes operations like Get/Put/Diff/ApplyDiff that materialize and mount a layer's rootfs, with the daemon holding all the layer metadata. The snapshotter instead returns a mount recipe and owns the parent-chain metadata itself. That's why the snapshotter model is more modular and pluggable — and why containerd could grow backends a graphdriver could never support.

Which one is running on your machine? Historically Docker used graphdrivers directly. Modern Docker increasingly runs on containerd with the containerd image store, which uses snapshotters. During the transition both exist: classic mode shows a graphdriver like overlay2; the containerd image store shows a snapshotter like overlayfs. Same OverlayFS underneath — different manager above it.
Mechanism 3

The landscape: who uses what CoW, and when

All of these do the same job — stack layers, isolate a writable top — but they get their copy-on-write from different places. containerd ships overlay, native, btrfs, devmapper, blockfile, and erofs snapshotters (plugins/snapshots/); the graphdriver names differ slightly but map to the same technologies.

The payoff: lazy pulling

Normally a container can't start until every layer is downloaded and unpacked — for a multi-gigabyte image that's a long wait, most of it spent on files the container never reads. The stargz and nydus snapshotters change this: they let the container start after fetching only the image's metadata, then stream individual file contents from the registry on demand as the running program actually opens them. This is impossible with a graphdriver, which must hand back a fully-materialized rootfs — but natural for a snapshotter, whose job is only to return a mount recipe, which can point at a remote-backed filesystem. It's the clearest illustration of why the "return a description, not a rootfs" redesign mattered.

Where this corrects the familiar version

"The storage driver is OverlayFS" conflates two layers: OverlayFS is the kernel mechanism (Lesson 15); the storage driver/snapshotter is the manager above it that decides where layers live and how they chain. That's why the same OverlayFS can be driven by an overlay2 graphdriver or an overlayfs snapshotter — different managers, one kernel feature. And the reason to care about the distinction isn't academic: only the snapshotter model's "return a mount recipe" contract enables lazy/remote pulling (stargz/nydus), which is where large-image startup is heading. The other drivers (vfs, btrfs, zfs, devmapper) are situational — you reach for them only when overlay isn't an option.

Where we are

Summary

Above the kernel's OverlayFS sits a manager that tracks layers and produces rootfs. Docker has two: the legacy graphdriver (daemon-owned metadata; the driver materializes and mounts a rootfs; priority list overlay2,fuse-overlayfs,btrfs,zfs,vfs) and containerd's snapshotter (owns its own parent-chain metadata; returns a mount recipe). The snapshotter model reduces to two verbs — Prepare makes an active writable snapshot from a committed parent, Commit freezes it into an immutable, parent-able committed one — so an image is a chain of committed snapshots and a running container is an active snapshot on top. The various backends (overlay, native/vfs, btrfs/zfs, devmapper, fuse-overlayfs) differ only in where their copy-on-write comes from, and the snapshotter's mount-recipe contract is what unlocks lazy pulling with stargz/nydus. We've now seen how layers are managed.
