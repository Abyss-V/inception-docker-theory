Manifest, config & digests: the whole image

Lesson 17 was one layer. Now we assemble them into an image — which turns out to be a small tree of JSON documents, each pointing at the next by hash.

The idea in one sentence

An image is not a single file — it's a manifest at the top that points to one config (the settings) and several layers (the tars from Lesson 17), each referenced by its hash.

1 Start here

An image is a tree of documents, not a file

Plain version: "pull an image" doesn't fetch one blob. It fetches a little index that lists the parts, then fetches the parts.

When you docker pull nginx:1.25, there's no single "nginx file." What you get is a small tree: at the top a manifest (an index), which names one config document (the image's settings) and a handful of layer blobs (the tars from Lesson 17). Everything below is just: what those documents contain, and how they point at each other.

2 The glue

Everything points by "descriptor" — {mediaType, digest, size}

Plain version: every "pointer" in an image is the same 3-field thing: what kind of blob, its hash, and its size.

Before the manifest makes sense, you need the one link primitive OCI uses everywhere: the descriptor. A descriptor is a tiny object with three required fields (from descriptor.md): mediaType (what kind of thing this is), digest (the sha256 that both names and locates the bytes), and size (how many bytes). That's it. Every reference in an image — manifest→config, manifest→each layer — is a descriptor. Once you see "descriptor," the whole image is just descriptors pointing at blobs by digest.

3 The top node

The manifest: the index of one image

Plain version: the manifest is a short JSON that says "this image = this config blob + these layer blobs."

The manifest (from manifest.md) has four things that matter: schemaVersion, mediaType, a config (one descriptor, pointing at the settings blob), and layers (an array of descriptors, pointing at the layer tars, bottom-to-top). That's the entire top node — it lists the parts and nothing else. And here's the important bit: the manifest is itself a blob with its own digest, and that digest is the image's true identity — the thing a tag ultimately points to.

4 The settings

The config: runtime defaults + the layer list

Plain version: the config blob holds two things — how to run the image by default, and the ordered list of its layers' content-hashes.

The config blob (from config.md) carries two distinct kinds of information. First, the runtime defaults baked into the image, under a config object: Env, Cmd, Entrypoint, WorkingDir, User, ExposedPorts, Volumes — this is where your Dockerfile's ENV/CMD/ENTRYPOINT/WORKDIR/USER/EXPOSE end up — plus the architecture and os from Lesson 1. Second, under rootfs.diff_ids, the ordered list of the layers' diffIDs — the exact input that gets folded into ChainIDs (the supplement). It also has a history array, one entry per build step.

This is the bridge to running. Those runtime defaults don't stay in the image — when you start a container, they're copied into the container's config.json (the runtime spec from Lesson 14): the image config's Entrypoint+Cmd become the process's arguments, Env becomes its environment, User its uid. The image config is the defaults; the runtime spec is those defaults resolved for one container (Lesson 21).
5 The payoff

Now the two hashes have homes

Plain version: the digest/diffID confusion from Lesson 17 dissolves once you see which document each lives in.

Lesson 17 said a layer has two hashes and it felt abstract. Here they are in their places: the manifest lists each layer by its digest — the compressed-blob hash, which is what you download. The config lists each layer by its diffID — the uncompressed-content hash, which is what gets verified after decompression and folded into the ChainID. Same layers, two documents, two hashes, each where it belongs: digest in the manifest (for transfer), diffID in the config (for identity).

6 Name to bytes

How a tag becomes an image

Plain version: a tag is just a nickname the registry maps to a manifest's hash; pulling follows the tree down from there.

A tag like nginx:1.25 is a mutable name. The registry maps it to a manifest digest, and from there the pull is deterministic: fetch the manifest, read its config descriptor and layer descriptors, download each of those blobs by digest. So resolution is tag → manifest digest → config + layers. Because the tag can be re-pointed but a digest can't, pulling nginx@sha256:… (by digest) always gets the exact same image, whereas nginx:1.25 might change under you. That difference — reproducible digests vs. movable tags — is why production deployments pin digests.

Check yourself

  • An image is a tree: a manifest at the top → one config blob + several layer blobs. Not one file.
  • Every pointer is a descriptor = {mediaType, digest, size}.
  • The manifest is the index (config descriptor + layer descriptors); its own digest is the image's identity.
  • The config holds runtime defaults (Env/Cmd/Entrypoint/User/…, architecture/os) and rootfs.diff_ids (the ChainID input).
  • Two hashes, two homes: digest in the manifest (compressed, for download), diffID in the config (uncompressed, for identity).
  • A tag is a mutable name → a manifest digest; pulling by @sha256:… pins the exact image.
Where this corrects the familiar version

"An image is a stack of layers" is only half of it — an image is a manifest plus a config plus the layers, and the config (the runtime defaults + diffID list) is easy to forget even though it's what makes docker run nginx know to launch nginx. Also: a tag is not the image — it's a mutable label pointing at a manifest digest, which is why "it worked yesterday" can break when a tag is re-pushed, and why digests are the reproducible identity.

Where we are

Summary

An image is a small content-addressed tree: a manifest (index) referencing — via descriptors ({mediaType, digest, size}) — one config blob and several layer blobs. The config carries the runtime defaults (Env, Cmd, Entrypoint, User, architecture/os) that later seed the container's runtime spec, plus rootfs.diff_ids that feed ChainID. The manifest lists layers by digest (compressed, for transfer); the config lists them by diffID (uncompressed, for identity) — the two hashes finally in their homes. A tag is a mutable name resolving to a manifest digest, so pinning @sha256:… is the reproducible way to name an image.
