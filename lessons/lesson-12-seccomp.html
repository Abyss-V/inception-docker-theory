seccomp: bricking up the syscalls a container never uses

Capabilities restrict privileged operations. seccomp restricts something more basic — which system calls a process may make at all — shrinking the kernel's attack surface. And Docker's default profile is cleverly wired to move in lockstep with capabilities.

Recall the shared-kernel wall from Lesson 1: a container's only real boundary is the host kernel, and every syscall is a door through it. The kernel offers around 350 syscalls; a typical container uses maybe a fifth of them. The rest are doors nobody in the container walks through — but a bug behind any one of them is a potential escape. seccomp ("secure computing mode") lets you brick up the unused doors, so a kernel vulnerability in a syscall your container never calls simply can't be reached. This is a different axis of defense from capabilities, and the two turn out to be wired together.

The intuition

Two different questions: "may you?" vs "can you even ask?"

Capabilities (Lesson 11) answer "are you permitted to perform this privileged operation?" — the kernel lets the syscall run, then checks a capability partway through. seccomp answers a more fundamental question, earlier: "are you allowed to make this syscall at all?" If a syscall is denied by seccomp, the kernel never even executes its logic — the call is rejected at the door.

Why does that matter if capabilities already guard the dangerous stuff? Because plenty of syscalls are dangerous despite not needing a capability — the danger is a bug in the syscall's implementation, not the operation itself. Kernel exploits routinely live in obscure, rarely-audited syscalls (old keyring calls, userfaultfd, exotic filesystem calls). Your container doesn't need those, so the safest thing is to make them un-callable. seccomp is attack-surface reduction: fewer reachable doors, fewer places a kernel bug can bite.

Mechanism 1

A filter the kernel runs on every single syscall

Step 1 · Explain

seccomp works by installing a tiny BPF program — a little decision tree that runs in the kernel — as a syscall filter. Once installed, the kernel runs this program on every syscall the process makes, before executing it. The program is handed the syscall number (and, if you want, the raw argument values) and returns a verdict: ALLOW (proceed), ERRNO (reject, return an error code), KILL (terminate the process), TRAP, LOG, or NOTIFY (hand off to a supervisor). The filter is a one-way ratchet: once set it can't be removed, and every child process inherits it.

There's one enabling rule worth knowing. An unprivileged process may only install a seccomp filter if it has first set the no_new_privs flag — a promise to the kernel that this process can never gain privileges via a setuid binary. Without that promise, you could use a filter to trick a setuid-root program into misbehaving, so the kernel forbids it. runc sets both:

The part that does the job

The whole mechanism is: compile the profile to a BPF program, then load it so the kernel consults it on every syscall. Because the filter is inherited and irreversible, the container's PID 1 gets it and so does everything it spawns — there's no escaping it from inside. And no_new_privs is the precondition that makes the whole thing safe to use without being root.

Mechanism 2

The profile: an allowlist that errors by default

Step 1 · Explain

A seccomp profile has a default action plus a list of per-syscall rules. Docker's default profile takes the safe approach: the default action is "return an error," and then it explicitly allows the ~350 syscalls normal programs need. Anything not on the allowlist hits the default and fails. Two design choices are worth pausing on. First, the default is ERRNO (fail with an error), not KILL — a blocked syscall returns something like "operation not permitted" and the program can handle it, rather than being executed on the spot. Second, the profile is architecture-aware, because syscall numbers differ per CPU architecture; the same profile carries an arch map so it applies correctly on x86-64, arm64, and others.

Step 2 · The source
The part that does the job

defaultAction: SCMP_ACT_ERRNO + a big SCMP_ACT_ALLOW list is an allowlist: known-good calls pass, everything else errors. Choosing ERRNO over KILL is a compatibility decision — programs that probe for a blocked syscall get a clean failure and fall back, instead of being killed. And archMap exists because "syscall 165" is mount on x86-64 but something else on arm64; the profile must match by architecture.

Mechanism 3

What's on the deny side, and why

Step 1 · Explain

The syscalls Docker leaves off the allowlist (~40-odd notable ones) are exactly the ones a normal app never needs but an attacker would love. They cluster into a few families:

Load kernel code

init_module, finit_module, delete_module — insert a kernel module = a rootkit with full host control.

Replace the kernel

kexec_load, kexec_file_load — boot an arbitrary kernel out from under the host.

Mount & namespace admin

mount, umount2, pivot_root, setns, unshare — reshape the filesystem / escape isolation (gated on CAP_SYS_ADMIN, below).

Change the clock

settimeofday, clock_settime, adjtimex — move the host's wall clock; reboot — restart the machine.

Kernel internals

bpf, perf_event_open, userfaultfd, keyctl, add_key — powerful, exploit-prone kernel subsystems.

Raw hardware / misc

ioperm, iopl — raw I/O ports; swapon/swapoff, acct — system-wide state a container shouldn't touch.
The part that does the job

None of these are things a web app, database, or language runtime calls in normal operation, but every one is a lever an exploit could pull. Removing them from the allowlist means that even if a container is fully compromised — even running as root — those doors are already welded shut. This is why the seccomp profile blocks meaningfully more than capabilities alone: it denies dangerous syscalls, including ones no capability even guards.

Mechanism 4 · the payoff

seccomp and capabilities are wired together

Step 1 · Explain

Here's the elegant part most explanations miss. Docker's seccomp profile isn't a fixed list — it's capability-aware. A whole group of syscalls (mount, unshare, setns, sethostname, bpf, and friends) is added to the allowlist only if the container holds CAP_SYS_ADMIN. So the two walls stay consistent: grant the capability and the matching syscalls unblock; don't, and both walls keep them out. You never end up with a capability you can't use or a syscall you shouldn't have.

The part that does the job

Two things click here. The Includes: Caps filter is the coupling: seccomp's allowlist expands when you add CAP_SYS_ADMIN. And the clone argument filter is seccomp reaching inside the call — it allows clone normally but denies it when the flags contain any CLONE_NEW* bit, which is exactly the namespace-creation mechanism from Lesson 6. So a default container cannot create new namespaces (can't nest containers) — not because of capabilities, but because seccomp inspects the argument and says no. (The profile also forces clone3 to return ENOSYS, so programs fall back to the older clone whose arguments seccomp can inspect — clone3 passes its flags in a struct the filter can't read.)

Where this corrects the familiar version

Three things people get wrong. First, seccomp is often described as "the syscall whitelist," missing that it can filter by arguments too — the clone flags filter is the proof. Second, "seccomp and capabilities are separate features" understates it: Docker's profile couples them, expanding the syscall allowlist when you add CAP_SYS_ADMIN. Third, and most important operationally: --privileged and --security-opt seccomp=unconfined remove this wall entirely. A privileged container has no seccomp filter and all capabilities — both walls of this lesson and the last are gone at once. That's why --privileged should be treated as "give this container the kernel."

Where we are

Summary

seccomp shrinks the kernel's attack surface by filtering which syscalls a process may make. It installs a BPF filter the kernel runs on every syscall (requiring no_new_privs first, and inherited irreversibly by children), returning a verdict per call. Docker's default profile is an allowlist: defaultAction: SCMP_ACT_ERRNO plus ~350 explicitly-allowed syscalls, arch-aware via archMap, so unlisted calls fail with an error rather than killing the process. The denied set — module loading, kexec, mount/namespace admin, clock changes, bpf, userfaultfd, keyrings — are exploit-prone doors no normal app uses. And crucially the profile is coupled to capabilities: a group of syscalls unblocks only with CAP_SYS_ADMIN, and an argument filter on clone blocks namespace creation unless you hold it — so a default container can't even spin up new namespaces. Two walls that move together, both erased by --privileged. Next: the third security primitive — the Linux Security Modules, AppArmor and SELinux, which guard what files and resources a container may touch.
